## Context

An assurance analysis relates to a node in more than one way, and a single column cannot answer more than one question. An earlier design used `node.analysis_id` for both "who produced this" and "who uses this", and that is the model this codebase deliberately migrated away from: an FMEA enumerating failure modes against the control-structure nodes an STPA identified has those nodes in front of it without owning them. One column forces the analyst to copy them, and the copies drift.

Three problems remained open around that aggregate.

**Provenance was optional at creation and mutable by generic edit.** `assurance_create_node` takes `analysis_id: str | None = None`, and `assurance_edit_node` exposes the same field. Twenty-six nodes in the live store have no analysis, and the reason is a gap in the write surface rather than carelessness — `analysis_id` could be set at creation and never afterwards, so a node authored before the aggregate existed could not be attributed to anything. Reattribution through `edit_node` was added deliberately, to repair exactly those. It is also, as a general edit, a path by which a node could be moved from one analysis to another.

**Deletion had rules that could not be followed.** `delete_analysis` blocks when the analysis still owns nodes and tells the caller to "reassign or delete" them — but reassignment is what immutable provenance forbids, so the advice cannot be taken. Separately, `assurance_analysis_members` carries a foreign key on `node_id` and none on `analysis_id` (SQLite cannot retrofit one, and the shipped store predates the constraint), so deleting an analysis that only *borrowed* nodes leaves membership rows pointing at nothing.

**FMEA was addressed as though it were a child of the store rather than a kind of analysis.** The matrix endpoint returned every failure mode when no analysis was selected, by design, and the GUI told the user so. That makes the unscoped result the default answer to a question that only makes sense within one analysis.

Alternatives considered:

- **Collapse participation into authorship again.** Rejected: it is the model the code moved away from, and its failure mode is silent duplication.
- **Attribute the twenty-six orphans automatically — to their first participating analysis, or to a catch-all.** Rejected: that invents provenance. A record of who produced a safety finding is worth nothing if the system is willing to guess it.
- **Keep provenance mutable and rely on the audit log.** Rejected: an audit trail records that authorship changed; it does not make the earlier claim true again. Downstream evidence citing the node's author becomes wrong, not merely historical.
- **Cascade deletion of an analysis to the nodes it authored.** Rejected: another analysis may reference those nodes, and a cascade destroys work whose owner never asked for it.
- **Three explicit relations, immutable provenance with one audited repair path, and refusal rather than cascade** (chosen).

## Decision

### Three relations

| Relation | Storage | Cardinality | Meaning |
|---|---|---|---|
| Filing | group → analysis | flat | Deleting a folder never deletes its contents |
| Authorship / provenance | `node.analysis_id` | single-valued | The analysis that produced the node |
| Participation | `analysis_members` | many-to-many | How one method draws on another's work |

The working set of an analysis is **authored ∪ participating**, exposure-filtered before it is returned, with edges surviving only when both endpoints are visible. It carries the authored ids separately, because a borrowed node has to look borrowed. That aggregate is the boundary; a handler filtering nodes itself is not.

**Participation is directional.** A node participates in an analysis; an analysis never participates in a node. The analysis therefore owns a collection of `participating-nodes`, which is what prevents the relation from being read backwards. Asserting a participation is idempotent. A node must not acquire a participation relation to its *own* provenance analysis: that request is refused as conceptually invalid rather than silently deduplicated, and no redundant row is written.

### Provenance lifecycle

| Transition | Verdict |
|---|---|
| Create without provenance | Rejected — creation requires a valid analysis |
| Unattributed → an existing analysis | Allowed, only through a dedicated audited provenance-assignment use case |
| Analysis A → analysis B | Rejected |
| Analysis A → none | Rejected |
| Provenance through the general edit contract | Removed — the field leaves the edit DTO |

Creation puts the provenance analysis in the path, because it is mandatory aggregate context rather than a field of the node. Provenance is otherwise addressed as the node's singleton provenance relation: re-asserting the same analysis is idempotent, asserting a different one is refused, and that route is the *only* one that may set it. Assignment uses a compare-and-set store operation, so two concurrent assignments cannot both succeed.

**Legacy policy for the unattributed nodes.** The existing store opens without destructive rewriting. Unattributed nodes are classified as explicit *legacy-invalid* records: readable, visible in a repair surface with their existing relations preserved, and **provenance assignment is the only mutation permitted** — no ordinary edit, no new participation, no new edge, no factor assessment until they are repaired. Without that, an unattributed node stays fully active while the invariant is claimed to be under restoration. New orphans are impossible, and the invariant is declared satisfied only when none remain. The GUI's "No analysis" scope becomes that repair surface, not a normal browsing scope.

### Deletion

| Operation | Rule |
|---|---|
| Delete an analysis that authored entities | Refused as `analysis_not_empty`. No reassignment is suggested, because none is possible: the entities remain, or are explicitly deleted |
| Delete an analysis (any) | Removes the participation records of nodes participating in it; the nodes and their provenance are unchanged |
| Delete a canonical entity other analyses reference | Refused as `entity_in_use` until the references are explicitly removed — never a silent cascade |
| Delete a group | Unfiles its analyses without deleting them |

Deleting an analysis and removing the participation rows of its participating nodes are **one store-level unit of work**, not an application-layer loop over lower-level calls. The in-use check and the deletion happen inside the same serialized operation, and the complete read–check–write–audit sequence runs inside the assurance single-writer boundary. Rules that exist only in application code are advisory; each of the four store backends gets both the delegation test and the original regression scenario.

### Addressing and projections

FMEA is a **method** of analysis, identified by a discriminator, not a child resource. There is one canonical analysis collection; the method-specific projections — the matrix, the completeness report — hang off an identified analysis. A projection asked of an analysis of the wrong method returns a typed mismatch, not an empty result. The completeness report is one operation returning a method-discriminated response, rather than one endpoint per method.

**The unscoped matrix is removed.** With no analysis selected, no matrix request is sent; a method-filtered analysis picker is shown instead. An unknown, hidden or wrong-method analysis produces the defined not-found or mismatch result. Reading every failure mode in the store is not a degraded version of reading one analysis's matrix — it is a different question, and one no surface asks.

A failure-mode subcollection is not introduced: it would be a node-type filter over the analysis's nodes, and the method-specific representation is already the matrix. A subcollection is justified by a distinct contract or behaviour, and that one would have neither.

A factor assessment appends a revision rather than replacing a value, so it is recorded as an append to the node's factor-assessment collection. The node's own provenance determines ownership, so the node id does not appear in the body.

### The MCP surface changes with the application layer

MCP tools reach the same use cases. Leaving them as they are would either break them or leave an unguarded route around the invariant, so provenance becomes mandatory on node creation, the field leaves the edit tool, and a dedicated provenance-assignment tool is added. Tool documentation is regenerated and gated, with signature regressions.

## Consequences

**Positive:**
- Two analyses can share a node without copying it, and a reader can always tell whose work it is.
- A provenance record, once made, is true for the life of the node. Evidence that cites an author does not silently become wrong.
- The twenty-six unattributed nodes are visible as a defect with a repair workflow, rather than invisible as ordinary data.
- No deletion destroys work another analysis depends on, and none leaves membership rows pointing at an analysis that no longer exists.
- A method-specific projection either answers for one analysis or says why it cannot; there is no unscoped answer to mistake for a scoped one.
- The invariants hold for every caller, because they are enforced inside the store and the single-writer boundary rather than in one handler.

**Negative / risks:**
- Creating a node now requires an analysis, so any caller that created one without an analysis must be changed — including MCP callers, whose signatures change in the same release.
- A genuine mis-attribution can no longer be corrected by editing. Correcting it means deleting the node and re-creating it under the right analysis, which loses its id.
- Legacy-invalid nodes are deliberately close to inert. A store with many of them is partly read-only until they are repaired, and that is intended pressure rather than a bug.
- Refusing deletion is less convenient than cascading, and an analyst clearing up an abandoned analysis has more steps.
- Removing the unscoped matrix removes a view someone may have been using as a store-wide report. That report is not reinstated; it was answering a different question.
- Four backends must each implement the atomic deletion and the compare-and-set assignment, so the store port grows and every backend carries both tests.
