## Context

An ArchiMate diagram's picture is laid out by GraphViz through the [PlantUML Engine](../../../projects/diagram-authoring/model/technology/system-software/SSW@1712870400.xVrBYD.plantuml-engine.md). An author can steer it only with a direction, groupings and hidden edges, or replace the generated body with a hand-written one that is then kept verbatim. There are no positions anywhere, so an arrangement that reads well cannot be kept, and a small model change can rearrange a whole view.

Alternatives considered:

- **A third-party diagram editor or router in the browser.** Each one owns the drawing, so the notation, colours, glyphs, icons and specializations the [PlantUML Renderer](../../../projects/diagram-authoring/model/application/application-component/APP@1777293136.yaxrWl.plantuml-renderer.md) already draws would be implemented a second time and kept equal by hand. The one proven router is browser-only and under a licence the product's licence gate refuses.
- **A second diagram format with coordinates**, beside PlantUML. Two sources for one picture.
- **Optional geometry over the existing diagram**, drawn by the server (chosen).

## Decision

A diagram may carry a layout: where each element sits and how large it is, which side and point each relation attaches at and where it bends, where its label sits, and how boxes are sized and stacked. The layout is geometry only, held in the diagram's frontmatter and keyed by the identities the diagram already uses. What the diagram means stays where it is. A diagram without a layout is drawn exactly as before.

Translation in is a render: the diagram is drawn once by PlantUML and its geometry is read from that picture, so taking a layout over starts from the picture shown. Translation out is deletion: removing the layout returns the diagram to PlantUML's arrangement with nothing else changed.

PlantUML stays the notation. An unchanged element is PlantUML's own drawing, placed where the layout says; a resized element is drawn from what the ontology declares about its appearance; relations are drawn as orthogonal lines with end decorations from the one relationship-notation declaration.

The server renders and routes. The browser shows provisional geometry while something is dragged and takes the server's result on drop. The geometry rules the canvas needs while dragging are one specification implemented in the backend and mirrored in the GUI, held equal by shared fixtures.

Every change to an arrangement reaches the diagram as a layout patch, checked and written through the one write path. A change stated as an intent is compiled to that patch: align, distribute, straighten a line, return to the automatic arrangement, nest or unnest an element, and create or delete a grouping. The canvas and an agent's command therefore produce the same layout. Grouping intents change the diagram's groupings, which are content, and drop the box geometry that no longer fits its members.

Saving an arrangement keeps every line the editor routed again — those with an end on a moved element and those something moved across — as the editor showed it, so the server routes no line on a save; a route stated by hand stays as stated. Taking a picture over keeps PlantUML's lines: only a line whose end moved, whose box side moved, or across which something moved is routed again. Every other line keeps PlantUML's course, with its ends carried onto the shapes' borders, so the cost of an edit follows what it moves rather than the size of the diagram.

Arrows stay attached. After every edit from every surface, each end of a relation lies on its element's border and leaves it outward, no segment passes through the relation's own ends, and no relation crosses another element. Two connected elements that overlap are a conflict no route satisfies; the editor marks it and the verifier reports it.

## Consequences

- An arrangement survives model changes: kept elements stay, a new one is placed near its neighbours, removed ones and their routes go. A laid-out diagram no longer gets GraphViz's global rearrangement; returning to it is always one action.
- Every path that produces an image has to honour a layout: the stored picture, the viewer, a lensed view, a download, a preview and an export.
- The stored picture of a laid-out diagram is no longer what PlantUML alone would draw from the body, although the body still renders anywhere PlantUML does, as [Icons on Diagram Elements](ADR@1790305455.DFw6BCk.icons-on-diagram-elements-one-stored-picture-embedded-where-it-is-drawn.md) requires.
- The structure of PlantUML's SVG becomes a contract the reader depends on. The reader refuses a structure it does not recognise: layout editing is withheld and the picture is unaffected.
- Two implementations of the geometry rules exist and must not drift; the shared fixtures are the gate.
- Implemented.
