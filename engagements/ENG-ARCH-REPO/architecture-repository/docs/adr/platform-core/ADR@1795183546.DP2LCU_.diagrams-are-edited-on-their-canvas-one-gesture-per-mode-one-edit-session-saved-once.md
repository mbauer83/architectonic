## Context

A diagram is edited today on a separate page: a sidebar adds entities, offers candidate connections and marks removals, the picture is a preview, and saving is allowed only after previewing. Nothing is changed on the picture itself. The [Scratchpad Canvas](../../../projects/platform-core/model/application/application-component/APP@1786225304.HgIA072.scratchpad-canvas.md) already shows that a canvas with keyboard parity and an undo history works in this product.

Alternatives considered:

- **Keep the sidebar editor and add a separate arrange mode.** Two places to change one diagram, and a mode inside a mode.
- **Let any drag on a viewed diagram create a layout.** A drag in a viewer pans; giving it a second meaning makes a reader's gesture an author's change.
- **A confirmation dialog on the first move.** Obtrusive, and it teaches the author to dismiss it.
- **An edit mode on the canvas, with one meaning per gesture** (chosen).

## Decision

A diagram has two modes. In view mode it is read: selecting, drilling down, zooming, and panning by dragging. In edit mode the canvas is the editor for the whole diagram: arranging it, adding elements and relations from the model, drawing a relation between two elements, creating an element at a point, and removing things from the diagram.

One gesture has one function within a mode. A drag pans in view mode. In edit mode a drag on empty space selects, a drag on an element moves it, and panning moves to a modifier, the middle button, the wheel and the overview. Every pointer gesture has a keyboard equivalent.

Moving an element on a diagram that has no layout takes the picture over, starting from exactly the picture shown, as one undoable step. A state indicator says whether a diagram is arranged automatically or by hand, and returning to the automatic arrangement is always one action.

An edit session collects every change on one undo history: arrangement, membership, groupings, and pending model changes such as a relation drawn on the canvas or an element created there. Saving writes them in one transaction, model changes before the diagram, so a refusal reaches the author before anything is written and a refused save writes nothing. This is the mechanism the amendment to [Diagram–Model Correspondence via Explicit Bindings](ADR@1783406738.Y7bzLM.diagram-model-correspondence-via-explicit-bindings-no-silent-model-mutation.md) states.

Dropping an element into a box nests it only where that is appropriate to the box: a grouping takes any element or grouping, a box whose membership is a rule takes only what the rule admits, and an element takes another element only for composition or aggregation. Where the model holds no such relation, the canvas proposes creating one as a pending model change; it never creates one silently.

An agent does the same through layout commands on the MCP surface, whose results equal the canvas's for the same command, in keeping with [Shared Semantics and Controls Across Human and Agent Interfaces](../../../projects/motivation-narrative/model/motivation/principle/PRI@1780220699.kWgVgr.shared-semantics-and-controls-across-human-and-agent-interfaces.md).

## Consequences

- The separate edit page for ArchiMate diagrams is replaced; its discovery sidebar becomes the edit mode's panel. Other diagram types keep their editors until they are moved over.
- The preview gate on saving goes: the canvas is the preview.
- Viewport behaviour (zoom, pan, overview, keyboard navigation) is built once and shared by every diagram viewer, laid out or not.
- An accidental takeover is guarded by a travel threshold, by being the first undo step, and by nothing persisting until the save.
- Not yet implemented.
