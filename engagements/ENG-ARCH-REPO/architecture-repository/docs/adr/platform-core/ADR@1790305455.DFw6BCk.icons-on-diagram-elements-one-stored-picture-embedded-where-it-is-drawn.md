## Context

The requirement [Custom Icons on Diagram Elements](../../../projects/motivation-narrative/model/motivation/requirement/REQ@1790305394.1bkWD0Y.custom-icons-on-diagram-elements.md) asks for product logos and pictures of an organisation's own on diagram elements. Until this decision an element showed only its type's glyph, and the [PlantUML Renderer](../../../projects/diagram-authoring/model/application/application-component/APP@1777293136.yaxrWl.plantuml-renderer.md) had just been restricted, for security, to images embedded as `data:` URIs: a diagram body may not read a file or fetch a URL.

Four facts shaped the answer. A repository is text in git, and every workflow — sync, promotion, proposals, rebase — carries text files and nothing else. A picture uploaded as SVG can carry scripts and external references. A logo is often wanted on every element of a type, and occasionally on one element only. And the enterprise repository may be reached by the same logo from several engagements.

## Decision

**A library icon is a text artifact, and its picture never changes under its id.** A [Library Icon](../../../projects/diagram-authoring/model/application/data-object/DOB@1790305394.OQBkE5f.library-icon.md) is a markdown file under `diagram-catalog/icons/`: its name, attribution, what it may be shown on, a default style, tags and status, then the stored PNG base64-encoded. A new version of a logo is a new icon, and replacing one re-points every diagram in one transaction. No git workflow gains a binary case, and no merge ever has two pictures to reconcile.

**Every upload is reduced to one stored form.** The [Icon Library](../../../projects/diagram-authoring/model/application/application-component/APP@1790305394.r5k14Kq.icon-library.md) decodes a raster within size limits, rebuilds an SVG from an allow-list of elements and attributes and rasterises it in a separate process with no file or network access, and stores a PNG at most 128 px high, 384 px wide and 32 KB. Every size the product draws an icon at is a box of a height and a maximum width, and the picture is fitted inside it keeping its shape, so a wide wordmark is drawn at the height of a square logo. What diagrams draw is always that PNG, so an icon looks the same everywhere and a hostile SVG never reaches the renderer. A picture the library already holds is not stored twice.

**A diagram states icons; the server decides which one shows.** A diagram's `diagram-entities` states an icon for one instance or for a type or specialization, and a repository may name a specialization's default. The most specific statement that resolves and applies wins, and an icon that stops applying is passed over rather than refused. The renderer, the verifier and the editor all read that one precedence; the editor asks the server rather than computing it.

**Every diagram body embeds the pictures it draws.** The body carries a generated block assigning each picture it uses to a variable named by the picture's digest, and each declaration refers to that variable. A body renders with nothing else present — in the enterprise before its library is synced, in an export, in any PlantUML — and the renderer's restriction to embedded images holds without an exception for icons.

**Two kinds of icon, one of them per diagram.** A picture one diagram needs is stored in that diagram's own file and travels with it through every workflow; it moves into the library when others need it. Promotion takes a diagram's library icons along, and names the enterprise's icon instead of copying one whose picture the enterprise already holds.

## Consequences

**The editor gains an icon per row without a separate mode.** The chip, the picker and the library page speak the same statements REST and MCP accept, and an agent can create a diagram with its icons in one call.

**An icon's size is the notation's, not the author's.** A badge stands in the label's line where the type glyph stood, so it takes that line's height; a figure is the element, so it takes a small element's height. A per-statement scale factor was considered and not adopted: a larger badge pushes the name out of its line and a smaller one is unreadable, sizes that differ on one diagram read as importance whether or not any is meant, and every statement would carry one more value through editing, restatement, promotion and proposals. What a scale factor would have been asked to repair — a wordmark shrinking to a strip — is answered by fitting each picture into its box. If emphasis is ever wanted, it is a choice among a few figure sizes, not a number.

**A diagram body grows by the pictures it draws** — up to about 33 KB for each distinct icon — and a hand edit to the embedded block lasts until the next write regenerates it.

**Two new dependencies ship with the product**, an image library and an SVG rasteriser, both under permissive licences.

**What is not covered.** Icons on connections, dark-theme variants, and assignment across several diagrams at once are not part of this decision. A specialization's default is set in `.arch-repo/specializations.yaml`, which the product reads and does not write.
