## Context

A [Viewpoint Definition](../../../projects/platform-core/model/application/data-object/DOB@1783870961.y7M3wz.viewpoint-definition.md) held stakeholders and concerns as free text, and a [Diagram](../../../projects/platform-core/model/business/business-object/BOB@1777230085.eGCeZq.diagram.md) held neither. The model already contains stakeholder and motivation elements, so the audience and question of a view were written as words that could not point at them, and nothing could answer which views address a given stakeholder or goal. A viewpoint also declares the representations it is meant for, and nothing noticed when it was applied to another.

Alternatives considered:

- **Prose only, on the diagram as on the viewpoint.** Readable, and unconnected to the model it describes.
- **References only.** Every audience would need a stakeholder element first, which over-models a one-off view.
- **One list shape for both, each entry prose or a reference, checked in one place** (chosen).

## Decision

A diagram and a viewpoint state who the view is for (`stakeholders`) and what it answers (`concerns`) in the same shape. Each entry is prose or a reference to an element. Which element types a reference may name is declared by the ontology in the [Architecture Ontology Configuration](../../../projects/platform-core/model/application/data-object/DOB@1777293139.UjyXG3.architecture-ontology-configuration.md): stakeholders for the first list, motivation elements for the second.

A diagram that applies a viewpoint inherits the viewpoint's lists, list by list, wherever it states none of its own.

Whether a reference resolves is decided by one check: the element exists and its type is admitted for the list that holds it. The [Model Verifier](../../../projects/platform-core/model/application/application-component/APP@1712870400.ca3vm7.model-verifier.md) applies it to a diagram, viewpoint authoring applies it before a definition is stored, and the [Promotion Engine](../../../projects/tiering-and-cross-tier-change/model/application/application-component/APP@1776633693.tIMxjr.promotion-engine.md) refuses a promotion that would leave a reference dangling. Each reports the fault in its own vocabulary; what counts as a fault is decided once.

A viewpoint applied to a diagram outside the representations it declares is a warning, not a refusal.

This realizes [Views State Their Stakeholders and Concerns](../../../projects/motivation-narrative/model/motivation/requirement/REQ@1795776616.Wl0K4oN.views-state-their-stakeholders-and-concerns.md), and extends [Viewpoint-Based Model Presentation](../../../projects/motivation-narrative/model/motivation/requirement/REQ@1783870981.mdH8Uv.viewpoint-based-model-presentation.md) from what a view selects to whom it is for.

## Consequences

- An element's page lists the views that address it, and the diagram list filters by stakeholder.
- A viewpoint written with plain-text lists reads as prose entries, so no stored viewpoint changes.
- A diagram reference that stops resolving is reported when the diagram is next verified; a viewpoint's references are checked when the definition is stored.
- Both lists stay optional; a diagram without them verifies as before.
