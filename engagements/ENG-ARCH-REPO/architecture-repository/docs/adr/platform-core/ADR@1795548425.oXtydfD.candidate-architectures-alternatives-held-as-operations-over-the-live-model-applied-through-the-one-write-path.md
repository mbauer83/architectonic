## Context

An architect weighing a change has had two places to put it. In the model, an alternative overwrites what is there, and only one alternative can exist at a time. In prose or a scratchpad, nothing about it can be checked against the model or applied to it. A [Proposed Change](../../../projects/tiering-and-cross-tier-change/model/business/business-object/BOB@1788599593.6x8cR_3.proposed-change.md) records one edit to enterprise content and is not a whole alternative. [Compare and Apply Alternative Architectures](../../../projects/motivation-narrative/model/motivation/requirement/REQ@1795548363.kNlXgAA.compare-and-apply-alternative-architectures.md) asks for alternatives that are named and argued, read against the model as it is now, and written into it as one verified change.

Alternatives considered:

- **A repository branch per alternative.** The whole model is copied, merging is textual, and the product reads one checkout.
- **Alternatives as model content from the start**, as plateaus and target copies of the elements they change. Relations are duplicated for as long as the alternative lives, and every reader of the model sees alternatives nobody has chosen.
- **Snapshots of the affected elements.** A snapshot goes stale as the model moves, and nothing tells a stale value from an intended one.
- **A candidate holding operations over the live model** (chosen).

## Decision

A [Candidate Architecture](../../../projects/platform-core/model/application/data-object/DOB@1795548363.1MP0Ygs.candidate-architecture.md) is a named, authored alternative change to the architecture. It carries a rationale, the end states it answers, the requirements it satisfies, and a place in the work: draft, candidate, integrated, rejected or superseded. Only a draft's operations may change. Integrated, rejected and superseded are terminal, and a rejected candidate is kept as a considered alternative.

A candidate holds a change set: operations that create, edit or remove an entity and add, edit or remove a connection, each with the base it was written against. It is the same operation value a diagram edit session and a proposed change use. A candidate may stack on a parent candidate, to any depth, and is read on top of it.

A candidate copies nothing from the model. Its scope names the model elements it is drawn over, it reads them live, and later changes to the model show through.

The standing of each operation is computed on every read and never stored. An operation applies, is already there, has drifted because what it would replace is neither its base nor its result, or conflicts because it has nothing to apply to or the verifier would refuse its result. Drift is decided by the same rule a proposed change is re-based by.

A candidate has one representation, its operation list, and one way into the model, the write path of [One Unified Backend Authority](ADR@1783406851.pGCuZn.one-unified-backend-authority-every-write-through-the-same-verified-pipeline.md). Applying it writes all its operations in one staged transaction through the [Staged Write Transaction Manager](../../../projects/platform-core/model/application/application-component/APP@1777399925.HOOYAQ.staged-write-transaction-manager.md), or none of them. A terminal candidate is not applied again, and a stacked one needs its parent integrated first. A conflicting operation refuses the application with its own reason. A drifted one requires a re-base, which writes it again against the model as it stands. An operation already there is skipped. The candidate is then marked integrated.

Candidates are a repository kind of their own, declared as [An Artifact Kind Is Declared Once](ADR@1795207261.tYY3QSb.an-artifact-kind-is-declared-once-and-consumers-ask-its-facts.md) requires. They are used from a page of their own and from stress analysis, over REST and MCP alike.

Further ways of working with candidates:

- **Comparing** several candidates against one common base, side by side.
- **Integrating** chosen candidates into a new candidate that holds their operations. Each conflict is resolved by taking a side, dropping an operation, taking a merged value where the parties agree on the field, or raising a decision; the chosen candidates stay as they were.
- **A derived target-state view**: the candidate drawn as it composes, computed on demand and stored only when the author saves it as a diagram.
- **Applying as a target state.** An added element is created as a draft, and a changed one as a "(target)" element of the same type with its relations and a trace relation to the original. A Baseline and a Target plateau hold them, with a «gap» assessment between the two, and the candidate's change set is kept. Moving the target into the baseline later is one generated operation list, checked, refused or re-based like any other.

## Consequences

- A considered alternative stays in the record whether it was integrated or rejected, toward [Considered Alternatives Survive Into the Record](../../../projects/motivation-narrative/model/motivation/outcome/OUT@1786223967.1mPt4f9.considered-alternatives-survive-into-the-record.md).
- A candidate written long ago reports which of its edits the model has overtaken, and applying it cannot overwrite them.
- What reads operations (standing, composition, overlap and ordering) takes the change set alone and needs no candidate name or state.
- Proposed change records never appear in the model, whichever way a candidate is applied.
- The candidate store lies outside the staged transaction, so a candidate is marked integrated by a save after the model write commits. If that save fails, applying again repairs it: every operation reads as already there, nothing is written, and the mark is saved.
- While a target state stands, the candidate is held: it cannot be applied directly, deleted or returned to draft until its target is moved into the baseline.
