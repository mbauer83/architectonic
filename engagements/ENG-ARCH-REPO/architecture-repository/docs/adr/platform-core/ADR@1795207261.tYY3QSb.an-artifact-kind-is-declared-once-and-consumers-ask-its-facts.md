## Context

A repository holds several kinds of artifact: entities, connections, diagrams, documents, icons and scratchpads. What follows from a file being of one kind was spelled at each place that needed it, as a branch on the kind's name: where its files live, what prefix its ids carry, whether the verifier takes it, whether a change to it changes what readers of the model see. Each branch was correct when written and had to be found again when a kind was added. Adding the icon kind left one consumer with no branch for it, and that consumer passed over icon files without anyone having decided it should.

A further kind is planned, and measuring what it would cost showed that most of the work was finding these places.

Alternatives considered:

- **Add each kind the way the last one was added.** The cost grows with every kind, and a missed place fails silently.
- **Let a deployment declare kinds of its own.** A kind carries a reader, a verifier and a page; these are code, and a declaration without them is a kind nothing can open.
- **One declaration per kind, held by the product, that every consumer asks** (chosen).

## Decision

Each artifact kind is declared once, as a row of facts, where the repository layout is defined. The path of a file decides its kind by walking these rows. A consumer that needs to know something about a kind asks the row for that fact and never compares the kind's name.

A row holds only facts something reads. A fact is added to the table with its first reader.

Kinds belong to the product. A deployment configures entity types, document types and diagram types within a kind; it does not add kinds.

The table is checked when the product starts, and a table that contradicts itself is refused: two kinds that could claim one file, a kind's own id prefix that a type also claims, or facts that cannot hold together.

Entities, connections, diagrams and documents keep their own index structures and readers. The table declares them; it does not replace them.

A kind may ship without a page of its own for one release, with the release that owes the page recorded on its row. A client older than a kind's stored format reads that kind and does not write it.

## Consequences

- Adding a kind is a row, plus the reader, verifier and page the row names. A place that would need a branch on the kind's name fails a fitness function instead of passing over the new kind.
- The places that still branch on a kind's name are held in a register that may only shrink, each with its reason and the change that removes it. Telling an entity file from a connection file inside a model root stays a comparison, since those two kinds share their roots.
- An id prefix is unique among kinds, and a kind's own prefix is unique against every type's. Prefixes of types in different kinds may coincide, as some diagram types and entity types already do.
- A batch write that touches a verified kind it keeps no staged records for is refused with the reason, where it used to pass over the file.
- Binding a kind's verifier and its page from the table, a generic index lane, and the facts those need are not yet implemented.
