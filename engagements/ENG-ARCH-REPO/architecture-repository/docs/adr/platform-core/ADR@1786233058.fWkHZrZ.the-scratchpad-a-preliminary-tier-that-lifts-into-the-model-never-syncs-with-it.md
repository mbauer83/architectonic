## Context

Everything this platform holds is already typed. `artifact_create_entity` demands an `artifact_type`
before it will accept a name; a connection is refused unless the ontology permits the triple; every
write is verified. That rigour is the product's value once you know what you are modelling, and a
wall in front of the moment when you do not.

The moment before knowing therefore happens elsewhere — a whiteboard, a notebook, someone's head —
and only the conclusion is transcribed into the repository. Two costs follow. Contribution is
confined to people fluent in a meta-ontology, which is a small fraction of those whose knowledge the
model needs. And the alternatives that were weighed, together with the reasoning that discriminated
between them, are discarded at the boundary, so nothing can later explain why a capability exists in
this shape rather than another.

## Decision

A **scratchpad** is a spatial collection of notes and links, held before its content is settled
enough to be typed, and progressively refined until some of it can become model content.

**It is its own artifact kind, not a document-type.** A document here is prose with prescribed
sections; a scratchpad is a graph with geometry. Filing one under documents would make
`/api/documents` return things no document consumer can render. The precedent followed is the
diagram: conventional identity and metadata, a body that is not markdown. One YAML document per
scratchpad, git-versioned and diffable like everything else.

**Content and layout are separated within the file.** Geometry changes on every drag; interleaving it
with titles and types would make a diff after an afternoon of tidying unreadable. Coordinates snap to
a grid and collections serialise in stable order, so a change of meaning and a change of position
appear in different places.

**The scratchpad is the aggregate root.** Notes, links, areas and groups have no life outside one,
which is what lets a note be created from nothing but a title — no global namespace has to accept it.
The root enforces the invariants, and the REST resource is the whole aggregate rather than its parts.

**Area membership is spatial.** Dragging a note into a frame *makes* it that area's; storing the
association separately would let the two disagree. A note inside no frame is legitimately unfiled.

**Refinement follows the meta-ontology's declared classification hierarchy**, not a fixed sequence of
steps — for ArchiMate 4, domain, then entity type, then specialization, a domain being a real first
narrowing because most areas permit several. See the requirement
[Declare a Meta-Ontology's Classification Levels in the Ontology Module](../../../projects/motivation-narrative/model/motivation/requirement/REQ@1786230066.vVjYCpP.declare-a-meta-ontology-s-classification-levels-in-the-ontology-module.md).

**Verification has two tiers**, and they are not the same event. A triple the ontology forbids is a
refusal that blocks (E126); a specialization's `restrict_relationships` narrowing is a warning that
does not (W128/W129). The principle
[Refusal Blocks; Narrowing Warns](../../../projects/motivation-narrative/model/motivation/principle/PRI@1786223967.IQqhM8k.refusal-blocks-narrowing-warns.md)
governs both this and the lift preflight.

**A note may be bound to model content that already exists**, not only lifted into new content. In a
repository that is not empty this is the commoner case, and without it lifting would mint duplicates.

**Lifting is a preflighted bulk transaction through the ordinary write path.** There is no second
route into the model. A second lift **skips** what is already realized and creates only what is new;
it never writes back. Bidirectional sync between a sketch and a governed model is not built, because
it would silently overwrite edits made in the model since the lift.

**Parity is required of the two principal surfaces.** Everything reachable in the GUI is reachable by
MCP, against the same aggregate and the same verification. This is stronger than the platform-wide
rule — the principle
[Shared Semantics and Controls Across Human and Agent Interfaces](../../../projects/motivation-narrative/model/motivation/principle/PRI@1780220699.kWgVgr.shared-semantics-and-controls-across-human-and-agent-interfaces.md)
disclaims full parity across every surface, and the CLI remains deliberately narrower. The scratchpad
has a local reason the platform as a whole does not: it is the lowest-barrier surface, so a
human-only version would make the one place newcomers start the one place agents cannot help.

## Consequences

The barrier to first contribution drops to writing a title, and what is written can become verified
model content without being re-entered. The reasoning around a decision survives beside it, because
lifting does not empty the scratchpad.

The model gains a way to be wrong safely, which is new. Nothing enters it unverified — lift runs the
same checks as any write — but a great deal may now sit *beside* it unverified and clearly marked as
such, and that material is a legitimate part of the record rather than a staging area to be emptied.

Costs accepted. A canvas produces events continuously against a repository that is a git working tree
behind a mutation gate, so the client batches and debounces and a save is one whole-aggregate write —
a discipline that must be asserted by a test rather than assumed. Alternatives multiply the state
space, so they arrive after typing and lift are solid. And a scratchpad's meta-ontology is frozen
while anything is typed; untyping, forgetting a realization and unbinding all remain available, so
the state is reachable rather than a trap.

Deliberately excluded: project delivery work — work packages, deliverables, plateaus and anything
finer — which belongs to a level below portfolio and outside this feature; scratchpad-level
alternatives, since one plan with a few contested decisions is the real shape rather than two
parallel plans; and alternatives that vary link topology, which would branch the graph.
