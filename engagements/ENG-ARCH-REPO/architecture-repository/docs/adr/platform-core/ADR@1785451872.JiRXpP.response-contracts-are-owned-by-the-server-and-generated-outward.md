## Context

Of 161 REST operations, 11 declared a real response shape. 69 declared an open object — a model with `extra="allow"`, which documents an object and promises nothing about its contents. Around 81 declared nothing at all, and most of the assurance surface returned a bare `JSONResponse` whose body no schema described. The generated OpenAPI document was therefore accurate about paths and close to silent about payloads.

The frontend compensated by hand-writing decoders. Those decoders were the only executable statement of what a response contains, which puts the contract on the wrong side of the boundary: a server free to change a field it never declared, and a client that discovers the change at runtime. Deriving the server's models from the frontend's decoders would formalise that inversion.

Error bodies were worse than undeclared — they were inconsistent. There are 114 `HTTPException(` uses in the backend, most raising a plain string (`HTTPException(404, f"Not found: {id!r}")`), so FastAPI returns `{"detail": "Not found: 'X'"}`. Alongside them, hand-built `JSONResponse` bodies used `{"error": ..., "reason_code": ...}` and `{"error": ..., "errors": [...]}`. A client cannot branch on a machine-readable code that only some responses carry.

Alternatives considered:

- **Generate the frontend's decoders from OpenAPI and delete the hand-written ones.** Rejected: the effect schemas carry runtime decode semantics — coercions, refinements, tagged unions — that generated types do not. Generation supplies types, not decoders.
- **Declare response models only where a client currently reads the body.** Rejected: that is how the present state arose. The undeclared operations are exactly the ones whose payload nobody can safely change.
- **One catch-all exception handler producing the typed envelope.** Rejected as insufficient: without a handler for FastAPI's own `HTTPException`, the 114 existing raises keep returning a plain string and the typed envelope is a fiction for most of the surface.
- **Server-owned DTOs, OpenAPI generated from them, and the frontend's decoders verified against the generated types** (chosen).

## Decision

**Ownership runs outward.** DTOs derive from application use-case outputs; the OpenAPI document is generated from the DTOs; the frontend's decoders are *verified* against the generated types. The decoders stay hand-written because they carry runtime semantics; generation supplies the oracle, not the decoder. The DTOs live under the existing delivery adapter rather than in a new top-level package, because they are the shape of this delivery mechanism and not a layer of their own.

**Every JSON body is runtime-validated, success and error alike.** An operation either names a DTO or declares itself explicitly bodyless, media or a stream — three named outcomes, not an absence. Where a raw response is unavoidable, the payload is validated before the response is constructed. `extra="allow"` survives only for a small, named set of genuinely dynamic maps.

**One error envelope, three handlers.** The envelope keeps FastAPI's `detail` key, so the outer shape and existing `HTTPException` handling survive, while the value becomes typed and uniform:

```json
{ "detail": { "code": "analysis_method_mismatch", "message": "…",
              "details": { } | null, "request_id": "…" } }
```

Three handlers are required, not one: `RequestValidationError` becomes `validation_error` with field errors under `details`; FastAPI and Starlette `HTTPException` are mapped into the envelope with their status preserved; an unhandled exception becomes a generic non-disclosing 500 whose text is never the exception's. A request-id middleware generates the id and emits it both in the envelope and as `X-Request-ID`. `details` is a closed DTO per error code — a discriminated union, never an open map, or the error path reintroduces exactly the arbitrary bodies this decision removes.

**Status and header conventions are part of the contract.** Creation returns 201 with `Location` and the created resource. A dry run of any kind returns 200 with its envelope, never 201 or 204. Deletion returns 204 with no body, except a dry-run deletion, which returns 200. An idempotent `PUT` that re-asserts an existing identical relation returns 204.

**Caching is two independent policies.** A response's `Cache-Control` directive and its eligibility for conditional reads are separate decisions, recorded separately. Setting them together would strip `no-store` from assurance responses precisely because those are deliberately ineligible for revalidation — and `no-store` is what keeps a confidential body out of a cache, while the *absence* of a validator is what keeps the existence of that body out of one. So: every assurance response carries `no-store`, success and error alike, including 404, 409, 422 and 423; model-derived cacheable reads carry their directive *and* an ETag; mutations and confidential responses never gain an ETag. A fitness test covers every declared assurance status, not only the success path.

**Contract verification is self-contained.** The frontend's contract check obtains the OpenAPI document in-process from the built application, generates TypeScript into a temporary location, compares that against the committed generated file, and runs type-level assertions that each hand-written schema matches its operation's response. The assertions must be type-level: generated TypeScript types do not exist at runtime and cannot be inspected structurally. The check requires no running backend and writes nothing into the working tree, because a gate that depends on a later gate cannot be run before a commit.

Operation ids are `{tag}_{verb}_{resource}`. Generation keys its output by operation id, so the id is part of the published contract and is stable across route renames. The document's version is read from package metadata rather than maintained as a second hard-coded value.

## Consequences

**Positive:**
- A response's shape is declared where it is produced, so a client can be generated or verified rather than guessed.
- An undeclared body becomes impossible to add: the operation has no third option between a DTO and an explicit non-JSON outcome.
- Every error carries a machine-readable code and a request id, so a client can branch on the cause and a user can quote something that appears in the log.
- Separating the cache directive from conditional-read eligibility makes the confidentiality contract explicit rather than incidental, and testable on error paths where it previously depended on each handler remembering.
- The frontend's decoders and the server's models cannot drift silently: the drift is a type error before it is a runtime one.
- The contract check runs before a commit, not only in CI, because it needs nothing but the source tree.

**Negative / risks:**
- Response bodies become closed where they were open. Any field a client relied on that was never declared has to be declared, and the migration surfaces that as a decode failure rather than a silent omission.
- A per-code `details` DTO is more work than an open map, and adding an error code means adding a type.
- Generated TypeScript is a committed artefact, so it can be stale; the contract check exists to make that a failure rather than a surprise.
- The typed envelope changes every error body in the product. Anything parsing `detail` as a string moves in the same release.
- The two-policy caching model asks contributors to make two decisions per read instead of one; the fitness tests over both are what keep the second from being forgotten.
