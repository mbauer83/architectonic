## Context

The same artifact was addressed two different ways inside a single router file: `GET /api/document?id=` against `PUT /api/document/{artifact_id}`. Across the surface the split was systematic rather than accidental — architecture reads were query-shaped, writes were RPC-shaped (`POST /api/entity/edit`, `POST /api/entity/remove`), and collections were spelled singular or plural depending on when they were written. The GUI mirrored it, so `/entity?id=` and `/documents/:id` coexisted in one navigation bar.

Inconsistent addressing is not only untidy. Four separate registries were keyed by the route path — the decorator, the mutation-authorization manifest, the `authorized_write` call inside each handler, and the conditional-read allowlist — and an equality test between any two of them passes while a third is stale. A stale authorization tuple fails the live write closed with nothing red in the suite, and an exact-string cache allowlist silently drops ETags when a path is renamed.

A second confusion sat underneath the first. This surface imports objects that arrive carrying identifiers defined by other standards — a PURL, a CPE, a BOM reference, a CVE or GHSA id — and it had begun treating those as though they were its own identities. `bundle_assembly.py` computed a `component_identity` as "whichever of `bom_ref`, `purl` or `name` is present", while snapshot persistence separately mints a segment-safe `SCM@…` id and stores `source_component_id`, `bom_ref` and `purl` beside it. One of those is the resource's identity; the other three are facts about it. Left unresolved, the question "what addresses this component?" has three answers, and whichever one happens to be reachable decides.

Alternatives considered:

- **Leave addressing as it is and document the exceptions.** Rejected: the documentation would have to be re-read by every contributor on every new route, and the four path-keyed registries would keep drifting because nothing derives one from another.
- **Normalise gradually, keeping old spellings as aliases or redirects.** Rejected: this product is local-first and was first released days before this decision, so the only migration obligation is persisted local data. An alias is a second spelling that consumers keep using, which means the migration never finishes and the registries stay ambiguous about which key is authoritative.
- **Make routes uniform by convention, enforced in review.** Rejected: a convention that is not executable is a convention that erodes. The specific failures above are all invisible to a reviewer reading one file.
- **Address resources by whichever identifier a caller happens to hold, percent-encoding it when its grammar does not fit a path segment.** Rejected: `%2F` is syntactically encodable but not reliably transportable — proxies and web frameworks differ on whether they decode it before route matching — so it cannot serve as one segment. Accepting external grammars into the path would also make every future feed's syntax a constraint on this system's routing.
- **State the addressing rule once, encode it in an executable manifest, and derive every path-keyed policy from it** (chosen).

## Decision

Identity of the resource addressed by an HTTP operation belongs in the path. Filters remain in the query. Command operands and alternate execution specifications may remain in the body. When the path supplies identity, the body must not repeat it.

Four cases distinguish the parts:

| Case | Test | Example |
|---|---|---|
| True identity | Removing the id leaves no resource | `/api/entities/{artifact_id}` |
| Anchor | Removing the id leaves nothing meaningful | `/api/entities/{artifact_id}/neighbors` |
| Filter | Removing it returns the whole collection | `/api/connections?entity_id=` |
| Operation | No stored thing is addressed | `POST /api/diagrams/{artifact_id}/sync` |

An identifier that selects one arm of a command-body union is not resource identity: `POST /api/viewpoints/execute` accepts either a saved slug or an inline query, and forcing that choice into the path would create two routes for one operation.

### Internal resource identity is not an external identifier

These are two different kinds of thing, and the rule above governs only the first.

An **internal resource id** is assigned by this system. It conforms to a single-segment grammar — no `/`, `?` or `#`, and no ambiguous encoded form — it is immutable, and it is validated at the boundary that assigns it, so an id that could not be addressed is never minted. Percent-encoding is not an escape hatch for a grammar violation: `%2F` may or may not survive to route matching depending on the proxy and framework in front of the application, so a slash cannot be smuggled through it.

An **external identifier** is defined by another standard or system: a PURL (`pkg:pypi/requests@2.31.0`, specified by purl-spec and standardised as ECMA-427), a CPE, a BOM reference, a CVE or GHSA id. Their syntax deliberately carries structure — `/`, `?` and `#` are meaningful inside a PURL — and this system's job is to validate and preserve them, not to prohibit or rewrite them. They are properties and alternate identifiers of a resource, never its address:

```
SecurityComponent
    component_id: SCM@4a89...                # this system's identity - one path segment
    purl:         pkg:pypi/requests@2.31.0   # external package identity
    bom_ref:      ...                        # source-system identity
```

Four rules follow:

1. Every independently addressable imported object receives an internal id, and canonical paths use it: `GET /api/assurance/security-components/{component_id}`.
2. An external identifier may appear in a **query** when it genuinely filters or resolves a collection: `GET /api/assurance/security-components?purl=...`.
3. An external identifier may appear in a **body** when it is the operand of an import, resolution or assessment command.
4. A singleton read keyed on `?purl=` is never retained on the grounds that the current "id" will not fit in a path. The resource is given an internal identity instead.

So the boundary of the addressing rule is not "identifiers containing a slash stay in the query". It is this: **external identifiers may contain characters outside the internal resource-id grammar; they are retained as data and may be used for filtering or resolution; every addressable resource receives a canonical, immutable, single-segment internal id.**

Two consequences of the internal grammar remain. Identifiers are percent-encoded per segment: `#` must be escaped, or a browser never sends the tail of a diagram-local id; `.` must not be, because ASGI decodes `%2E` back and the two spellings would be different keys for one identity.

### The manifest is the enforcement

The rule is enforced by a **route-policy manifest** — one row per canonical operation, carrying its method, route template, resource kind, identity parameters, operation id, mutation domain, cache directive, conditional-read eligibility, timeout class and response contract. Handlers name an operation id and the manifest supplies the method/template pair, so the path is written down once. The conditional-read middleware, the mutation-authorization gate, the cache-directive middleware and the frontend's timeout classification all read from it rather than restating it.

Because the manifest is a specification rather than a description, agreement with the served surface is proven, not assumed. Fitness functions compare it against oracles it does not produce: the generated OpenAPI document for the inventory, the mutation-authorization manifest for the write gate, the caching allowlist for ETag eligibility. Migration state is itself data — a ledger of retired addresses and of canonical operations not yet mounted — so the inventory check stays an *equality* at every point during the migration and the amount of work left is a fact in the source tree.

Emitted identifiers use the short, rename-stable form; the server also accepts the slugged form as an alternate spelling of the same identity. That is not an alias in the compatibility sense — both are current spellings of one id, and neither is deprecated.

## Consequences

**Positive:**
- One place states an operation's address, so a rename moves the decorator, the authorization key, the cache-eligibility template and the client and proxy timeout rule together.
- A route can be reasoned about from its URL: whether it addresses a resource, a collection or a command is visible without reading the handler.
- The path-keyed registries stop being independent copies, which removes the failure mode where two agree and a third is stale.
- Consumers can construct a detail URL from an id without knowing which query parameter a particular router happened to choose.
- The addressing rule is testable over the whole surface at once, so a new route inherits it rather than re-deriving it.
- External identifiers stay intact. A PURL is stored and matched as its standard defines it, and no feed's grammar becomes a constraint on this system's routing.
- "Which identifier addresses this?" has one answer per resource, so a correlation key used during import cannot quietly become the public address.

**Negative / risks:**
- The change is breaking, with no aliases and no redirects. Every consumer — the GUI, the CLI, examples and documentation — moves in the same release.
- The manifest is a second artefact to keep current. This is mitigated by making it the *source* the runtime reads, so an out-of-date row fails a request rather than only a test.
- Identity in mid-path means prefix-based routing rules can no longer express a policy: a dev proxy has to match route templates, since `/api/entities/{id}/neighbors` shares its prefix with an ordinary entity read.
- Percent-encoding rules are subtle and asymmetric between `#`, `.` and `/`; they are therefore implemented in one builder rather than at each call site.
- Imported objects need an internal id minted at import, which is a persistence obligation and a migration for anything already stored under a source-system key.
- A caller holding only a PURL needs two requests — resolve the collection, then address the resource — where a `?purl=` singleton read would have taken one. That cost buys an address that does not change when a feed's identifier scheme does.
