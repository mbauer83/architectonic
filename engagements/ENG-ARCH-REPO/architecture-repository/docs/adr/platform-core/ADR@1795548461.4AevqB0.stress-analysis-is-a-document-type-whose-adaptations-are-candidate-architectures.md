## Context

A stress analysis tests an architecture against what its environment may do to it. The architect lists stressors, the end states they lead to and the adaptations that would let the architecture survive them, then tests the adapted architecture against stressors held back from the design. [Stress an Architecture Against Its Environment](../../../projects/motivation-narrative/model/motivation/requirement/REQ@1795548363.8FZbiLJ.stress-an-architecture-against-its-environment.md) asks for this to be done against the model. Held in a spreadsheet beside the model, the components a stressor hits are names that drift, and an adaptation is prose nobody can read against the architecture or apply to it.

Alternatives considered:

- **A spreadsheet or free document beside the model.** Nothing in it is checked against the model, and an adaptation stays prose.
- **A store of its own, as the assurance analyses have.** A second store and verifier for content that is architectural and not confidential.
- **One decision covering both stress analysis and candidates.** A candidate is useful without any analysis, and an analysis is a method that may change without changing what a candidate is.
- **A document type with typed tables whose adaptations are candidate architectures** (chosen).

## Decision

A stress analysis is a document type with typed tables, verified like every typed table:

- **Stressors**, each drawn for the design or held back for the test, with the end state it leads to.
- **End states**, each with the requirement stating the required behaviour and the drivers, goals or stakeholders it affects, or the reason no change is needed.
- **Adaptations**, each naming the end states it answers, the [Candidate Architecture](../../../projects/platform-core/model/application/data-object/DOB@1795548363.1MP0Ygs.candidate-architecture.md) that holds it, and how far it has got toward integration.
- **Incidence**, which components each stressor hits.
- **Test set**, a verdict per held-back stressor and architecture: the naive architecture, the integration, or any candidate the architect chooses to evaluate. A verdict is survives, degrades or fails; a stressor judged unusable is struck with its reason.

The test set belongs to the same analysis, scope and naive architecture as the design set, and is kept apart from it: every design read leaves it out, and it has reads and actions of its own. It is filled by writing stressors into it or by holding out a random third of the design stressors, with the seed recorded. Nothing hides or seals it; the procedure of writing it apart, not adapting against it and judging at the end is stated where it is used and in the documentation.

The residuality of an architecture A is (Y − X) / n over the usable test stressors, where X counts the naive architecture's survivals and Y A's, a degradation counting half; the strict figure, full survivals only, is given beside it. It is computed on read, never stored, and given only once both are judged on every usable stressor.

A stressor is one line of free text; its kind is optional. Writing is supported by a shipped set of perspectives (PESTLE, Porter's five forces, the business model canvas, organisation and people), each with a guiding question, drawn from the system's environment and never from its elements.

Starting an analysis writes its naive architecture and the document naming it in one write, both or neither. The analysis evaluates its naive architecture, a candidate defined on its own canvas: the model elements it references and the operations it records (new elements, relations and changes), with a stored diagram or another candidate as an optional seed. Its scope is what it references; there is no separate scope. The canvas needs no stored diagram, and nothing reaches the model before the naive architecture is applied. It reads the model live as every candidate does. The analysis itself carries only an optional context, not a single question. Each adaptation is a candidate stacked on the naive architecture. Subjects and hit components resolve in the naive candidate.

Progress, incidence and coverage are derived on read from the tables and the naive candidate as it is now, and are never stored.

The analysis records which adaptation answers what and how far it has got. The candidate holds what the adaptation changes, and reaches the model only as [Candidate Architectures](ADR@1795548425.oXtydfD.candidate-architectures-alternatives-held-as-operations-over-the-live-model-applied-through-the-one-write-path.md) decides.

## Consequences

- An adaptation that was decided out stays in the analysis, and its candidate is kept.
- A change to the model after the start shows through the naive architecture, and the workspace says when the model has moved since it was read.
- A candidate an analysis starts from cannot be deleted while the analysis names it.
- The analysis gains what candidates gain. Comparing and integrating adaptations wait on the candidate decisions not yet built.
- The document type, the start in one write, the workspace on the candidate canvas, the derived progress, incidence and coverage, and the test set with its residuality are implemented.
