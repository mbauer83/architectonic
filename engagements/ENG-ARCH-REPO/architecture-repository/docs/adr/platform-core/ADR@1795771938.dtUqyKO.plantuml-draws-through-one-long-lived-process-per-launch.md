## Context

Every picture the [PlantUML Renderer](../../../projects/diagram-authoring/model/application/application-component/APP@1777293136.yaxrWl.plantuml-renderer.md) produced, and every [PlantUML Syntax Check](../../../projects/platform-core/model/common/function/FNC@1712870400.wIVwom.puml-syntax-check.md), started a Java virtual machine for the [PlantUML Engine](../../../projects/diagram-authoring/model/technology/system-software/SSW@1712870400.xVrBYD.plantuml-engine.md), drew one diagram and exited. Starting the machine cost most of each render: an SVG took about 0.8 s and a PNG about 1.5 s, of which the drawing itself was tens of milliseconds. A diagram save renders twice, and a canvas session renders on every change. Four modules spelled the command line, each with its own copy of the scratch-file and output-naming workarounds.

Alternatives considered:

- **PlantUML's HTTP server mode.** One process, per-request format, but it binds a TCP port, which collides between installations on one machine and widens the surface the sandbox has to hold.
- **Keep one process per render and cache harder.** The picture cache already serves repeated bodies; every new body still pays the start.
- **PlantUML's pipe mode, one process per launch** (chosen).

## Decision

One infrastructure module owns running PlantUML. It keeps one long-lived process per launch, where a launch is everything that decides the picture apart from the body: output format, resolution, size limit, and the PlantUML, Graphviz and Java executables. A body goes to the process on its standard input and the picture comes back on its standard output, followed by a random delimiter. Draws on one process are serialised, so outputs never interleave. The process binds no port and only its parent can reach it.

The sandbox is unchanged: headless, the SANDBOX security profile, the size limit, the directive policy applied before a body is handed over, and the Graphviz choice. Only a body with exactly one start/end block goes to the live process; anything else is drawn by a one-shot run, so a malformed body cannot spill into the next diagram's output. Preprocessor variables, definitions and skin parameters do not carry from one block to the next (checked on the pinned release).

The process starts on first use, is replaced if it dies, is killed when a render passes its deadline, stops after a period without renders, and is stopped by the backend's shutdown sequence. The syntax check draws through an application-layer port, so the application never holds a process.

## Consequences

- The pictures are byte-identical to the per-render ones for the committed diagrams. A warm SVG render takes about 23 ms (median) and a PNG about 85–220 ms, instead of about 0.8 s and 1.5 s.
- The backend holds up to three warm Java processes (SVG, PNG, syntax check), a few hundred megabytes each, until they have been idle for five minutes.
- Concurrent renders of the same format queue behind each other; a very large diagram delays other previews of that format for as long as it takes to draw.
- A fitness test refuses any other module that runs the PlantUML jar.
