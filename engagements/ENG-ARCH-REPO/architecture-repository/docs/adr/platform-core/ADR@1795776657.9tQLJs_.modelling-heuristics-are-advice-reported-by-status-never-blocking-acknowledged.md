## Context

The [Model Verifier](../../../projects/platform-core/model/application/application-component/APP@1712870400.ca3vm7.model-verifier.md) reported two kinds of finding. An error is a definitional fault and refuses the write; a warning is a claim that is wrong but not fatal. [Refusal Blocks; Narrowing Warns](../../../projects/motivation-narrative/model/motivation/principle/PRI@1786223967.IQqhM8k.refusal-blocks-narrowing-warns.md) keeps the two apart.

Some modelling guidance fits neither. A process that composes several steps nothing orders is often a function under the wrong type, and sometimes a deliberate checklist. Reporting it as a warning tells an author who chose it on purpose that the model is wrong, on every verification, with no way to say the choice was made. Leaving it unreported loses guidance the ontology already has the facts to give.

Alternatives considered:

- **Report heuristics as warnings.** They would sit beside real faults and train authors to read past warnings.
- **Keep heuristics in authoring guidance only.** An author who does not ask never hears it, and a reviewer cannot see which elements depart from it.
- **A third kind of finding, advice, acknowledged per element** (chosen).

## Decision

Advice is a third finding kind beside error and warning, with its own code range. It never refuses a write, a save or a promotion.

How advice is presented follows the element's status. On a draft element it is a marker on the element's page and a count in the verification summary, since a draft is expected to be incomplete. On an active element it is listed with its reason. The [Promotion Engine](../../../projects/tiering-and-cross-tier-change/model/application/application-component/APP@1776633693.tIMxjr.promotion-engine.md) lists it in the promotion dry run, so a reviewer sees what reaches the enterprise tier with advice outstanding.

An author acknowledges an advice on the element it concerns, with a reason, through the ordinary entity edit. The element stores the code and the reason, and the advice stays quiet at every status from then on. Only advice can be acknowledged; an error or a warning cannot.

An advice rule names no element type. It reads what the [Architecture Ontology Configuration](../../../projects/platform-core/model/application/data-object/DOB@1777293139.UjyXG3.architecture-ontology-configuration.md) declares about types and relationships, so another ontology gains the advice by declaring the same facts. The first rule reports an element whose type the ontology declares to be an ordered sequence, composing two or more parts that no path of dynamic relations orders. It reads three declarations: which types denote an ordered sequence, which relationships are exclusive containment, and which relationships are dynamic.

This realizes [Advise on Modelling Choices Without Blocking Them](../../../projects/motivation-narrative/model/motivation/requirement/REQ@1795776616.gmLsdPo.advise-on-modelling-choices-without-blocking-them.md).

## Consequences

- Warnings keep their meaning: something in the model is wrong.
- An acknowledged advice records why the model departs from the heuristic, on the element, where the next reader finds it.
- An advice rule is added by declaring the ontology facts it needs, without a change to the verifier for each ontology.
