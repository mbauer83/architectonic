## Context

Until this decision there was no update path. Releases were tags with no assets and no signature; the installation guide said to pull and rebuild, and the data upgrade — [Upgrade Repository Format](../../../projects/platform-core/model/common/process/PRC@1786821070.9ybAn48.upgrade-repository-format.md), run by the [Repository Upgrade Framework](../../../projects/platform-core/model/application/application-component/APP@1783872532.OZbaBh.repository-upgrade-framework.md) — was the operator's to remember. The requirement [Verified Software Update](../../../projects/motivation-narrative/model/motivation/requirement/REQ@1789640735.7Qke86l.verified-software-update.md) asks for one command that checks what is published, proves what it installs, and leaves a deployment consistent whether it succeeds or fails, for a local checkout and for a container deployment alike.

Four facts about the product shaped the answer. The installation *is* a git checkout with a locked dependency set, so "which version is installed" is a commit and "move to a release" is a fast-forward. The served GUI is built from the checkout, which needs Node on the installing machine unless the release carries the built bundle. The data upgrade's backend-not-serving guard probes the configured port on localhost, so it cannot see a backend serving the same volumes from another container. And the repositories a deployment holds may reach six-figure file counts, so any safety point taken as a file copy is too slow to be taken every time.

## Decision

**The checkout stays the installation, and an update is a fast-forward of it to a signed release tag.** A release is what the publisher's release record says it is — the [Release Manifest](../../../projects/platform-core/model/application/data-object/DOB@1789640747.7dTQJU9.release-manifest.md): version, tag, commit, assets and their digests. Three things are verified before anything changes, and each names what it proves: the tag's signature against the signers file the installed version carries, the release's commit against the tag fetched from the origin, and every downloaded asset against both the release's stated digest and the published checksum file. An installation that carries no signers file does not enforce signatures and says so; once it carries one, an unsigned or untrusted tag is refused.

**The release publishes the built GUI**, so an update needs no Node. The bundle is installed beside the served directory and swapped in; the previous one is kept until the update is verified.

**The next version's data upgrade is rehearsed before the live checkout moves.** A worktree at the release tag gets its own environment from the same lock, and that version's own `arch-repair upgrade` dry run inspects the deployment's repositories and operational targets while the current version keeps serving. Blocking findings, uninspectable targets and step errors are known before anyone is asked to stop anything, and the whole dry run — check, verify, rehearse, plan — writes nothing to the installation.

**A commit is a journaled sequence of phases, and the new version runs the second half.** The [Update Journal](../../../projects/platform-core/model/application/data-object/DOB@1789640751.6FYoz2f.update-journal.md) records the prior state, the target, the phase last completed and the phase begun. The installed version stops the backend, moves the checkout and syncs the environment, then re-executes itself from the moved checkout; the new version installs the GUI, reconciles pinned assets, migrates, starts the backend, authorizes the store where it was open and verifies the served version. Credentials the restart will need are asked for before the first phase that writes, and never on a dry run.

**The data upgrade takes the safety point, not the updater.** `arch-repair upgrade --commit` pins each repository's working tree under a git ref and copies each operational target before its first write, and gains `--restore`. The [Software Updater](../../../projects/platform-core/model/application/application-component/APP@1789640743.3hRHTJT.software-updater.md) records the set's id and restores it on rollback; it never writes to a model repository itself. Rollback restores data first, software second and the serving processes last, and reverses the phase that was begun as well as the phases that completed.

**Deployment kinds are observed, and each has one behaviour.** A local checkout is updated in place. A checkout whose compose project runs the app is a compose host: the image is built for the new checkout outside the downtime, the container is stopped *before* the migration because the guard is blind across containers, the migration and its restore run inside the new image against the mounted volumes, and the installed version's image is kept under its version so a rollback retags rather than rebuilds. A container without a checkout, a checkout attached to a remote backend, and a checkout that both serves locally and runs the container are refused with the instruction that resolves each.

## Consequences

**Updating is one command with the exit table operators already know**, and the process [Update Installed Software](../../../projects/platform-core/model/common/process/PRC@1789640738.siHhysu.update-installed-software.md) is distinct from the data upgrade it invokes. The first release that carries this decision is installed by hand; every later one by the command.

**Trust is anchored in the checkout.** The signers file ships with the software, so an adopter who installs from the repository inherits the publisher's key, and rotating it is a release. Provenance attestations are published with each release but not yet verified by the updater; that is a later release's work, named as such in the plan output.

**The rehearsal is default-on because it is cheap.** Measured on the development machine, the worktree, its environment and the dry run take about thirty seconds with a warm or a cold package cache. It can be skipped, and the plan then says the live migration is the first attempt.

**Four defects were found only by driving a second installation**, none of them reachable by the unit suite: a configured repository absent from disk crashed the credential probe; running a checkout's tools through the package manager re-locked the project after the version bump and dirtied the checkout; the update lock did not survive the handover because the tool is started as a child process; and the data upgrade's checkpoint failed on every enterprise repository from the template, because git refuses a plain exclude pathspec for a directory the repository itself ignores. The second installation and the two throwaway releases it updates between are the gate for any change to the phases.

**What is not covered.** MCP stdio bridges that agent clients started keep running the previous version until the client restarts them. A store under the manual activation policy whose key needs a master password from the environment is refused without a terminal, naming the variable. Downgrades remain unsupported.
