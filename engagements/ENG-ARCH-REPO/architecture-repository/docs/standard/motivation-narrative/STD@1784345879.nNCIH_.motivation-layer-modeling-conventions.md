## Scope

All motivation-domain content in this model (stakeholders, drivers, assessments, goals,
outcomes, principles, values, requirements) and the application-component traceability
convention the conformance views evaluate.

## Motivation

Reviews kept re-arguing the same semantics per edge: whether assessment mediation counts
as a driver-to-goal trace, when associations may become influences, how values differ from
goals, and what "traced" means for a component. Recording the conventions once makes
conformance mechanically checkable and keeps future passes from double-counting legitimate
mediation as gaps.

See requirement [Support Models, Diagrams, and Documents](../../../projects/motivation-narrative/model/motivation/requirement/REQ@1712870400.HR7AGz.support-models-diagrams-documents.md)

## Summary

Assessment mediation is an accepted driver-to-goal trace; direct driver→goal influence edges
are the exception and must state their causal claim. A **value** states undated, interest-relative
stakeholder worth; a **goal** states a desired enterprise condition — they are never duplicates.
Stakeholders link to drivers, goals, and values. Signed `influence` edges carry a
positive/negative `polarity` and a one-sentence causal description. Principles influence goals
(they do not realize them). Component conformance means a forward structural chain to a goal or
requirement.

## Specification

### Driver-to-goal tracing

`driver —influence→ assessment —influence/association→ goal` is the preferred, richer trace
because the assessment names the judged condition the goal responds to. Where the assessment's
effect on the goal has a defensible causal sign it is an `archimate-influence` with a
`polarity` (a threatening assessment negatively influences the goal it works against);
otherwise it stays an `archimate-association`. A direct `driver —influence→ goal` edge is
warranted only when (a) no assessment-mediated path exists AND (b) the causal claim is real;
such an edge must carry a one-sentence description.

Current dispositions (all six drivers have a retained trace path):

* Increasing Demand for More Autonomy of Teams & Systems — direct influence to five goals.
* Rising Software Complexity & Interdependence — direct influence to two goals.
* AI-Assisted and Agentic Development as a Dominant Production Mode — assessment-mediated (e.g.
  via "AI-Generated Change Volume Outpaces Architectural Planning and Review Capacity").
* Demand for Faster Product and Service Learning Cycles — assessment-mediated (positive
  influence into the agentic-velocity, change-volume, and centralized-governance assessments).
* Safety, Security & GRC Capability Gap for Small Teams — assessment-mediated (via "Assurance
  Cannot Keep Pace with Agentic Development Velocity" and "Assurance Disconnected From
  Architecture Loses Traceability").
* Expanding Software & AI Assurance Obligations — assessment-mediated (via "Assurance
  Disconnected From Architecture Loses Traceability" into "Provide First-Class Assurance
  Integrated with the Architecture Model").

### Values vs goals

A **value** (ArchiMate `value`, motivation aspect) expresses *standing, interest-relative worth*
to a beneficiary and has **no achievement date** — e.g. *Unity of Effort* is the worth, to
coordinating stakeholders, of autonomous contributors pursuing compatible intent. A **goal** is a
*desired enterprise condition* the architecture intends to bring about — e.g. *Sustain Unity of
Effort at Agentic Velocity*. Never model the same intent as both; if it can be achieved or measured
at a point in time it is an outcome, not a value. Value↔goal is not an allowed `association`, so
anchor them with `influence`: goal/outcome achievement → (+) → the worth it realizes; an enabling
value → (+) → the goal it enables. Value→value "constituted by" is expressed as positive influence
(the honest "contributes to" claim), not composition/aggregation. Name a value for the *raw worth*;
do not bake the resolution ("coherent", "within guardrails") into the label — let the connected
goals, outcomes, and principles carry it.

### Signed influence descriptions

An `archimate-influence` may carry a `polarity` of `positive` or `negative`; the renderer prepends a
green `+` / red `−` to the edge label. Every directional influence carries a one-sentence
description stating the causal claim and, where a horizon matters, the time frame — e.g. the
short-term-cost / long-term-benefit efficiency trade is one influence whose description reads
`(-) short-term | (+) medium- and long-term`.

### Principle-to-goal edges

In this repository profile a principle **influences** a goal; it does not `realize` it. Realization
is reserved for outcomes realizing goals (and requirements realizing outcomes or goals).

### Stakeholder legs

Every stakeholder should be associated with one or more drivers AND one or more goals, and with the
values it holds (stakeholder→value uses `archimate-association`). The stakeholder–driver hub uses
`archimate-association` for consistency; use influence only where a directional claim is stated in
the description.

### Retyping associations

An `archimate-association` may be retyped to `archimate-influence` ONLY where the connection's
description states a direction. Retyping is remove-and-recreate with the same endpoints (a
connection's type cannot be edited in place); the new description must preserve the original
provenance and, for a signed edge, set `polarity`.

### Component-conformance convention (shared with the traceability views)

An application component conforms iff a FORWARD structural chain
(composition/aggregation/assignment/realization, direct or derived up to 4 modeled hops) reaches a
goal or requirement — the same semantics the component-traceability-gaps viewpoint evaluates. A part
does NOT inherit the whole's trace (composition is not traversed against its direction), and serving
chains do not count as realization.
