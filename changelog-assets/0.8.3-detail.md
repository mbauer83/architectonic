Maintainer-facing mechanism for the summary in `CHANGELOG.md`.

## A lock the caller cannot wait for

`SnapshotConnection.open` and the VEX assessment store's `_conn` each ran one pragma script on every
connection open:

```
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
PRAGMA foreign_keys = ON;
```

The first of those three behaves unlike the other two. `journal_mode` is a property of the **database
file**, it persists once set, and changing it needs an exclusive lock. SQLite does not run the busy
handler for a journal-mode change: it returns SQLITE_BUSY immediately, however long the connection is
willing to wait. On sqlite 3.45.3, a second connection asking for WAL while a first holds a write
transaction fails in **0.000 s against a 10-second timeout**.

A process that opens a connection per thread could therefore fail with "database is locked" on the
open itself, and no timeout would have absorbed it.

## The split, and why a refusal is safe to ignore

The pragmas are separated by scope, and `apply_signals_pragmas` is the one place that applies them:

- `synchronous` and `foreign_keys` are per-connection and take no lock. They are applied first and
  unconditionally, so a store enforces its foreign keys whatever happens next.
- `journal_mode` is attempted, and a lock refusal is tolerated.

Two properties make tolerating that refusal correct rather than convenient:

- **Setting WAL on a file already in WAL succeeds in 0.000 s, even while another connection holds a
  write transaction** — SQLite short-circuits a no-op mode change. The exclusive lock is contended
  only on the first open of a new file, not on the ones after it.
- **A refusal on that attempt means another connection holds the lock**, and a connection holding the
  lock is one that is setting the very mode being asked for. The mode belongs to the file rather than
  to this connection, so there is nothing left for the caller to do.

Any failure that is not a lock refusal propagates, and has its own test. The narrowing is on the
exception message rather than its type: these stores are opened over SQLCipher in production and plain
sqlite3 elsewhere, and the two raise different `OperationalError` classes for one condition.

## What the tests now state

**A deterministic case for the open under contention.** Hold a write transaction, then configure a
second connection. No threads and no timeout: the file has to be left in its default journal mode,
because that is both the only moment the lock is contended and what a store nobody has configured yet
looks like.

**A case for the narrowing.** A connection whose pragma call raises something other than a lock
refusal must still surface it, or a corrupt store would hide behind a connection that looks
configured.

**The four-thread migration race keeps its shape, with two corrections.** Its pragma call ran outside
the `try` that reports errors, so a failure there escaped the thread — which `filterwarnings` makes an
error — and left the connection unclosed while it still held its lock. A failure also left the other
three threads waiting on a barrier participant that would never arrive, until the join timed out and
reported the wait rather than the cause. Every step is now inside the `try`, and a thread that fails
aborts the barrier.

## Not the artifact index

The artifact index also sets a journal mode and is unaffected: it is an in-memory shared-cache
database rather than a file, and its pragma script runs once on the single write connection rather
than on each pooled reader.
