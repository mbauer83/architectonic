# 0.9.0 — detail

Maintainer-facing mechanism for the summary in `CHANGELOG.md`.

---

## What a proposed change is

A deployment's engagement repository holds no enterprise content. It holds proxies — one per
promoted artifact — and those proxies are bookkeeping: they are never shown to a reader and never
edited. An edit to a promoted artifact therefore has nowhere local to land, and does not land
locally at all. It is recorded as its own artifact, of an internal kind, naming the proxy as its
subject and carrying the edit in the vocabulary of the artifact being changed, not of the proxy
standing in for it.

The edit is a closed union rather than a patch: each member names a kind of artifact and the fields
it may set. A recorded change therefore cannot express something the write path cannot replay, and
replay is not interpretation — it calls the same authorised writer an ordinary edit would, in the
enterprise repository, so a proposal cannot write what a direct edit could not.

`proposal-state` is `draft`, `submitted`, `integrated` or `abandoned`. The first two are pending;
the last two are terminal and are kept rather than deleted, because a change somebody reviewed
leaves a trace whatever became of it.

**Standing is derived, never stored.** Whether a change still applies to the baseline is a fact
about the proposal *and* the artifact it names, and the artifact moves without the proposal
changing. Storing it would mean a stored value that is wrong the moment upstream moves and right
again by accident. Every read derives it.

## A second edit to something already proposed

Editing an artifact that already carries a pending change is ordinary — the author has not finished
thinking — and what it does depends on where the first change is.

A draft is revised in place. A change already submitted is **superseded**: a new record is written
and the old one retired, in that order, so a crash between the two leaves two records rather than
none. Revising a submitted change in place would rewrite what a reviewer is reading, which is the
one thing the reviewer's copy must not do.

A second change writing a field another pending change already writes is refused when the pair is
composed for submission, not when it is written. Whichever replayed second would silently overwrite
the other, and ordering them is a guess about intent.

## Submission as a saga

Publishing is three steps that each survive a crash between them, because "push again and see" is
not available: a submission marks its changes submitted, so a retry has to know whether *this*
branch at *this* commit is what a reviewer is looking at.

1. **Prepare.** Record the intent — which changes, which branch, which commit is expected on the
   remote — and persist it before anything touches the network.
2. **Push**, unless the remote already carries the expected commit, which is what a retry finds.
3. **Resolve** by reading the ref back and comparing it against the expected commit.

Status is derived from the ref, never stamped from the fact that a push call returned; the two
differ exactly when it matters. A ref at an *unexpected* commit fails closed: the branch moved for a
reason this process did not cause, and treating that as a successful idempotent retry would mark
changes submitted against content nobody here produced.

## Upstream is the authority, and it is not this checkout

Whether a change has been taken up is asked of `origin/main`. The local enterprise checkout is the
wrong place to ask: it carries this deployment's own unmerged work, so asking it reports every
submission as integrated the moment it is committed locally — and the sweep that acts on that
answer then deletes the review branch out from under the reviewer.

Integration is decided by **content**, not by ancestry. A reviewer who applies a change by hand, or
squashes it, or rewords it, has taken it up; a check for the commit would say they had not. One
module owns "what upstream says", and it refuses to answer rather than falling back to the local
checkout when the remote cannot be read.

## Rebasing onto a moved head

A rebase is rehearsed in a throwaway `git worktree` rather than in the live checkout, and worktrees
an interrupted run left behind are pruned at startup. Each pending change is classified against the
moved head as still applying, already superseded by what upstream now says, or conflicting.

The branch is shared: it accumulates promotions as well as submitted changes. So a rebase replays
**the whole submitted set**, in the order the submission recorded, onto a replacement branch, and
refuses outright when the branch carries work the set does not account for. Replaying only the
changes would drop the promotions sharing the branch. The replacement branch is established before
the reviewed one is taken down, so a failure between them leaves the reviewer with a branch rather
than with nothing.

## One writer, one gate

Every repository mutation runs through a single-worker queue. A mutation authorises against a fresh
snapshot, submits once, re-checks inside the worker, and takes the write gate once. The value of
the re-check is that authority can change between deciding and doing; the value of the single
worker is that two mutations cannot interleave halfway through a multi-file write.

Settling a withdrawal was doing its work outside that queue on one path. It is inside now, which is
what makes "withdraw settles everything the branch was carrying, at once" true rather than usually
true.

## Two deployments, one remote

Two deployments propose changes to overlapping artifacts routinely. Working branch names carry a
per-deployment component, so two deployments cannot name the same branch and then fight over it.
Branch existence is matched exactly rather than by prefix — `arch/work-X` is not `arch/work-X-2`,
and a substring match there silently binds one deployment's operation to another's branch.

## Search by meaning

Retrieval is two branches fused by reciprocal rank, with a tie-break that claims only determinism.
Fusion is a step of discovery rather than a peer of either retriever: scaling one retriever's
scores into the other's range compares numbers that mean different things, while rank fusion
compares positions, which mean the same thing in both lists.

The embedding model is **static**. It encodes a query in 0.04 ms where the ONNX route takes
10.5 ms, builds the whole corpus in 0.04 s where that route takes 15.5 s, and costs 140 MB of
closure against 248 MB. At 0.04 s a query cache would save nothing, so there is none.

The weights are not a lock entry. They are acquired once as a content-addressed asset with a
committed digest, through the one module that owns fetching a pinned asset and proving it. A
deployment that has not acquired them answers exactly as it does with the setting off.

## Where an artifact is filed

Choosing a home on create and changing it on edit is one concern across three artifact families.
Two contract mixins carry it — `FiledOnCreate` and `Rehomeable`, inherited by every create and edit
body — with one self-defaulting control in the GUI, which takes its initial value from the
collection being browsed. A move heals the links into the moved artifact through the function that
already heals a link when any artifact moves, rather than a second reader matching directory
segments.

## A collection is more than its source directory

A diagram collection is backed by up to three directories: public sources, confidential sources,
and the rendered PNG and SVG, which are filed by the source's own collection segment. A rename moved
only the first: the sources took the new slug, the pictures kept the old one, and every PNG download
in
that collection answered `404 PNG not yet rendered — save the diagram first` for a diagram that was
saved. The SVG route re-derives on read and went on answering 200.

The answer to "which directories back this group" is given once and read by rename, by the
archive-emptiness check and by collection deletion, so deleting a collection now takes its rendered
output with it rather than orphaning it. `arch-repair upgrade` repairs repositories already in that
state, deriving where each picture belongs from where its source sits now rather than from a record
of the rename — so it repairs output stranded by a rename nobody wrote down, however many renames
ago it happened.

## Upgrading into this release

The enterprise sync aggregate's schema moved from 2 to 4 — a submission record, then a superseded
branch — and needs no migration: both fields read as "none in flight" when absent, which is what
was true of a file written before they existed.

No repository-side file exists per artifact kind, so the internal kind this release adds needs no
preparation either. A kind that later does need one is covered by the shipped-schemata step, which
probes every shipped entry rather than a listed few.
