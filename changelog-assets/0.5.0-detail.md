## Breaking changes

### `artifact_submit_for_review(dry_run=True)`

The tool now takes `dry_run`, defaulting to `true`. Previously it took no parameters and pushed the
enterprise working branch to `origin` on the first call.

| `dry_run` | Effect | Answer |
| --- | --- | --- |
| `true` (default) | Nothing is pushed | `{ok: true, dry_run: true, pushed: false, branch, message}` |
| `false` | Branch is pushed, state moves to `pending` | `{ok: true, dry_run: false, pushed: true, branch, message}` |

**Migration:** callers relying on the bare call to push must pass `dry_run=false`.

Both paths run the same preconditions — a branch exists (not detached HEAD) and the tree has no
uncommitted changes — from `enterprise_git_ops.submission_preflight`, which `push_enterprise_branch`
also calls. Refusal messages are identical between the two paths.

The already-submitted branch of the answer now carries `pushed: false` and `dry_run`, which it did not
report before. `pushed` and `dry_run` are the keys `artifact_save_changes` and the create/edit tools
already use.

### Diagram deselection

See [Diagram selection semantics](#diagram-selection-semantics). Affects every diagram view, not only
fullscreen.

## The `destination` contract

In 0.4.0 the `destination` enum was declared in the domain and re-declared in the scratchpad
contracts. A stored value absent from the second declaration failed to parse, and the whole
scratchpad became unreadable rather than the single field being rejected.

`destination` is now imported from `src/domain/scratchpad` by every contract that declares it —
request and response, REST and MCP.

There are two parse boundaries, with different behaviour:

| Boundary | Behaviour on an unrecognised value |
| --- | --- |
| `domain/scratchpad/parts.py::parse_destination` | Heals to `undecided` |
| `application/scratchpad/requests.py::from_request_document`, `ScratchpadEdit.validate` | Rejects |

The healing boundary serves the file reader, where rejection makes a stored document unreadable. The
rejecting boundaries serve clients, which can correct the input.

Rejection applies to the rows supplied by the caller, not to the merged document. A scratchpad that
already holds an unrecognised value remains editable.

## Request contracts

Typed contracts replace open maps for:

- the scratchpad delta body (`PATCH /api/scratchpads/{id}`)
- the scratchpad whole-document body (`PUT /api/scratchpads/{id}`)
- the MCP scratchpad write tools' parameters

Conventions these follow:

- Request contracts inherit `contracts.wire_shape.Closed`; they do not restate `extra="forbid"`.
  Enforced by `tests/architecture/test_closed_response_models_share_one_base.py`.
- Request models are separate from response models. A served note carries a derived `area` and a
  served link a derived `verdict`, neither of which a writer supplies.
  `test_wire_null_policy.py::test_no_marked_dto_is_also_a_request_body` rejects reuse of a
  `NullsOmitted` response DTO as a request body.
- MCP tool parameters are annotated as a model, not `Model | Mapping`. A union publishes
  `anyOf[model, object]` in the tool schema. Runtime coercion happens in `_shaped()` in
  `scratchpad_tools.py`, because FastMCP constructs the model on invocation while the write queue and
  tests call these functions directly.

## Analysis scoping on the assurance reads

Six read tools now accept `analysis_id`. Omitting it reads the whole store.

| Tool | Added in |
| --- | --- |
| `assurance_stpa_complete`, `assurance_cast_complete`, `assurance_grc_complete` | this cycle |
| `assurance_stats`, `assurance_coverage`, `assurance_risk_register` | this cycle |

Mechanics:

- `analysis_id` is forwarded to `store.list_nodes(analysis_id=…)`. The port declares the parameter and
  all four backends implement it.
- Edges are not filtered by `analysis_id`. The exposure filter retains only edges whose **both**
  endpoints are in the retained node set, so scoping the nodes scopes the edges. `list_edges` has no
  `analysis_id` parameter.
- The exposure-filtered node/edge view is `AssuranceContext.exposed_graph(analysis_id=…)`, previously
  assembled separately in each of the three aggregate reads. It returns a `NamedTuple` of `nodes` and
  `edges`.
- The withheld-node count is not reported by these three reads. Reporting it beside an aggregate
  discloses the size of what the classification ceiling withheld.

An unknown `analysis_id` yields an empty result, not the whole store.

## Tools with no parameters

Tools serving `{"type": "object", "properties": {}}`: 11 at the start of this cycle, 4 now.

Four are nullary by design:

| Tool | Reason |
| --- | --- |
| `assurance_store_status` | Reports the store's availability; there is no content to scope |
| `artifact_help` | The unfiltered catalogue, called before a caller knows a type name. Filtering is `artifact_authoring_guidance(filter=[...])` |
| `assurance_security_stats` | Its answer is the roster of entities carrying an active signal snapshot. Per-entity reads are `assurance_security_metrics(anchor_entity_id=…)` |
| `assurance_verify` | `verify_store` is defined over the whole store; checks such as edge-endpoint resolution are cross-analysis, so a scoped run reports an in-scope edge to an out-of-scope node as dangling |

`assurance_verify` has no `return_mode`. It would control output shape rather than scope.

`tests/tools/test_mcp_config_entrypoints.py` holds a register of these four in both directions: a tool
serving an empty schema without a register entry fails, and a register entry for a tool that now takes
parameters fails.

## MCP return types: current state

All 89 tools return `dict[str, object]`. 84 publish `outputSchema` as
`{"type": "object", "additionalProperties": true}`; 3 publish a `{"result": …}` wrapper (they return a
`list` or `dict | None`); 2 publish none (`artifact_help` and `artifact_authoring_guidance` register
with `structured_output=False`).

Typing them was planned for this release and deferred. Facts that informed the decision:

- The Anthropic Messages API tool definition carries `name`, `description` and `input_schema`, and has
  no output-schema field. `output_config.format` constrains the model's own response; `strict: true`
  validates tool input. An MCP `outputSchema` therefore reaches the client, not the model.
- Under MCP 2025-11-25 (the version the installed SDK speaks), servers **must** return structured
  results conforming to a declared `outputSchema` and clients **should** validate them. The Python SDK
  validates at `mcp/client/session.py:437`. An open schema cannot fail a client; an incorrect closed
  schema can.

Three measured FastMCP behaviours constrain any implementation:

| Annotation | Behaviour |
| --- | --- |
| Pydantic model or `TypedDict` | Undeclared keys are dropped from `structuredContent` and retained in the text block |
| Any model with optional fields | Unset optionals serialise as `null`; `convert_result` passes fixed dump arguments, so `response_model_exclude_none` has no equivalent here |
| Union (`A \| B`) | The answer is wrapped in `{"result": …}` |

A payload-only model also converts an in-band refusal into a protocol-level `isError`.

The design that satisfies all three — a `RootModel` union of payload and refusal, with a
null-omitting `model_serializer` on the model itself — is recorded outside the repository with its
measurements. Nothing for it was left in the tree.

## Diagram sidebar in fullscreen

Fullscreen is requested on the canvas element via the Fullscreen API. The browser renders nothing
outside that element, so a sidebar in the layout's third grid column was not visible.

`DiagramSidebarDock` (`tools/gui/src/ui/components/DiagramSidebarDock.vue`) relocates it:

- Outside fullscreen: the sidebar renders in place, unchanged. No wrapper element is added — the
  sidebar is `position: sticky` as a grid child, and a wrapper would take its place in the grid.
- In fullscreen: the sidebar is teleported into the fullscreen element and shown when something is
  selected. It is absolutely positioned at the right edge, `min(380px, 40vw)` wide, full height.

`Teleport` with `:disabled` is used rather than `v-if`/`v-else` over two positions, so the component
instance survives the move; a remount would re-run the sidebar's entity query and reset its scroll
position.

Presentation lives in `tools/gui/src/ui/styles/shared.css`, keyed on `.img-container:fullscreen >
.sidebar`. The transition animates `transform` and `opacity` over 0.22s.
`prefers-reduced-motion: reduce` removes the translation and keeps a 0.12s fade.

## Diagram selection semantics

| Gesture | Before | Now |
| --- | --- | --- |
| Click an unselected entity | Selects it | Selects it |
| Click the selected entity again | Clears the selection | No change |
| Click away from any entity, connection or sub-part | No effect | Clears the selection |
| Drag across an entity | Pans; no selection change | Pans; no selection change |

Applies to every diagram view. The background listener is attached to the SVG element and tests
`event.target.closest('[data-entity-id], [data-conn-id], [data-subpart]')` rather than relying on
handlers calling `stopPropagation`. Drag is unaffected because `usePanGesture` swallows the click
following a pan in the capture phase.

`useDiagramSvgSelection` gains `hasSelection` (an entity, connection or sub-part is selected) and
`clearSelection`.

## CI coverage gaps closed

- **Four diagram types were not exercised in CI.** Their suite was parametrized over capabilities
  absent from the CI environment, producing an empty parameter set and a passing run. The
  parametrization is removed; the suite asks the same questions in every environment. This was also
  the probable source of an intermittent xdist collection race (`Different tests were collected
  between gw<N> and gw<M>`) affecting those four types. Both full runs since have been clean.
- **A `src/domain/**` coverage floor.** `npm test` does not apply the per-directory thresholds in
  `vite.config.ts`; `npm run test:coverage` does. Six type-level `*.test-d.ts` files counted as
  0%-covered source and took the directory from ~90% to 71.9%.
- **An IPv4/IPv6 bind mismatch.**

## Test coverage of the MCP surface

MCP tools named literally in `tests/`: 69 → 86. The remaining 20 were reachable only through
loop-over-every-tool gates, which assert registration, safety hints and input-schema shape, not
answers.

New behavioural tests assert that filters select rather than merely being accepted — for example
`assurance_list_edges` is queried with a `source_id` that has no outgoing edge and a `target_id` that
has an incoming one, and the completeness profiles are queried with an `analysis_id` that does not
exist.

Tests reading the real repository assert invariants, not counts, lists or positions: the exported BOM
is well-formed CycloneDX 1.6 and its `component_count` equals its own component list length;
`artifact_aibom_coverage` and `artifact_aibom_export` report the same component set; every datatype
classifier carries a non-empty `type_id` and `label`.

**Defect found and fixed:** `assurance_scan_ai_candidates` documents its input as the output of the
arch-repo-read list/query tools, which serve `artifact_id`, `artifact_type` and `summary`. The scanner
read `entity_id`/`id`, `entity_type`/`type` and `description`/`content` only, so such input produced
candidates with an empty `entity_id` and no type bonus. The scanner now reads both vocabularies.

Three tools still have no test naming them, each requiring more fixture than the store alone:
`assurance_cast_complete` (needs the archive), `assurance_list_bom_components` and
`assurance_list_vulnerabilities` (need a signal snapshot).
