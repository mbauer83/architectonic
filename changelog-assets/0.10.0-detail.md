# 0.10.0 — detail

Maintainer-facing mechanism for the summary in `CHANGELOG.md`.

## The update is a journaled sequence of phases, and the new version runs the second half

`arch-update` is composed in layers. The pure part — `src/application/software_update/` — holds the
release and version types, the installation observation vocabulary, the planner (`plan_update`, a
decision table whose every refusal carries its remedy and its outcome), the journal state machine
(`UpdateJournal`: a closed phase literal, `begin`/`advance`, validation on load), the phase runner
(`run_phases`) and the reversal (`roll_back`). Adapters live in `src/infrastructure/software_update/`:
the GitHub Releases reader, the git checkout (observe, fetch a tag, `verify-tag` against the signers
file, fast-forward, `reset --keep` back), the `uv` environment (a selection of groups and extras
derived from what is installed, so the next sync reproduces it), the rehearsal worktree, the GUI
bundle swap, the journal store with its lock, the credential prompts, and one `UpdateActions`
implementation per deployment kind — `LocalCheckoutActions` and `ComposeActions`.

Two boundaries decide the shape. **The re-exec.** The installed version cannot import the new
version's migration or start its backend, so after `environment_synced` the process executes the
recorded resume command and the new version continues from the journal. The command is
`uv run --frozen --no-sync --project <checkout> arch-update --resume`: without those flags `uv run`
re-locks a project whose `pyproject.toml` version changed and re-syncs the default groups, which
dirtied the checkout and would have dropped the derived selection. The lock is released before the
exec rather than carried by pid, because `uv run` starts the tool as a child; the in-flight journal
is what keeps a second `--commit` out. **The safety point.** `arch-repair upgrade --commit` takes it
(`take_checkpoint_set`) after its gate and before its first write, as a pinned ref per repository
and a copy per operational target, and reports the set's id; the updater records the id and calls
`--restore` on rollback. The set is taken whole or not at all — a failure on the second repository
releases what the first pinned — and a checkpoint that cannot be taken is exit 21.

The rollback order is fixed by dependency: stop the backend the update started, restore the
checkpoint set while the new software can still read its own report, restore the GUI, return the
checkout and sync the environment to it, re-provision the previous pins, start the previous backend,
re-authorize the store. Every reversal runs even when an earlier one failed, and what remains is
reported line by line as `partial` (exit 20).

## The rehearsal reads the next version's report, and refuses one it cannot read

`rehearsal.rehearse` creates a detached worktree at the release tag (`rehearsal_worktree`, removed
however the block exits), syncs it with the derived selection, and runs that version's `arch-repair
upgrade --json` with the same `--workspace` and `--settings` the live command receives. The report
is summarised into a `RehearsalVerdict` — blocking findings (`blocks_commit`, new in report schema
2), uninspectable targets, step errors — and a report schema this version does not know is refused
rather than half-read. Measured on the development machine with the full dependency selection:
about thirty seconds, warm or cold cache, which is why it is on by default and `--no-rehearse` is
the opt-out.

## The staging rule and git's treatment of an ignored exclude

`STAGE_ALL_BUT_RUNTIME_STATE` was `add -A -- . ':(exclude).arch'`. When `.arch/` exists and the
repository's own `.gitignore` lists it — the enterprise template does — git 2.39 counts the exclude
item as a path named on the command line that is ignored, and refuses the whole `add`. The rule is
now `':(exclude,glob)**/.arch/**'`, which is not a named path and holds in both configurations; a
round-trip test stages a dirty tree with an ignored and with a merely untracked `.arch/`.
