## Malformed `local:` in `arch-workspace.yaml`

`configured_repo_path` passed `spec["local"]` to `Path()`. A non-string raised an unhandled `TypeError`
at startup.

| `local:` value | Before | Now |
| --- | --- | --- |
| `repos/engagement` | resolved | resolved |
| absent key (bare `local:`) | `TypeError` traceback | `ERROR: engagement.local must be a non-empty string` |
| a list or mapping | `TypeError` traceback | same refusal |
| `""` or whitespace | resolved to the **workspace root** | same refusal |

The guard is in `_validate_repo_spec` (`src/config/workspace_paths.py`), the single point every path into
that module already passes through, alongside the existing rule that `git` must be a mapping.
`configured_repo_path` states the precondition in its docstring rather than re-checking it.

The blank string is refused for the opposite reason to the type error: `Path("")` is `.`, so an empty
`local:` silently treated the entire workspace as the repository.

## `assessed_entity_id` reported two values

`assurance_list_vulnerabilities` and the REST signal reads.

| Call | Before | Now |
| --- | --- | --- |
| scoped (`assessed_entity_id=APC@….payments-api`) | echoed the caller's argument | the stored id |
| unscoped (all assessed entities) | the stored canonical id | the stored id |

The store canonicalises an entity id to `PREFIX@epoch.random`, so a caller passing the slugged form got
it back unchanged from one read and canonicalised from the other. Joining the two result sets on
`assessed_entity_id` matched nothing.

## Render scratch files after a hard kill

The renderer writes its PlantUML input into the diagram catalog — PlantUML resolves the injected
`!include`s against the including file's directory — and unlinks it in a `finally`. That covers returning
and raising, not SIGKILL or an OOM kill.

Each render now discards `tmp*.puml` older than **300 s** in that directory before writing its own. The
bound is five times the 60 s subprocess timeout, so a concurrent render is never swept out from under
itself; the pool is bounded but not serial. The sweep is best-effort — a file that has vanished or that
the process may not remove is skipped rather than failing the render.

Placed ahead of every early return, so a machine rendering native SVG or lacking the PlantUML jar still
clears what it accumulated when it had one.

`tests/rendering/test_no_render_temp_file_is_committed.py` still guards the *commit*, and now derives its
name pattern from the renderer instead of restating it.

## One YAML loader

`src/domain/yaml_documents.py`. 77 call sites across 63 files said `yaml.safe_load`, the pure-Python
loader, on installs shipping a C loader with identical semantics.

| Measurement | Pure Python | libyaml |
| --- | --- | --- |
| 1,514 stored documents, 470 KB (median of 5 interleaved runs) | 377 ms | 40 ms |
| full verification pass, 965 files, PlantUML syntax skipped | 516 ms | 189 ms |

Equivalence, measured rather than assumed:

- 0 of 1,514 stored documents parse to a different value under the two loaders.
- Both raise `yaml.YAMLError` subclasses, the contract ~15 call sites catch.
- All 43 committed diagrams render to byte-identical SVG.

In `src/domain/` because the dependency policy lets `domain` import only `domain`, and domain modules
parse YAML — anywhere else could not be the single owner. Falls back to `SafeLoader` where PyYAML was
built without libyaml, so such an install keeps exactly the previous behaviour. `USES_LIBYAML` reports
which was chosen; nothing about a parsed value reveals it.

`parse_yaml` returns `Any`, as `safe_load` did: a YAML document is legitimately a mapping, sequence,
scalar or null, and every call site already narrows what it expects.

**Not changed:** serialisation. `yaml.safe_dump` has an equivalent C dumper, but no profile blames it.

`tests/architecture/test_yaml_parsing_has_one_owner.py` fails if anything outside the owner names a
PyYAML load function or loader class.

## One frontmatter definition

`src/domain/repository/frontmatter.py`, replacing fourteen readings in five families:

| Reading | Sites | Behaviour |
| --- | --- | --- |
| `^---\n(.*?\n)---\n` | 4 | closing fence must be followed by a newline |
| `^---\n(.*?)^---\n` (MULTILINE) | 1 | closing fence anywhere at a line start |
| `^---\n(.*?)\n---\s*\n?` | 1 | trailing whitespace tolerated, final newline optional |
| `startswith("---")` + `find("\n---", 3)` | 2 | accepts `----` and `---anything`; matches `\n----` |
| `\A---[ \t]*\r?\n…` | 1 | CRLF, trailing whitespace on both fences, may end at EOF |

Plus five `startswith("---")` guards and one `find("\n---\n", 4)`.

The two loosest were the **verifier** and the **document write path**, so a file could be verified under
one delimitation and rewritten under another.

The surviving reading is the last row — `rendering/puml_safety`'s, already a superset of the other four.
Nothing was invented.

| Input | Old strict readings | Now |
| --- | --- | --- |
| block ending at EOF, no trailing newline | no frontmatter | read |
| trailing space on either fence | no frontmatter | read |
| CRLF line endings | not read by most | read |
| `----` as an opening fence | accepted by the loose readings | refused |
| `---anything` as an opening fence | accepted by the loose readings | refused |
| closing fence with trailing text (`---more`) | truncated the block | not a closing fence |

Measured across 975 files in both repositories: the five old readings disagree on **zero**, and all agree
with the new one. All 43 committed diagrams render byte-identically.

The API, and why it is more than one function:

| Function | For |
| --- | --- |
| `read_frontmatter` | the block, or **which** fence is missing |
| `parse_frontmatter` | the mapping; `{}` when absent, unterminated, empty or not a mapping |
| `body_after_frontmatter` | the document with the block stripped |
| `replace_frontmatter_text` | rewriting the YAML, both fences left as authored |
| `opens_with_frontmatter` | the cheap guard, requiring the fence to be a fence |

`read_frontmatter` returns three things rather than two because the verifier reports a missing opening
fence (**E011**) and an unclosed block (**E012**) as different mistakes; `None` for both would have cost a
diagnostic. Its two codes are now a table rather than two branches.

Two regressions found by the suite during the migration, both now pinned:

- `---\n---\n`, a zero-length block, was read as unterminated. The content group is optional.
- `application/artifacts/parsing.extract_yaml_block` must answer `None` for "no readable block" and `{}`
  for "present but empty" — the unrecognized-structure upgrade step branches on exactly that.
  `parse_frontmatter` answers `{}` for both, so that caller reads `read_frontmatter` directly.

`tests/architecture/test_frontmatter_has_one_definition.py` inspects the **call**, not the literal. An
earlier version scanned every string for three dashes and reported seventeen false positives: markdown
table separators, the `source---target@@type` connection-id separator, an error message quoting the fence
in prose, and the three writers that legitimately compose frontmatter.

## The worker default's justification

`_DEFAULT_PASS_WORKERS` stays 1. The comment above it cited a measured 73 s pass at one worker, 4.4× the
CPU at four, and a profile pointing at 200,574 YAML documents and 982,904 `realpath` calls. Re-measured
over 965 files, same settings:

| | Recorded | Now |
| --- | --- | --- |
| YAML documents per pass | 200,574 (~228/file) | 1,472 (~1.5/file) |
| `realpath` calls | 982,904 | 3,392 |
| `lstat` calls | 7,653,729 | 30,656 |
| full pass, PlantUML skipped | ~63 s | 0.19 s |

Single acquisition (`acquire_snapshot`) had already removed the re-reading; this release's loader moved
the remainder onto libyaml. The table is kept as historical, because it is what the default was chosen
from, and the default's reason is restated: there is no longer a pass worth splitting. `ARCH_VERIFY_WORKERS`
still overrides it.
