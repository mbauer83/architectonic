## The label an element carries on one diagram belongs to that diagram

An ArchiMate element's box carried whatever its record said — the display block's `label`, else the
name — on every diagram, and nothing but the element could change it. `diagram-entities.display_labels`
is the diagram's own statement: a mapping from instance id to label, where a instance id is the entity's
artifact id for its base instance and the occurrence id for a further one, the same identity an
authored grouping's members and the editor's rows already use.

The statement reaches the picture by whichever route the body is written:

- a **rendered** body has the renderer emit it — `entity_label_and_stereotype` takes the instance's
  label ahead of the element's, and the join from instance id to alias is made once, in
  `archimate_occurrences.instance_labels_by_alias`, for base instances and occurrences alike;
- a **kept** body — hand-laid, or supplied by the caller — has the declaration relabelled in place by
  `relabelled_declaration`, which lives in `puml_alias_declarations` beside the reading lens's
  `restyled_declaration` for the reason that module exists: one owner of what declares an alias. The
  sprite, a specialization's guillemet line and a lens's appended block are kept; only the name moves.

Its reading twin, `label_declared_on`, is what the diagram context read reports as `drawn_labels`:
what the body calls each instance as it stands. That read is what lets the editor show a hand-laid
label the element's record does not know about, and carry it into `display_labels` before a save
regenerates the body — without it, the first save from the editor reverted such a label to the name.

The label is spelled through `quoted_label_text`: one line, quotes folded to apostrophes, because it
sits inside a quoted PlantUML string. `test_a_relabelled_declaration_still_declares_its_alias` asserts
the write-then-read pair over every declaration form the owner names and over labels carrying quotes,
newlines, the word `as`, a colour-looking `#` and guillemets.

## The editor's entity panel and the groupings beneath it

The edit view placed its sidebar with an explicit row span and left the column to auto-placement.
The sidebar was the only item with a definite row, so the grid placed it first — in the **left**
column — and the groupings editor was then auto-placed directly beneath it in the same column. The
sidebar is sticky, and a sticky item slides within its grid container rather than its grid area, so
on scroll it moved down over the groupings until it covered them.

The view now uses the split layout every diagram detail surface uses: canvas, home selector and
groupings in the left column, the sidebar alone in the right one, with the draggable divider that
layout provides. Nothing sits beneath the sidebar in its column, so there is nothing for it to
cover. A browser test scrolls the page to the bottom and asserts the two boxes do not intersect.
