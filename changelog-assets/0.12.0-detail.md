# 0.12.0 — detail

Diagrams edited on their canvas, candidate architectures, stress analysis with a test set, and the install,
update and security work that goes with serving them.

## Editing on the canvas

ArchiMate views whose diagram type declares `arranges_on_canvas` open in an edit mode on the diagram page. The
session holds three kinds of change: placement (elements, boxes, line courses, label positions, stacking),
composition (what the diagram draws: elements, further occurrences, relations, boxes) and model commands
(create, rename, edit, delete an element or relation). Save writes them in one transaction, model changes first;
**Save will write** lists the model changes and a single **Layout changed** row. Undo steps through every change
and names it.

Arranging snaps to an 8 px grid and to neighbours' edges and centres within 6 px, with dashed guides. Taking an
automatic picture over keeps PlantUML's lines; a line is routed again only when an end moved, the side of a box
it ends at moved, or something moved across it (`routing/kept`, held equal between TypeScript and Python by the
shared fixtures). During a drag a moved shape's lines follow it; the drop routes only lines that then break a
hard rule. A save states every line the editor routed again, so the server routes none on a save. Pictures
PlantUML has drawn are kept in a bounded store (`application/plantuml_pictures.py`) keyed by source and toolchain,
so one save no longer draws the same body three or four times.

A diagram whose PlantUML body was written by hand — `manual-layout`, or a body that draws boxes, elements,
relations or a direction its generated picture would not (`application/modeling/hand_drawn_constructs.py`) — is
protected: a replacement that would regenerate its body is refused with `400` naming, by label and name, what
would be lost, unless the request states `manual_layout: false`. The diagram read carries `written_by_hand` and
`hand_drawn`; edit mode says arranging is saved and changing what is drawn is not. **Lay out automatically…**
shows the generated picture beside the hand-drawn one and gives the body up on confirmation.

The whole-diagram replacement takes an optional `base_revision` (`application/modeling/diagram_revision.py`, over
what the diagram draws, its other statements and its body; the layout block is guarded per entry by
`based_on`). A stale replacement is refused with `409` naming the part that changed.

Reading: focus an element and choose how many steps of incoming and outgoing relations to show; the rest fades.
A diagram too large to read whole opens at 60 % on its top-left box with an overview, and box names are drawn at
screen size while the picture's own text is unreadable. Every viewer offers full screen; the stress workspace
docks the focused stressor or the judging walk beside it.

## Candidate architectures

A candidate is an ordered list of operations over the live model (create, edit, rename, delete an entity;
add, edit, remove a relation), stored as `candidate-architectures/*.candidate.yaml` and read live: each operation's standing
(`applies`, `already there`, `drifted`, `conflicts`) is computed on every read. Candidates stack; a stacked
candidate names an element its parent creates by that element's artifact id. A candidate is sketched on its own
canvas, which needs no stored diagram: its picture starts from the diagram its stack is drawn on, else a view
generated from what it references, else an empty picture.

Comparing lists the operations of several candidates against one base with a word-level diff of changed text.
Integrating builds a new candidate from chosen ones; each conflict is settled by taking a side, dropping an
operation, a merged value where the parties set the same field, or raising a draft decision record. Applying
writes every operation in one staged transaction. Applying as a target state writes added elements as drafts and
changed ones as "(target)" copies with their relations and an association to the original, under a Baseline and
a Target plateau with a gap between them (relation types declared by the ArchiMate module); moving the target
into the baseline, or withdrawing it, is a generated operation list with a dry run. Reject keeps a candidate as a
considered alternative; delete removes it.

REST: `/api/candidates/…`, `/api/candidate-checks`, `/api/candidate-integrations`, operation ids `candidates_*`.
MCP: `candidate_*` tools. A candidate's optional `description` (at most 300 characters) states its core idea.

## Stress analysis

A document type (`stress-analysis`) with tables for stressors, incidence, end states, adaptations and the test
set. Starting one writes its naive candidate and the document in one write and opens the naive architecture on
its canvas. Stressors are one line of free text with an optional kind; the shipped perspectives (PESTLE, Porter's
five forces, the business model canvas, organisation and people) prompt writing them and can be extended per
repository in `.arch-repo/stress-perspectives.json`. Adaptations are candidates stacked on the naive one.

The test set is a separate table of the same analysis, never read by the design views. **Hold out a random
third** moves a seeded draw of design stressors into it; repeating the same draw writes nothing. Verdicts are
survives, degrades or fails; residuality is (Y−X)/n with a degrade counted as a half, beside the strict figure.
Candidate columns are typed `id` cells (`kind: candidate-architecture`): a short id is stored in its full form
and an unknown candidate is refused (E164). The analysis reads are served under `/api/stress-analyses/{id}/…`;
residuality per candidate is MCP `analysis_residuality`.

## Install, update and repair

* `fastapi` and `uvicorn` are core dependencies, so `uv sync` runs the backend.
* `arch-update` keeps edits to `arch-workspace.yaml` and `config/settings.yaml` across an update and merges
  them onto a release's version; the dry run refuses a conflicting edit, a `skip-worktree`/`assume-unchanged`
  flag and a diverged `main`, each with its remedy. 0.11.x installations follow the documented procedure.
* A checkpoint set records the settings document it was taken under; restore reaches every target it recorded,
  names the databases it puts back whole, and refuses to discard work written after the upgrade unless told.
  The per-user guidance cache is no longer checkpointed.
* Format contract 7: `d13-entity-ids-used-names-elements`, `d14-drawn-relations-bound` (binding through the
  verifier's own reading in `verification/drawn_relations.py`), `d15-outgoing-source-entity-long-form`.
  `default-document-types-ensure` adds every shipped document type a repository lacks, never overwriting.
* A GUI built after the backend started is served without a restart; a new repository commits its generated
  includes; a backend started from a git worktree serves that worktree.
* The backend reads every push URL of a remote; a push that needs a credential answers `git_credentials_required`
  and the GUI asks for it (`PUT /api/sync/credentials`, local operator only, held in memory). Submit links to the
  platform's new-pull-request page. The MCP bridge exits when its session ends after a backend restart.
* Releases publish only after `ci.yml` passes on the tagged commit.

## Security

`arch-backend` binds only the loopback unless `--allow-remote-without-auth` or
`backend.allow_remote_without_auth` is set. A host guard admits loopback names and `ARCH_ALLOWED_HOSTS` (`421`
otherwise) on the GUI, REST and MCP. Routes declare a `gate` on their policy row; `local_operator` (loopback and
the `X-Arch-Operator-Request` header) covers assurance reload and supplying a git credential. Client-named
locations are confined to the configured repositories by `application/repository_confinement.py` for reads and
writes alike, with an architecture test that every location parameter goes through it. Responses carry a
content security policy and `nosniff`, `X-Frame-Options: DENY` and `Referrer-Policy: same-origin`; every
`v-html` sink is registered with its sanitiser. TLP ranking has one reader, and an unknown level ranks as RED.

## Operations and permissions

`application/operation_catalog.py` names every canvas, candidate, stress-analysis and artifact write as one
operation with the REST operation and MCP tool that carry it. The sync status answers `denied_operations`, and
the GUI offers or refuses every command, key and gesture from that answer with its reason. Per-operation checks
at the write are the seam for per-user policies.

## Search and verification

Fusion of the keyword and vector branches keeps the keyword branch's first hit in each kind first
(`fuse_keeping_the_lead`). W387 reports a stale generated header. The verifier reports occurrence ids listed as
entities (E301) and relations a body draws by nesting that `connection-ids-used` omits (E316), which format 7
repairs.
