# 0.3.1 — detail

The short version is in [`CHANGELOG.md`](../CHANGELOG.md). Nothing the product serves changed shape
in this release: no new route, no new payload field except one refusal, no model semantics. What
changed is what a whole-repository verification does to the process it runs in.

## The complaint

A cold `artifact_verify` over the whole repository took minutes, and for those minutes the backend
answered nothing else — not `/api/backend-identity`, not a health probe, not the event stream. An
operator watching the GUI saw a frozen application and no reason for it; one waited out a 30-minute
client timeout on a call that was working correctly the whole time.

Two separate faults sat behind that. The pass held the workspace gate for its entire duration, so
every write waited for it. And the pass ran on the event loop, so everything else waited too.

## What a pass actually holds

A pass has two halves with very different requirements. **Acquisition** reads the repository — a stat
sweep plus every file's bytes — and must be indivisible, or the pass judges a mixture of two states.
**Evaluation** applies every rule to what was read, and needs nothing but the bytes it already holds.

Measured on the 880-file, 1.0 MB repository: acquisition takes **192 ms**; the pass takes **minutes**.
Exclusivity was being held for the second number when only the first requires it.

So a pass now acquires one `RepositorySnapshot` and evaluates from it, and the gate is released
between the two. A write arriving during evaluation is admitted immediately; a write arriving during
acquisition waits, and its wait is bounded by how long reading the tree takes. Both are asserted.

The guard against a rule quietly reaching past the snapshot is behavioural rather than a search for
`read_text`: acquire, corrupt every file on disk, evaluate, and demand identical diagnostics. A rule
that still touches the filesystem fails immediately. PlantUML syntax checking is the one documented
exception — it shells out to `java -jar` over paths, and a `.puml` file's syntax is self-contained.

## Verification inside a write

The first design for this said "the verification entry point wraps its work in `gate.reading()`".
That would have deadlocked the backend on a routine promote.

Whole-repository verification is not only a read operation. It is a *step inside two write
operations*: `promote_execute` and `cascade_delete` both verify the target tree while the authorized
mutation executor holds `gate.writing()`. The gate is not reentrant — `reading()` waits while
`_writing` is set — so a verifier that acquired READ for itself would have waited on its own caller,
for ever, with no error and no log line.

Acquisition therefore never takes the gate. *Who* acquires is the caller's decision, made where the
gate context is known: the MCP read path wraps acquisition in `gate.reading()`, and the two write
paths call it holding WRITE, which is strictly stronger. Both nesting cases have regression tests,
because the failure only appears when those paths reach their verification step, which most tests
stub.

## One sweep, not two

Reachable with no concurrency at all: the incremental path built the file inventory, decided a full
pass was required, and called the full path — which built the inventory *again*. The state saved at
the end paired the **first** sweep's file snapshots with the **second** sweep's results.

A file changed between the two builds was therefore recorded as verified at a state it was never
verified at, and the next incremental pass trusted that record. Nothing reports it; the file simply
stops being checked.

A pass now acquires exactly once, at the top, and every branch — `full`, `incremental`,
`incremental-cached` — shares the same image.

## Off the event loop

FastMCP dispatches a synchronous tool directly on the event loop: `func_metadata` awaits an async
function and *calls* a sync one. `artifact_verify` was synchronous, so a minutes-long pass occupied
the only thread serving every other request.

It is a coroutine now, and its pass runs on a worker of its own. Its own, not `asyncio.to_thread`'s
default executor, which git-status, group refreshes and every other offload share — a pass sitting in
that pool for minutes starves them. And not a pool per call either.

Shutdown abandons a pass rather than draining it, and cancels before abandoning. A pass owes nothing
durable, so waiting would spend the stop budget on an answer nobody will receive; but a pass left
merely un-awaited would finish and *save* on the way out, which is the one thing a stopping process
must not do.

## Refused, not queued

A second pass over the same roots is refused. Queuing it would make the caller wait minutes to be
told what the first pass is about to say anyway, and a queue that accepts every duplicate is how a
retrying client turns one slow answer into an hour of work. The refusal is a `pass_mode` of
`already-running`, in the shape of the `full-required` refusal beside it.

Cancelling the awaiting task cancels the pass. It stops *between files* — the grain at which stopping
is cheap and the partial result coherent — and it stops by **raising**, which is what keeps the
promise that it writes nothing. Every `save` sits after the work in its own function, so an exception
passing through cannot produce one. The check governs `incremental-cached` too, which applies no rule
and so trips no per-file check, and still saves.

## A pool that cost on every axis

A pass fanned out over `min(32, cpu + 4)` threads — the `ThreadPoolExecutor` default, which is sized
for work that *waits*. Rule evaluation never waits. Interleaved, repeated runs against the live
repository, on a machine shared with other work, recording the backend's own CPU seconds beside wall
clock so that external load could be told from real cost:

| workers | wall | backend CPU | identity p95 during the pass |
| --- | --- | --- | --- |
| 1 | 73 s | 92 s | 11.6 ms (1.5× idle) |
| 2 | 161 s | — | 14.7 ms |
| 4 | 314 s | 408 s | 18.6 ms (2.7×) |
| 20 | 298 s | 403 s | 44.9 ms (5.9×) |

Four threads spend **4.4× the CPU** of one for the same 880 files. That is redundant work, not
scheduling overhead: a profile puts the pass in pure-Python YAML parsing (200,574 documents) and path
resolution (982,904 `realpath` calls). Pure-Python YAML holds the GIL throughout, so the threads
cannot overlap and only add contention.

The default is now one file at a time. `ARCH_VERIFY_WORKERS` opts back in, so the number can be
re-measured without a release once the per-file cost comes down.

Two other candidate fixes were tested and **rejected** rather than assumed: a 1 ms GIL switch
interval measured worse on both axes (p95 27.5 → 31.0 ms, wall 308 → 327 s), and the per-file rebuild
of pass-invariant id sets in `verify_outgoing` measured at 0.1 s across an entire pass.

## Two hazards in the gate itself

**A writer nothing woke.** `reading()` notified waiters only when the reader count reached zero, so
under continuously overlapping readers a waiting writer was never woken at all — not delayed,
unreachable. Readers now yield while a writer waits, and every release notifies.

**A mirror nothing cleared.** Lock ownership was tracked in a thread-local mirror of the index lock's
state, which is correct only while the thread that acquires is the thread that releases — an
assumption offloading work to an executor quietly breaks. The lock now answers for itself, and the
lock-order check guards `reading()` and `privileged_writing()` too, which were unguarded. This also
removed an import cycle: the dependency now runs the same direction as the lock order it describes.

Separately, the filesystem watcher stopped taking a write gate around its refresh enqueue. It mutates
an in-memory queue, not the workspace, and nothing there was protected by the acquisition — but it is
a periodic, unawaited writer, so it collided with everything.

## The wrong repository answered

Found by running two backends on one machine, which is not something a unit test does.

The second was given its own `--repo-root`, `--enterprise-root` and `arch-workspace.yaml`.
`/api/backend-identity` truthfully reported those roots. Its MCP tools then read the *first*
workspace's repository — 880 files out of a directory that was empty. Nothing errored. The wrong
repository simply answered.

The MCP layer resolved its default roots from `Path(__file__).parents[4]`: where the code lives. That
is the workspace in a developer's checkout, and in the container, where `arch-workspace.yaml` is
mounted beside the code at `/app` — which is exactly why it had never shown up. It stops being the
workspace the moment one installed copy serves a different directory.

Twelve modules share that resolution, `write/entity.py`, `write/connection.py` and `delete_tools.py`
among them, so this was never confined to reads: an authored entity or a delete could land in a
neighbour's model. It is the hazard `/api/backend-identity` was introduced for in 0.3.0, one layer
further in — client *routing* was fixed then, and the server's own resolution was not.

The backend already knows what it was told to serve. That is now the first answer; the code-relative
path remains the fallback for a process with no served roots, which is what the stdio bridges and the
CLIs are.

## How this release was tested

Beyond the standard gates, because the standard gates would not have found either of the two defects
above:

- **Both nested write paths driven for real.** The F6 deadlock guard used to assert a *lookalike* —
  a thread taking `gate.writing()` and calling `verify_all`. It now drives `promote_execute` and
  `cascade_delete` through their REST routes, and asserts the *premise* too: that the gate really is
  held at the moment verification runs. "The promote completed" passes just as well once the nesting
  quietly goes away, at which point the guard guards nothing.
- **SIGTERM with a pass in flight**, the pass confirmed in flight by a second verify being refused as
  `already-running`. The process exits in 0.6 s against its own 27 s contract, without SIGKILL, and
  leaves no incremental state.
- **A real MCP client killed mid-pass.** Admission is released — the tool is not wedged until
  restart — and the next verify runs a full pass, because the interrupted one saved nothing.
- **The deployment matrix**: `--read-only`, `--admin-mode`, and two backends on one machine, which is
  what found the defect above.
- **The steady state**, all at once: a full pass, authorized writes, the watcher and git-sync. 1274
  read requests with **0 failures** at p95 12.1 ms, 37 writes admitted with **0 refused**, the
  slowest taking 0.3 s against a 75 s pass.
- **Docker upgrade acceptance** against a rebuilt image and a copy of a real previous-release volume
  export with its pre-upgrade state restored.

## What is not fixed

The per-file cost above. Verification parses ~228 YAML documents and resolves ~1,100 paths per file,
with `yaml.CSafeLoader` available in the environment and unused at every call site. A C loader would
cut the parse cost *and* release the GIL, at which point parallelism might genuinely pay — so the
worker default should be re-measured after that work, not before it.
