# 0.10.1 — detail

Maintainer-facing mechanism for the summary in `CHANGELOG.md`.

## A PlantUML diagram body may reference no file or URL, and the renderer could not follow one if it did

PlantUML's preprocessor and its creole markup can read local files and fetch URLs, and under its
default security profile both succeed and their result is drawn into the output. The product's
defence was one check, `puml_safety.find_unsafe_puml_directives`, which listed the directives it
refused. Three things were wrong with it, each confirmed against 0.10.0:

- **The list was incomplete.** Its include pattern ended `!(include|includeurl|…)\b`, and the word
  boundary does not match before an underscore, so `!include_once` and `!include_many` passed. Creole
  images (`<img:path>`, `<img src=…>`) and a C4 macro's `$sprite="img:path"` were not in the list at
  all. `!include_once <canary>` put the canary's contents into the rendered SVG.
- **Only the edit path applied it.** The diagram edit path called it; the create path
  (`diagram.py::_build_from_puml`) did not, and a body that arrives through git passes no write path
  but is rendered by the verifier's syntax check and by every on-demand render.
- **Nothing stood behind it.** PlantUML ran with the default profile. An earlier comment judged the
  SANDBOX profile unusable because it refuses the managed relative includes
  (`!include ../_archimate-*.puml`); every render path already inlines those before PlantUML sees the
  body, so the judgement held only for the verifier, which handed the stored file over unexpanded.

**The policy is now an allow-list with one owner in the application layer**,
`src/application/puml_directive_policy.py`, re-exported from `puml_safety`: `!include <…>` for the
bundled standard library, `!include ../_*.puml` for the managed fragments, and `img:` only with a
`data:image/…;base64,` target. Every other `!include*` and `!import*`, `!theme … from`, the builtins
that read the environment or the filesystem (`%load_json`, `%getenv`, `%file_exists`, `%dirpath`,
`%filename`, theme loaders), and every other image target is refused. It is applied at the create
and edit paths, in `render_puml_bytes` on the prepared bytes (previews, reading lenses), in
`render_diagram_outputs` before the on-disk render, and in the verifier's syntax check, which reports
`E353` and does not render.

**Every PlantUML run is sandboxed through one builder**, `artifact_verifier_syntax.plantuml_command`,
which always passes `-DPLANTUML_SECURITY_PROFILE=SANDBOX`. The five launch sites — the on-demand
renderer, the two on-disk renders, the single and batch syntax checks — and the runtime check use it,
and a fitness function refuses any other code that assembles a `-jar` command. For the syntax check,
`DefaultPumlSyntaxAdapter` hands PlantUML a copy of a file whose managed-fragment markers are
replaced by the generated fragment, the same bytes every render produces.

`tests/rendering/test_a_puml_body_cannot_reference_files_or_urls.py` holds both barriers
separately: the spellings the list missed, the refusal on each write and render path, the sandbox run against the attack
with the policy bypassed (watched fail with the profile set to UNSECURE), the C4 standard library
still rendering under the sandbox, and a stored managed marker still verifying.

The defect and both barriers are recorded in the assurance self-model: the existing STPA-Sec analysis
of the PlantUML preprocessor gains the three loss scenarios above, a second constraint for the
sandbox, the earlier constraint restated as the property it claims, a risk entry, two FMEA failure
modes with occurrence judgements, and an assurance case for the render path.

## GSN side nodes

`gsn/svg_renderer._place` stacked a rank's side nodes (contexts, assumptions, justifications)
downward from the rank's centre line, inside a band sized for the rank's main row. A second side node
therefore reached into the next rank, where that rank's own side node was drawn over it. Each rank is
now as tall as the taller of its main row and its side stack, and the stack starts at the rank's top.

The side column is right of the whole argument, so a qualified node that was not rightmost in its rank
had its connector drawn across the nodes beside it, which then read as the node being qualified.
`_place` now orders each rank so that nodes with side nodes come last; the order is otherwise kept.

## The baselines listing and its contract

`SQLCipherAssuranceArchive.list_baselines` returns every column of `baselines`, and the table has
carried `timestamp_token_hex` since RFC 3161 timestamps were added. `AssuranceBaselineRecord` is a
closed contract and did not declare the field, so validation refused every row and
`GET /api/assurance/baselines` answered 500 as soon as one baseline existed. The contract now declares
it as an optional nullable string, and the GUI's schema follows. The HTTP tests used a fake archive
whose rows were whatever the fake returned; `test_a_sealed_baseline_lists_through_its_contract.py`
seals with the real archive and validates its rows against the contract.

## An edit re-renders a GSN argument

The edit path decided whether `diagram_entities` generate the body by asking whether the diagram type
declares diagram-owned entity types (`ui_config.diagram_only_types`). That holds for activity,
sequence, datatype and the C4 types, and not for GSN, whose goals, strategies and solutions are
hosted by the diagram without declared types. A GSN edit therefore stored the new nodes and kept the
old body and picture; creation, which renders from the entities whenever no body is supplied, had
always looked right. The diagram-type protocol now carries `body_is_rendered_from_diagram_entities`:
the base answers from the declared types as before, GSN answers true, and
`diagram_entities_are_authoritative` asks it. Bowtie and control-structure diagrams keep the base
answer: they are projections of the assurance store, whose nodes exist there with connections of
their own, and are drawn from it.
