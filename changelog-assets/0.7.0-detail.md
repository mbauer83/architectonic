Maintainer-facing mechanism for the summary in `CHANGELOG.md`.

## One vocabulary for what a document should reach

`required_entity_type_connections` said what *entities* a document should link and could say
nothing else. A term now names one of three vocabularies, under one pair of fields:

```json
{
  "required_connections": ["requirement", "@internal-behavior-element", "doc:adr"],
  "suggested_connections": ["principle", "diagram:c4-container", "doc:@all"],
  "sections": [
    { "name": "Architecture Decisions", "required_connections": ["doc:adr"] }
  ]
}
```

| form | names | example |
| --- | --- | --- |
| bare | one entity type | `requirement` |
| `@class` | every entity type in an element class | `@internal-behavior-element` |
| `@all` | any entity | `@all` |
| `doc:<type>` | a document of that `doc-type` | `doc:adr` |
| `diagram:<type>` | a diagram of that `diagram-type` | `diagram:c4-container` |
| `doc:@all`, `diagram:@all` | any document, any diagram | `diagram:@all` |

### Why one list rather than a field pair per kind

The entity-only pair was named *literally* at thirteen sites: the schema loader, the verifier, the
promotion closure, the placeholder writer, two REST contracts and four GUI modules. Two more kinds
as parallel pairs would have meant six field names at each of them, and eight when a fourth kind
arrives. The verifier's severity split and the promotion set-difference are per-*term* rather than
per-field, so they would have been the same code written three times.

A term stays a `str`, which is what keeps the set arithmetic in `promote_schema_check` and the GUI
chips working without a shape change.

### The prefix is a syntax, so it has an owner

`src/application/artifacts/reference_terms.py` — `parse_reference_term` for the kind and the name
within it, `ReferenceTermVocabulary` for whether a term expands here, what a link of that kind would
satisfy, and how to say it in a message. It has a row in
`tests/architecture/test_each_syntax_has_one_reader.py`, whose probe is the literal `doc:` or
`diagram:` handed to a locating call.

The write/read round trip is stated over what the syntax **permits** rather than over what the
shipped schemata declare. A gate of that shape stated over the shipped catalogue alone passes
against a broken reading whenever the catalogue exercises none of the interesting cases, which is
what happened to the PUML-alias round trip in 0.5.3.

### The old spelling

Read at the one loader (`document_schema.normalize_document_schema`) and never emitted again. Both
keys are read rather than one winning, so a schema part-way through being rewritten cannot silently
lose whichever list it kept in the old spelling. Existing repository schema files are not rewritten
on upgrade; the shipped defaults and this repository's own were.

### Classifying a link is a filter, not a fourth reading

`document_links.resolve_artifact_links` opens each target `references_from` yields and says whether
it is an entity, a document or a diagram, and of which type. It replaces `resolve_entity_links`,
which reported every target's `artifact-type` — so a linked diagram contributed the literal type
`diagram` to the set an entity term was matched against, and a linked document the literal type
`document`. Harmless only while no entity type is spelled either way.

It reads the target's own frontmatter rather than the artifact index, which does hold a path→id map:
the verifier's document rules take an optional registry and run over a *staging* directory during
write-time preview, where the document is not indexed and its links reach out of the staged tree.

### Three states, not two

Diagram types are the one conditional vocabulary: a host without the confidential store registers no
assurance module. `TermStatus` therefore has `UNREGISTERED` beside `KNOWN` and `UNKNOWN`. A stored
diagram of an unregistered type still satisfies the term — the link resolution reads the diagram's
frontmatter, which does not care what is registered — and an unmet one is **W159** rather than
E155/E156.

### Verification and promotion

| case | document level | section level |
| --- | --- | --- |
| unknown term | E155 | W157 |
| unmet requirement | E155 | E156 |
| unmet, term names an unregistered diagram type | W159 | W159 |

One rule serves both levels now; they differ only in severity and in whether the message names a
section.

Promotion closes over a required document or diagram exactly as over a required entity: the
enterprise verifier raises E155/E156 for the dangling link after the copy either way, and plan time
is where the artifact that would fix it can still be named. `_ClosureScope` gains document
membership from `registry.enterprise_document_ids()`, which already existed. The engagement/
enterprise schema comparison also compares the document-level terms, which it had never done — a
term the enterprise schema requires and the engagement one does not lets an engagement author a
document the enterprise then refuses.

## C4: the two axes

`_C4_LEVELS` was a linear depth carrying a comment about why `c4-system-landscape` had no row in it.
Both new types exist now, and only one of them is a level.

```python
_C4_LEVELS = {"c4-system-landscape": 0, "c4-system-context": 1,
              "c4-container": 2, "c4-component": 3}
DEPLOYMENT_TYPE = "c4-deployment"          # deliberately absent from the levels
```

A deployment view draws the *same* containers a container view draws, placed on the technology that
hosts them. A depth would claim it sits below components. The navigation names the relation in its
own two fields instead — `deployment_diagrams` from a logical view, `subject_diagrams` from a
deployment one — and `current_level` is `null` there.

### A scope that is a set

The other four C4 types are scoped by one entity. A portfolio has no single subject, so `Target`
gains `entity_ids` beside `entity_id` — the entity counterpart of `connection_ids`, which has
carried a set since bindings shipped. **E405 is unchanged**: a landscape still has exactly one
diagram-level `scoped-by` binding, and the plurality lives in its target. A member that does not
resolve is **E414**, as a `connection_ids` member is E407.

`_ResolvedState.scope_item` became `scope_items`. The render modes divide along the same line a
boundary does: `node` draws every scope item, `boundary` wraps the single one.

### Deployment is derived, not declared

ArchiMate has no relation from a node to an application component, and `connections.yaml` permits
none — so the ontology needed no change. What is permitted is the two-hop chain, and that is what
`_hosts_of` walks:

```
technology-node --aggregation--> artifact --realization--> application-component
```

A container with no artifact is undeployed and is left out rather than given an invented host. Each
host is drawn as a `Deployment_Node` boundary with its containers inside; the system in scope is the
title rather than a box, so it is not part of what the diagram references — the same rule that holds
at container and component level. The C4-PlantUML header is now the type's to declare
(`c4.puml_stdlib`), because `Deployment_Node` lives in `C4_Deployment` and including the component
header would have left the macro undefined and rendered an error image.

### Four consolidations the two types forced

Each replaced a rule that could only say "one":

- `scope_entity_ids` / `scope_target` / `scope_shorthand` in `domain/diagrams/bindings.py` are the
  one reading of a diagram-level `scoped-by` binding over parsed records; `diagram_scope_entity_ids`
  is the same rule over unvalidated frontmatter, where parsing first would raise on a file whose
  whole problem is that it is malformed. A test holds the two to the same answer. Three modules
  spelled the loop themselves, and each read only the singular target.
- `render_entities_with_scope` restores the scope the persist path strips. The create path and the
  edit path each had a copy. The key comes from the binding's target *shape* rather than from how
  many ids it holds, which is what keeps `_scope_entity_ids: [one]` round-tripping as itself; the
  read envelope serves it back by the same rule.
- `C4Projection.scope_of` declares which drawn scope item a non-drawn descendant rolls up to, in
  place of "if this is the context level, everything falls back to the one root" — a rule a
  landscape's several roots cannot state.
- `SCOPE_KEY` / `SCOPE_IDS_KEY` moved to the domain beside the binding they normalise into, which is
  also what the dependency policy requires of a diagram type reading them.

`_projection.py` reached 425 counted lines against a 350 limit. The deployment axis moved to
`_projection_deployment.py` and the strategy registration to `_manifest.py` — registration rather
than algorithm, and the composition root imports `MANIFEST` from there.

## arc42

Twelve sections in the standard's order, each declaring what it expects:

| § | section | asks for |
| --- | --- | --- |
| 1 | Introduction and Goals | `goal`, `outcome`, `stakeholder`, `requirement` |
| 2 | Architecture Constraints | `driver`, `principle`, `@motivation-element` |
| 3 | Context and Scope | `diagram:c4-system-context`, `diagram:c4-system-landscape` |
| 4 | Solution Strategy | `doc:adr`, `principle`, `course-of-action` |
| 5 | Building Block View | `diagram:c4-container`, `diagram:c4-component` |
| 6 | Runtime View | `diagram:sequence`, `diagram:activity` |
| 7 | Deployment View | `diagram:c4-deployment`, `diagram:archimate-technology` |
| 8 | Cross-cutting Concepts | `doc:standard`, `doc:spec`, `principle` |
| 9 | Architecture Decisions | **requires** `doc:adr` |
| 10 | Quality Requirements | **requires** `requirement` |
| 11 | Risks and Technical Debt | `assessment`, `driver` |
| 12 | Glossary | `meaning`, `business-object` |

**It is the test of whether the vocabulary is expressive enough, and it needed no new field.**
`tests/domain/test_arc42_document_type.py` holds every term arc42 declares to resolving against the
complete catalogs, and holds that all three vocabularies are in use — if a section ever needs
something the terms cannot say, one of those fails.

Only §9 and §10 require anything. arc42 is unambiguous that decisions belong in one and quality
requirements in the other; everywhere else the template invites, so a skeleton is writable the day
it is created rather than refused by E156 twelve times over. The twelve headings themselves are
required, as for any document type (E154).

The id prefix is `SAD`, not `ARC`: `ARC` already prefixes ArchiMate diagram ids, and a test holds
the two apart.

### Licensing

arc42 is CC BY-SA 4.0. What is reproduced is the section structure; every hint is this project's own
one-line prose, because arc42's guidance text is the part ShareAlike would follow into the file that
carried it.

The licence gate inventories dependencies and sees nothing shipped inside the source, and
`THIRD-PARTY-NOTICES.md` is generated — so a hand-written section there would have been overwritten
on the next regeneration. `licenses/content.json` is a new inventory for shipped content, rendered
by `generate_notices.py` as a "Shipped content" section. A `license_text` that is a URI now
satisfies the missing-text check, because Creative Commons names a hyperlink to the licence as one
of the ways a redistributor may carry it.

`attribution` is also a field on the document type, served with the schema and shown on the create
form: an attribution only a notices file carries is not seen by whoever writes from the template.

## C4: notation, boundaries and stores

### A boundary is not an element

C4 says a group "will be rendered as a boundary around those elements" and that groups do not
appear as elements in the model. Three things in a generated body are boundaries — the scope
wrapper at the zoom levels, a grouping, and a deployment node with containers in it — and the
projection now treats them as one kind. Two rules follow and are enforced where membership is
decided rather than where the picture is written:

- a group holds one level of abstraction, so a member the level does not draw is not in the
  boundary, and a group left with no members is not drawn;
- nothing attaches to a boundary alias, so an edge that rolls up onto one is dropped. The
  containment survives in `scope_of`; only the drawing is declined.

`_boundary_aliases` decides this from `children` rather than from an item type, which is the same
test the renderer applies when it opens a boundary instead of drawing a box. An unoccupied
deployment node is a plain container and an edge may reach it.

### Roll-up over the whole closure

`rollup_conns` wants one endpoint outside the scope and `direct_conns` wants both endpoints drawn,
so a dependency between a drawn box and a deep descendant of *another* drawn box fell through both.
Collection now runs over the scope's full closure, and `scope_of` — filled at the zoom levels, not
only at context level — maps each undrawn descendant to its nearest drawn ancestor, which is the
box the edge lands on.

### Where a technology line comes from

Three sources in order: the host's own model type on a deployment view, the attributes the diagram
type's `config.yaml` names, then the technology element the model says *serves* the element. The
third applies only to a declared `data-store`. What serves an ordinary application is its host,
which is the deployment view's subject; C4-PlantUML infers the box shape from the technology
string, so an inherited host name could have drawn an application as a cylinder.

### Layout

`left to right direction` + `skinparam linetype ortho` + a nested cluster is a combination dot
cannot lay out. It is not a size limit: an eleven-box body with no hidden edges reproduces it, and
a fifty-six-box body with fifty-eight hidden edges does not. Two of the three are worth keeping, so
`_direction` is per diagram. Separately, hidden ordering chains are emitted after the visible edges;
declared before them the same chains crashed the same body.

### Module shape

`_projection.py` held the level algorithm and the vocabulary it is written in, so each of the three
sibling projections imported that vocabulary back from the module that calls them — a cycle, paid
for with a lazy in-function import and a lint suppression at four call sites. The vocabulary and
the projection records moved to `_projection_vocabulary.py`, and the structural walks to
`_projection_rollup.py`, which takes its relation types as parameters and therefore knows nothing
about C4. `topmost_ancestor` and `nearest_drawn_ancestor` are two stopping rules over one ancestry
walk; they had been written twice, in two modules, with two spellings of the cycle guard.

### Crash detection

`_is_error_render` read stderr. An `EmptySvgException` out of dot's orthogonal router exits 0,
prints nothing, and draws the trace into the image, so the rendered SVG's own text is read for it
(`_svg_is_error_image`). SVG renders first and the PNG only if it succeeded — otherwise a crashed
body reached disk under the diagram's own name before anything established that it was a crash.
`render_diagram_outputs` is the single owner: the create path raised `E350` and the shared commit
tail every edit goes through reported the same crash as a warning with `valid: true`.

## Migration

Nothing is required. The `*_entity_type_connections` keys are still read wherever a repository
carries them, and are treated as entity terms.

Two things move for a consumer of the HTTP surface:

- `GET /api/document-types` sends `required_connections` / `suggested_connections` in place of the
  `*_entity_type_connections` pair, and `attribution` where a type has one.
- `type_extras.c4_navigation` sends `current_level` as nullable, plus `scope_entity_ids`,
  `scope_entity_names`, `deployment_diagrams` and `subject_diagrams`.

A repository upgraded in place does not gain the `arc42` document type — `ensure_arch_repo_defaults`
never overwrites and only writes what is missing, so it arrives on the next `arch-init` or by
copying `arc42.json` into `.arch-repo/documents/`.
