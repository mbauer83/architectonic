## An element with two containers was drawn twice, and one drawing vanished

**Symptom.** A generated ArchiMate technology view rendered four of its region boxes **empty**, and
the region-to-environment membership was simply absent from the picture. `artifact_verify` reported
`valid: true`, because every id in `entity-ids-used` and `connection-ids-used` resolved — what was
lost is not an id.

**Cause.** PlantUML containment is a tree. A second `as ALIAS` for an alias already declared is not
an error: it is read as a *reference* to the element already created. The generator nested each
aggregated child inside its parent, and an element aggregated by two parents was emitted **once
under each, with the same alias** — so PlantUML built it inside the first, treated the second as a
reference, and rendered the second container empty.

Observed on a 17-element technology view: **29 `as <alias>` declarations for 19 distinct aliases**,
ten elements emitted twice, every one an environment aggregated by both its subscription and its
region.

The smallest case — two containers aggregating one element:

| shape | declarations | distinct aliases |
| --- | --- | --- |
| two parents, one child | 4 | 3 |
| three parents, one child | 7 | 5 |
| two parents, child has its own child | 7 | 5 |
| single parent (control) | 3 | 3 |

The third row shows the duplication is **recursive**: a twice-parented element takes its whole
subtree with it, so an element with *n* descendants duplicates *n+1* aliases.

## A containment cycle emitted an empty diagram

The same shapes, extended to a containment **cycle** — A aggregates B, B aggregates A — emitted
a body with **no elements at all**:

```
@startuml repro
title repro
@enduml
```

Both elements counted as nested, so neither was left to declare at top level, and nothing rendered
them as a child of anything. A self-aggregation (A aggregates A) did the same with one element.

Both symptoms are one broken invariant. `build_visual_nesting` kept **three** records of one fact
and they disagreed: `children_map` held every parent, `direct_parent_by_alias` held the *last*, and
the junction path updated two of the three. They are now one record — `_NestingForest` — that admits
only a forest: one parent per child, first wins, nothing inside itself, no cycle.

## Why the fix needed no new mechanism

Two mechanisms could express the containment that cannot nest: `diagram_entities.occurrence[]` — the
documented form for "additional occurrences of an already included model entity", making the second
drawing a distinct element backed by the same entity — or an arrow.

The arrow was already built. `render_connection_lines` draws a nesting-class
relation as its own typed arrow whenever the pair is **absent** from `children_map` — written for the
authored-group case, and carrying this comment:

```python
# Not nested visually (e.g. the member belongs to an authored group,
# which wins) — the relation must still be EXPRESSED: draw its arrow.
```

It was suppressed here only because `children_map` wrongly claimed the child under *both* parents.
Making the nesting a forest restores the arrow with no new code: containment that can nest still
nests, and the rest is drawn as the relation it is.

Occurrences were not used. They are **author-declared** drawings with their own ids in
`diagram-entities`; synthesising them would mean the generator inventing and persisting ids in order
to draw one model element as two boxes with nothing saying they are the same.

## E318, and where the gap was

The renderer can no longer produce a duplicate, but the hole was the verifier passing a body that had
already lost a relationship. **E318** refuses a body that declares an alias twice, read through
`application.puml_alias_declarations` — the owner registered in 0.5.3, not a second reading.

Two scoping decisions, both paid for by measurement rather than argument:

- **Only bodies in the element-declaration vocabulary.** A diagram type that owns its entity types
  (`diagram_only_types` — datatype, C4, sequence) carries unquoted prose no reading of `as ALIAS` can
  tell from code. This repository's own persistence-model datatype diagram describes a record
  "persisted **as a** single markdown file" twice. Across the 48 bodies here, that is the only hit.
- **The `as` form only, counted raw.** `macro_alias_declared_on` answers the first argument of any
  `Name(ALIAS, …)` line, for renderers that emit `Person(alias, "label")`. On an ArchiMate body that
  shape is a *relation*: `Rel_Realization(REQ_kOU3al, OUT_620dTh, "")` names two aliases and declares
  neither, and reading it as a declaration reported **three duplicates in a clean diagram**. And
  `normalize_puml_alias` folds `-` to `_`, which PlantUML does not — two aliases differing only there
  are two elements.

Error rather than warning: the defect is silent by construction, severity is what decides whether a
refresh may write the body, and nothing in either repository has to change to satisfy it.

## One insertion of a direction into an arrow token

Drawing the diamond (below) needs the `o--` and `*--` token forms. All **three** implementations of
"insert a direction into an arrow token" returned those **unchanged** — each tests `startswith("-")`
and `startswith(".")`, and a token opening with a source marker matches neither.

The three: the renderer's (`_diagram_text`), the layout optimiser's that rewrites stored bodies
(`artifact_write_layout`), and one in `diagram_builder` that **no caller had reached since it was
copied**. The two live ones agreed exactly, which is the dangerous kind of duplicate — nothing failed,
so nothing reported them. A fix applied to the renderer alone would have left the optimiser silently
dropping the direction from every arrow it rewrote: a layout regression with no failing test anywhere.

`application.puml_arrow_tokens` now owns both inserts, and the register has a row for it with a probe
on the direction alternation any second implementation must spell. Application rather than
infrastructure, because the layout optimiser is an application module that was reaching into
`infrastructure/rendering/` for it.

The syntax register added in 0.5.3 did not catch this, and could not have: its probes are literals
handed to locating calls, and this duplication is *logic*. That remains the open item (B23).

## The diamond the ontology already declared

Once a containment that cannot nest is drawn as an arrow, the arrow is visible — and it was a bare
`-->` with `show_stereotype: false`, so nothing on the picture said which relation it was.

`connections.yaml` declared both spellings of one fact and they disagreed:

```yaml
archimate-composition:  puml_arrow: "-->"   notation: {line: solid, source: filled-diamond, target: none}
archimate-aggregation:  puml_arrow: "-->"   notation: {line: solid, source: hollow-diamond, target: none}
```

`notation` is read by the GUI graph canvas, which drew both diamonds; `puml_arrow` is read by the PUML
renderer, which drew neither. Two views of one relationship, disagreeing.

**The claim that kept them that way** is in `relation_notation`'s own docstring: *"PlantUML expresses
containment by nesting rather than by a diamond, so composition and aggregation are both spelled
`-->` there."* The first half is true and is why nesting remains the default. The conclusion does not
follow, and PlantUML disproves it — `A o-- B` between two rectangles renders

```xml
<polygon fill="none" points="91,78.6069,87,84.6069,91,90.6069,95,84.6069,91,78.6069"/>
```

a hollow diamond at A, and `*--` the filled one. The docstring is corrected rather than deleted,
because the claim is why the values were wrong.

**The gate found more than it was written for.** `dt-composition` and `dt-aggregation` have been
spelling `*--` and `o--` since they were written — the datatype diagrams were drawing PlantUML
diamonds all along, which is independent proof the claim was wrong — while declaring
`notation.source: none`, so the graph canvas drew them plain. Declaring their notation was not
enough: **only the ArchiMate loader parsed `notation` at all**, so the field was silently ignored
everywhere else. The diagram-type, assurance and SysML loaders read it now.

`tests/domain/test_arrow_spells_the_notation.py` holds the two in agreement in both directions: a
declared diamond must be spelled, and a spelled diamond must be declared. It asserts end markers
only — line style is left out deliberately, and three types disagree on it today
(`archimate-access` declares dotted and spells solid; `flow` and `influence` declare dashed and spell
dotted). `archimate-assignment` declares a `ball` at the source, which PlantUML has no form for, so
`-->` is the honest approximation there and is not asserted.

## Measured on the repository

Every diagram re-rendered through the product's own refresh path
(`artifact_edit_diagram(puml="auto-sync", dry_run=true)`), old against new.

| | |
| --- | --- |
| diagrams re-rendered | 47 (34 auto-layout, 9 standalone, 4 projector-owned) |
| bodies changed by the nesting fix | **0**, over 85 nesting decisions with 0 rejections |
| bodies changed by the diamond | 2 — one gains the diamonds, one reorders a frontmatter list |
| entity or connection ids gained or lost | **0**, in any of the 47 |

No diagram in this repository has an element with two containment parents, so the nesting fix is a
no-op here and the defect it fixes is one this repository could not have shown.

The one picture that changes: `GOL_FCfDuc -down-> GOL_7RZp1S` becomes `GOL_FCfDuc o-down- GOL_7RZp1S`
— the direction survives, which is what the consolidation above was for. The one reorder is a pair
carrying **both** a composition and a triggering: with composition no longer spelling `-->`, the bare
arrow resolves to the triggering directly instead of by fallback.
