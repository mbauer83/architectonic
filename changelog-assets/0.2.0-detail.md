# 0.2.0 — detailed changelog

Every change since `v0.1.0` — 148 commits — at the grain a maintainer or a migrating consumer needs.
`CHANGELOG.md` carries the summary and what an adopter must *do*; this carries the reasoning, the
statuses and the per-route detail behind each line of it.

Split for the reason the route map was: a reader should be able to finish the changelog. Compressed
into it, this produced a release section adopters skimmed, which is the same as not publishing it.
Nothing is lost by moving it — this file is part of the release record.

See also **[the route map](0.2.0-route-map.md)**: all 79 renames, held against
`src/infrastructure/rest/route_policy/_retired.py` by a fitness function.

---

### Breaking — REST resource addressing and response contracts

Identity of the resource an HTTP operation addresses now belongs in the path; filters stay in the
query. **There are no aliases and no redirects** — every consumer moves in this release. Persisted
local data is migrated non-destructively; nothing else is.

**[Complete route map → `changelog-assets/0.2.0-route-map.md`](changelog-assets/0.2.0-route-map.md)**
(79 retirements with their replacements). `operationId` is unchanged across the renames, so a
generated client keyed by operation id needs only the new paths.

Why the surface is shaped this way is in the ADRs, not here: *Resource Addressing: Identity in the
Path, Filters in the Query*, *Response Contracts Are Owned by the Server and Generated Outward*, and
*The Assurance Analysis Aggregate: Filing, Provenance and Participation Are Three Relations*.

#### Errors — every body changes shape

- **One typed envelope everywhere.** `detail` is an object, not a sentence:
  `{"detail": {"code", "message", "details", "request_id"}}`. `code` is a closed vocabulary,
  `details` is a per-code payload. **Anything parsing `detail` as a string must change.** The
  assurance surface included: it answered `{"error": "...", ...}` with a vocabulary of its own, so a
  client branching on `detail.code` fell through on every refusal it made.
- **A refused deletion is an error, not a `200` carrying `ok: false`.**
- **Three assurance statuses change.** Deleting an analysis that authored nodes is
  `409 analysis_not_empty`; filing under a group that does not exist is `404`; a rejected field value
  is `422`. All three were `400`.
- **A failed signal ingest, an unknown vulnerability and an absent snapshot answer the envelope**
  rather than a body carrying a `status` word. The status codes are unchanged.
- **An identifier that collides with a literal collection segment is refused** with `400` — a
  viewpoint named `pins` or `criteria-catalog` could be written and never read back.

#### Methods and statuses

- **Partial updates are `PATCH`; whole-resource replacements are `PUT`.** `POST …/edit` is gone.
- **Deletions return `204` with no body** — except a dry run, which returns `200` with its envelope.
- **Recording an FMEA factor is `POST`**, at
  `/api/assurance/nodes/{node_id}/factor-assessments`: it appends a revision, and `PUT` promised an
  idempotence the surface never had. `node_id` leaves the body.

#### Routes that split or collapse (not in the route map, which lists renames)

- **`GET /api/ontology` becomes two.** It chose its shape by whether `target_type` was supplied, so
  no single schema could describe it. Use `GET /api/ontology/classification?source_type=` for what a
  type may connect to, and `GET /api/ontology/pairs?source_type=&target_type=` for what is permitted
  between an ordered pair. Naming a document or diagram reference as an endpoint now answers `422`.
- **The four `*-complete` endpoints collapse into one.**
  `GET /api/assurance/analyses/{id}/completeness` returns a method-discriminated response; `method`
  names which report it answered and the argument case travels under `case`. A method with no
  completeness projection returns `409 analysis_method_mismatch`.
- **`POST /api/assurance/security-snapshot-delete` is gone**, and with it the body that chose between
  deleting one snapshot and all of an anchor's. The scope is the address:
  `DELETE /api/assurance/security-snapshots/{snapshot_id}` or
  `DELETE /api/assurance/arch-artifacts/{arch_artifact_id}/security-snapshots`.
- **The unscoped FMEA matrix is gone.** `GET /api/assurance/fmea` with no analysis returned every
  failure mode in the store; the matrix is a projection of one analysis.

#### The assurance analysis aggregate

- **`POST /api/assurance/nodes` is gone.** A node is created inside its provenance analysis, at
  `POST /api/assurance/analyses/{analysis_id}/nodes`, and provenance is mandatory. `analysis_id`
  leaves the node edit contract; `PUT /api/assurance/nodes/{node_id}/provenance` is the only route
  that may set it, and only for an unattributed node — re-asserting the same analysis is `204`,
  asserting a different one is `409 provenance_immutable`.
- **Participation is a relation, not a collection post.**
  `PUT`/`DELETE /api/assurance/analyses/{id}/participating-nodes/{node_id}` are idempotent and answer
  `204`; the node is in the path. A node may not participate in the analysis that authored it —
  `409 invalid_participation`.
- **Deleting a node another analysis references is refused** with `409 entity_in_use`, and the details
  name the referencing analyses. Remove the participation relations first.
- **Deleting an analysis ends the participation it held, and nothing else** — the nodes it authored
  survive with their provenance intact.

#### MCP

- **`assurance_create_node` requires `analysis_id`**, `assurance_edit_node` no longer accepts it, and
  `assurance_assign_provenance` is the repair tool for an unattributed node.
- **Execution errors report the REST vocabulary.** The shape is unchanged — JSON-RPC has no HTTP
  envelope, so a failure still arrives in band as `{"error": {code, path, message}}` — but the `code`
  is now the same word REST uses. `execution-timeout` and `derivation-limit` become
  `traversal_time_budget_exceeded`, `binding-cardinality-violation` becomes
  `binding_cardinality_violation`, and `missing-parameter` / `unknown-parameter` /
  `parameter-type-mismatch` become `validation_error`, with the parameter named in `path`.
  An agent reading both surfaces saw two names for one failure.

#### CLI

- **`arch-gui-server` is gone.** It named `src.infrastructure.gui.gui_server`, a module this release
  renamed, so the command raised `ModuleNotFoundError` on any invocation. Nothing referenced it and
  `arch-backend` is the documented way to run the server, so it was removed rather than repointed.

#### Fixed

Each of these was reachable in ordinary use and invisible to every gate; the browser suite is what
found them.

- **A repository-authored viewpoint could not be applied to anything.** The write path built its
  verifier from the process catalogs, whose viewpoint catalogue is the module-shipped starter
  library and reads no repository — so a diagram or matrix naming a definition you had just saved
  was refused with `E180 Unknown viewpoint slug`, permanently rather than until a restart.
- **A viewpoint with a binding made `GET /api/viewpoints` answer 500 for everyone.** The response
  contract declared `select` as `entity`/`connection`; the domain and the write path use
  `entities`/`connections`. One saved definition took the whole catalogue down with it.
- **The FMEA matrix rendered blank for any analysis with no dismissals.** `dismissal` was served as
  `{}` while the published contract declares both of its fields present, so the client's decode
  threw before a single row was drawn.
- **Three assurance links pointed at retired addresses** — the node list and its rows to
  `/assurance/node/{id}`, "Explore graph" to `/assurance/graph?node_id=`, and the FMEA wizard to the
  flat `/assurance/fmea` — and the standalone node page read the pre-rename `id` route parameter, so
  every assurance deep link resolved to an empty page.
- **An unserved address renders a not-found page.** There was no catch-all route, so a retired
  address, an old bookmark or a stale link rendered the chrome and an empty `<main>`.
- **`/api/diagrams/preview` answers 400 for a selection the diagram type cannot draw**, naming
  `diagram_entities`, instead of a 500 whose body deliberately carries no diagnostic.
- **A `?param.` value on a shared link is honoured.** For a definition whose parameters are all
  optional or defaulted the gate discarded them and the address-rewriting surfaces then erased them
  from the URL, so such a link could not even be re-shared. A value the parameter's type cannot
  represent now reaches the server and is refused, rather than being silently read as `false`.
- **The preview's derived-entity checklist honours the server.** The scope root can no longer be
  unchecked — the engine will not exclude it — and a server-side exclusion renders as excluded.
- **A witness chain that cannot be read says so** instead of showing "Loading witness chain…"
  for as long as the dialog stays open.

#### Additive

- **Every response carries `X-Request-ID`**, echoed from the request when supplied; every error
  response carries `Cache-Control: no-store`.
- **The OpenAPI document's version is the package version.** It previously read `0.3.0` against a
  `0.1.0` package, so a client pinning the document version was pinning a number nothing produced.

## Breaking

### A concept's specializations are one field, `specializations`

The scalar `specialization` is gone from every record, response contract and write input. It held the
first element of `specializations` and was reconciled with it in `__post_init__` so a caller could set
either one — two spellings of one fact, with a mechanism whose only job was to stop them disagreeing.

**Responses.** `EntitySummary`, `EntityRecordFields`, `ContextConnection`, the connection detail, and
the entity-context read all published only the first specialization; they now publish the ordered set.
A concept may carry several (ArchiMate §15.2), and a client that showed a badge for the primary had
nowhere to learn there were others, because the detail read had the same shape.

**Write inputs.** `POST`/`PATCH /api/entities…`, `POST`/`PATCH /api/connections…` and the
corresponding MCP tools (`artifact_create_entity`, `artifact_edit_entity`, `artifact_add_connection`,
`artifact_edit_connection`, `artifact_bulk_write`) take `specializations` only. Send `["x"]` where you
sent `"x"`; send `[]` to clear. A body that still carries `specialization` is refused `422` by the
closed contract rather than silently ignored.

**Three things keep the singular name, and are not this field:**

- the **on-disk frontmatter key** `specialization`, whose value is a scalar for one specialization and
  a list for several. Deliberate: 146 entity files carry the scalar form and stay byte-identical.
  `applied_specialization_slugs` is the one reader of both shapes.
- the **effective-schema selector** on `GET /api/entity-schemata/{artifact_type}?specialization=`,
  which names *which* schema to compute, not what an artifact carries.
- unrelated singular concepts: an AIBOM component's specialization, a guidance lookup key, and the
  ArchiMate exchange format's element specialization.

**Two latent defects this exposed**, both invisible while the scalar existed because callers took the
other branch:

- `edit_entity` and `edit_connection` read `isinstance(value, list)`, so a **tuple** silently became
  `[]` — the edit *cleared* the specializations instead of setting them, and the write-quarantine gate
  then had nothing to refuse. Over REST a JSON array arrives as a list, so this reached in-process and
  MCP callers rather than HTTP ones.
- `EffectiveEndpoint` carried the scalar into `_check_entity_relationship_restriction`, so a concept
  with two specializations had the second one's relationship restrictions **silently unenforced**.
  Nothing in the dogfood model carries two (146 of 500 carry exactly one), so no verification verdict
  changed; what is gone is a rule that held by accident of the data.

**Two improvements that came free.** A viewpoint condition on `specialization` now matches a concept by
*any* of its specializations — `_compare` already read a collection that way. The GUI renders a badge
per specialization instead of only the first.

**Boundary narrowing, stated.** The ArchiMate exchange format names at most one specialization, so an
export of a concept carrying several emits the primary. The others stay in the repository; a round trip
through the exchange format cannot preserve them.

### `POST /api/identifiers/allocate` no longer accepts `owner_kind`

It was in the published schema, hard-coded to its only possible value by both callers, typed as that
literal in the frontend port — and **never read by the handler**. A parameter with no effect. Removed,
with the dead `_AllocateRequest` class beside it, a leftover from an earlier signature.

`diagram_type` and `entity_type` both remain required, and the docstring now says why they are a
composite key rather than alternatives: the entity type must be one the *named diagram type* owns,
workspace-scoped, with an `id_prefix` declared in its ontology. "classifier" is only meaningful as the
classifier type of the datatype diagram type.

### `dry_run` defaults to `true` on every write

It already did on 25 of the 29 write operations. The three document routes and
`DELETE /api/viewpoints/{slug}` defaulted to committing, so one flag meant "preview" on most of the
surface and "commit" on the rest. A client that omitted it on those four now gets a plan; pass
`dry_run: false` (body) or `?dry_run=false` (query) to commit.

### Document writes: 404 for an absent artifact, 400 for a malformed payload

The write raised a bare `ValueError` that no route caught, so naming the wrong address produced a
non-disclosing `500` — the one status a caller can neither retry nor correct on.

### A rejected viewpoint parameter no longer carries a retired code word in its `message`

The 0.2.0 notes said the finer distinction "still appears inside the `message`"; it does not any more.
`"parameter-type-mismatch: anchor"` is now `"anchor: expected entity-id, got boolean"`, on REST and MCP
alike. Branch on `detail.code` (`validation_error`) and read the parameter from
`details.field_errors[].field` — or `path` on MCP.

## Additive

### `/docs` gains section views

`/docs/architecture` (104 operations) and `/docs/assurance` (62) render the one OpenAPI document
filtered by tag, with `/openapi/architecture.json` and `/openapi/assurance.json` beside them. The
document is 136 paths, 166 operations, 391 schemas — about 874 KB — and `/docs` renders all of it.

**Views, not separate documents**, deliberately. One document is load-bearing: `contracts.mjs` dumps it
to a single file, generates `openapi.generated.ts` from that, and `contracts:check` holds the
hand-written Effect schemas against it. Splitting the contract would fragment that pipeline and force a
decision about which document owns each of 391 schemas, many of them shared. It is also one service on
one origin with one auth surface and one error vocabulary, so a partition would not correspond to
anything. `architecture` is defined by *subtracting* the assurance tags, so a future section joins it
without anyone editing a list.

### Every operation carries exactly one tag, and the assurance surface subdivides

**59 of 166 operations published no tag** — the whole assurance module, plus sync, promotion and the
event stream — so a third of the surface sat under an unnamed "default" heading. The assurance surface
now has six sections along the sub-routers it already composed (`store`, `analyses`, `nodes & edges`,
`FMEA`, `arguments`, `security signals`), because one tag would have held 62 operations, twice the next
largest.

Tags are declared on the router and held by `tests/architecture/test_openapi_tags.py`: exactly one tag
per operation, from a closed vocabulary, no declared tag unused, no section past a size a reader can
scan. Not derived from the route-policy manifest, though that was the first plan — the manifest's row
groups and the documentation sections genuinely disagree in about ten places, and deliberately: the
three search operations are grouped together for *addressing* and want tagging by the artifact kind
each one searches. Addressing and documentation are different concerns over the same operations.

## Fixed

- **Security-signal ingest could not anchor outside the working directory.** `anchor_reader_for`
  resolved the architecture model from `Path.cwd()` and honoured neither `--repo-root` nor
  `ARCH_REPO_ROOT`. A deployment that runs from its workspace was unaffected, which is why it went
  unnoticed. Two configurations were not: with roots configured and no workspace config — a mode
  `docker/entrypoint.sh` supports explicitly — nothing lies at or above cwd, so
  `UnavailableAnchorReader` reported every anchor unknown and **every `POST
  /api/assurance/arch-artifacts/{id}/security-snapshots` was refused** for entities that plainly
  existed. With a *different* workspace at cwd, resolution succeeded against the wrong model and
  refused an entity belonging to the repository being served. It survived because both ingest suites
  monkeypatch the resolution away.
- **A domain card on Home opened the last-browsed collection.** `/api/stats` is repository-wide, so a
  card's count is every entity in that domain; the link carried only `?domain=` and `EntitiesView`
  fills an absent `?group=` from the collection last browsed. Clicking Motivation after working inside
  a project showed that project's motivation entities, usually none of them. The restore is right and
  stays — `NavBar`'s browse link and `EntityDetailView`'s back link rely on it — so the fix is a
  `?group=all` value a link can use to mean "every collection", which an absent parameter cannot.

## Internal — no adopter-visible change

Recorded because the release contains substantial work whose value is in what it *prevents*.

### The dark-operation register is empty

`NEVER_REQUESTED_OPERATIONS` recorded the REST operations no running server had ever answered `2xx`
for. The last 38 entries were the whole `/api/assurance/*` surface, dark for one precondition rather
than 38 reasons: each needs the confidential store unlocked, and the only unlocked store on a
developer machine holds real analyst evidence.

`fixture_workspace` now builds a disposable SQLCipher store — created by the product's own
`arch-assurance` CLI in a child process, keyed into a throwaway Fernet vault inside the fixture, with
its own settings document so the activation policy is `persistent` and a walk does not meet a `423`.
The 38 operations are requested by `rest_write_walk.py` (17 steps) and `rest_read_walk.py` (21), and
the `assurance-write` MCP mount's 22 tools are invoked over their own transport. `UNWALKED` and
`KNOWN_DEFECTS` are empty too.

Three harness lies surfaced on the way, none visible to a status assertion:

- `_answers.refusal` knew `wrote: false` and `ok: false`; the assurance mount refuses with a bare
  `{"error": …}`, so a refused FMEA write reported itself green. Fourteen cases now hold the detector
  in both directions.
- The FMEA matrix answered `rows: [], count: 0` for want of a `binds-to` reference from a
  control-structure node, so a judgement had no basis digest to pin itself to while every read
  answered `200`.
- A security advisory that matches no component is recorded as *unmatched*, not refused — so a
  malformed advisory produced a snapshot with components, no findings, and eight security reads
  answering `200` over nothing.

### The browser suite refuses to run against a stale backend

`reachablePreflight.ts` already refused a run when `dist/` was not the working tree's, on the grounds
that "every test would have passed or failed against code you did not write". Nothing did the same for
the **backend**. A server left running across a contract change serves the old field names while the
freshly built SPA decodes the new ones, and twenty tests report GUI defects that do not exist — which
cost an 8.8-minute run during this release. `staleBackendReason` compares the served component schemas
against the tree's and names the command that fixes it.

### Every commit subject names its area, and a fitness function keeps it that way

`Area: clause`, where the clause completes "When applied, this commit will …". The prefix is what makes
`git log --grep '^Assurance:'` answer "what has happened to this concern" over a hundred commits, and it
works only while one concern has one name. The convention was written down nowhere and checked nowhere,
so it lapsed for 81 consecutive commits — the whole of 08-02 and 08-03 — while the preceding 68 kept it.

All 149 subjects in `v0.1.0..HEAD` were rewritten: the 81 gained a prefix, and the 68 that carried one
had noun-phrase labels turned into instructions ("REST: typed contracts for the platform reads" →
"REST: type the contracts for the platform reads"). Bodies and trailers are byte-identical and every
tree is unchanged. The vocabulary in `AGENTS.md` is the one the history already used, extended only
where a real concern had no name; `tests/architecture/test_commit_message_convention.py` holds the shape
and the area set, and skips rather than passes where the tag is unreachable.
