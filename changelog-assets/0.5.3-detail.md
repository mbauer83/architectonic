## A decorated declaration was invisible to the writer

**Symptom.** Authoring an ArchiMate view that draws `function → junction → function` failed
verification with **E315**: *diagram body draws entity alias 'JNA_zGOowi' … which is listed neither in
entity-ids-used nor in diagram-entities*. The alias is the junction's real `display_alias`, the
junction is a model entity, and its connections resolve — both were recorded in
`connection-ids-used` by their real ids. Only the entity was missing.

**Reproduced on 0.5.2, in this repository, with `dry_run`:**

| Body | `entity-ids-used` | Verdict |
| --- | --- | --- |
| `circle " " as JNA_zGOowi #252327` | junction **absent** | E315 |
| the same body, colour removed | junction present | **clean** |
| `rectangle "…" as FNC_erPw5B #E6F3FF` | function **absent** | E315 |

**Cause.** One regex, in the reader that derives `entity-ids-used` from a body:

```python
re.search(r"\bas\s+([A-Za-z0-9_-]+)\s*\{?\s*$", stripped)
```

The alias had to **end the line**. A junction is drawn as a coloured circle, so the trailing colour
hid the declaration — while the verifier, which resolves *drawn* aliases against every entity's
`display_alias`, saw it perfectly well and refused the diagram for omitting it. Two readings of one
syntax, and the disagreement was the defect.

The product's own renderer appends a `color_suffix` for any entity carrying a specialization notation
colour, so this was never confined to hand-authored bodies.

## Why the first diagnosis was wrong, and why it matters

The first diagnosis named a type or domain filter excluding the two junction types, and proposed
including junctions "wherever any other entity type is included". Acting on that would have produced a
junction-shaped fix for a defect that is not about junctions: a coloured **rectangle** fails
identically. `resolve_diagram_selection` handles junctions explicitly and correctly, including the
rule that a junction is pulled in only when its whole neighbourhood is present.

Its second symptom, **E317** on junction-sourced edges, is **not reproduced** by this mechanism and is
deliberately not claimed as fixed. Against a decorated body the connections were recorded correctly and
only E315 fired; the E317 seen in one probe here was correct behaviour, for a pair that genuinely had
no model connection. Whatever produced the observed E317 is a separate question — most likely the
re-derived list left behind by the no-`puml` edit their own report describes.

## An explicitly passed `entity_ids` was discarded

`artifact_create_diagram` routed on `if entity_ids and not puml:`, so a caller who supplied **both** a
body and the ids it draws had the ids **silently dropped**, in short or full form. That is the report's
cases B and C, and it is worse than a refusal: nothing told the caller the diagram they had just
written could not verify.

Now membership is honoured — the ids are expanded to full form and merged with what the body infers.
`connection-ids-used` is deliberately left to the body: that list records what is *drawn*, and only the
body can say what that is.

## Five readings of one syntax

There were **five** parsers of "this line declares an alias", and each knew something the others did
not:

| Reader | Alias must end the line | Hyphen in alias | Strips quoted labels |
| --- | --- | --- | --- |
| `artifacts/parsing.py` — derives `entity-ids-used` | yes | yes | no |
| `puml_grouping_parsing.py` | yes | **no** | no |
| `puml_relation_parsing.py` (container) | yes | yes | no |
| `puml_relation_parsing.py` (leaf) | yes | yes | no |
| `modeling/artifact_write_layout.py` | **no** | no | **yes** |

The tolerant reading already existed, in the layout preserver. The quoted-label care existed in exactly
one place, so the other four read `"AI-Assisted Development as Dominant Production Mode"` as declaring
an alias named `Dominant`.

`src/application/puml_alias_declarations.py` is now the one reading, carrying the union: anything may
follow the alias, quoted text is not code, a hyphen belongs to an alias, and whether the line opens a
containment block is a separate question the caller asks. All five call sites were migrated. Two
latent defects went with it — a *coloured container* was neither container nor leaf, so its nesting was
lost, and a coloured grouping-open matched nothing, so its label was lost.

## Why 10,031 tests missed it

1. **`infer_entities_from_puml` — the function that derives `entity-ids-used` from a body — had no test
   at all.** It was referenced only from `src/`.
2. **Every hand-written test body uses `as ALIAS` or `as ALIAS {`.** Not one puts anything after the
   alias: the tests were written from the same mental model as the parser, so they shared its blind spot.
3. **Nothing round-tripped the renderer's output back through the reader.** That is the gate that would
   have failed the day `color_suffix` arrived.
4. The 20 test bodies that *do* carry a trailing colour are all diagram-owned types (bowtie, C4, GSN,
   sequence, datatype), whose entities live in `diagram-entities` — a path that never consults
   `entity-ids-used`.
5. This repository's own junction diagram declares its junctions **without** colour, so the 969-file
   verify walk never exercised it.

**A caution recorded because it nearly shipped.** The first version of the new round-trip gate *passed
against the broken reading*: the shipped specialization catalogue declares no colours, so a round trip
over what the renderer emits today proved nothing. It was caught only by neutering the fix and
re-running. The gate is now stated over what the syntax **permits** — a decoration cross-product over
the whole entity-type catalogue — and verified to fail: **178** of its assertions go red on the old
reading, plus 3 of the 5 write-path tests, one per defect.

## The register, and the debt it names

The lesson had been learned three times and fixed three times, each as an instance with its own test
naming its own owner: 77 `yaml.safe_load` call sites, fourteen frontmatter readings, and now five alias
readings. Six such single-owner gates exist, 750 lines of them, and between them they enumerated
nothing — so "who reads a PUML declaration?" had nowhere to be a *missing row*.

`tests/architecture/test_each_syntax_has_one_reader.py` is that place. Each row names the syntax, its
owning module, what to call instead, and the incident that earned it. Two detectors, because a second
reader announces itself two ways: a **reserved name** in its own namespace (`yaml.safe_load`), or a
**literal probe** on a pattern handed to a locating call. Inspecting the call rather than the literal is
what keeps a renderer that *writes* `as ALIAS` out of it.

Four syntaxes are registered. Two are fully clean. Two carry named, **shrink-only** exemptions:

| Syntax | Owner | Exempt |
| --- | --- | --- |
| frontmatter block | `domain/repository/frontmatter.py` | — |
| YAML document | `domain/yaml_documents.py` | — |
| PUML alias declaration | `application/puml_alias_declarations.py` | 1 |
| connection-declaration section | `domain/repository/connection_declaration.py` | 5 |

**The register earned its place on the first run**, and the measuring mattered twice. It reported
eleven second readers of the connection-declaration section; two were false positives — a probe that
also matched a bare `###` heading had flagged the *display-block* readers (`### archimate`), which have
nothing to do with connections. The probe now requires the arrow, because that is what makes a section
a connection. Of the eight real ones:

- **three are converted here.** `connection_header_matches_shape` asked only for a ` → ` with
  non-empty sides, so it called a header valid that the parser then declined — a shape check and a
  parse disagreeing is how a section reads as present to one half of the verifier and absent to the
  other. The other two hand-rolled the `[multiplicity]` stripping the parser already does, which was
  the same seven lines a third and fourth time;
- **three rewrite files and stay exempt**: cascade delete removes the sections naming a deleted entity,
  promotion retargets a header in place with `re.sub`, and cleanup counts and strips broken ones. The
  owner exposes *parse* and *format*, not "retarget a declaration" or "remove those naming X".
  Converting them means designing those primitives onto the aggregate, and getting one wrong corrupts
  model files rather than failing a test — its own change, with its own tests;
- **two read the standalone reference form**, and following that thread found a third and a worse
  problem — see below.

The budget is asserted, so a ninth cannot arrive by being added to a list.

## The transposed tuple

The two readers set aside as "a different syntax" turned out to be `parse_connection_ref_id` and
`parse_connection_artifact_id` — the *same function under two names*, byte-identical including the
comment about hyphen-terminated keys. Following them found a **third**, `_parse_conn_full` in the
promotion planner, and the three did not agree:

| | bulk / sync | promotion planner |
| --- | --- | --- |
| arrow split | `split(" → ", 1)` — first arrow | `rsplit(" → ", 1)` — last arrow |
| **tuple order** | `(source, target, type)` | `(source, type, target)` |
| whitespace | not stripped | `.strip()` on each part |
| malformed canonical id | `None` | falls through to the arrow branch |

Three functions parsing one string into a three-string tuple, two of them with **target and type
transposed**. Nothing would have caught a caller being moved between them: both halves type-check, both
read correctly at the call site, and the values are strings either way. The existing test for the third
asserted its order positionally, so it documented the divergence rather than exposing it.

`artifact_id.parse_connection_reference` is now the one reading, and it answers a
**`ConnectionReference` record** rather than a tuple — so the transposition is not merely fixed, it is
unspellable. The resolved contract is stated where it lives: the *first* arrow (an artifact id contains
no spaces, so a well-formed reference has exactly one, and for a malformed one either answer is equally
arbitrary — this one is chosen rather than incidental), parts stripped, and a malformed canonical id is
`None` rather than falling through, since a string carrying `---` and `@@` was making the canonical
claim. All four call sites and the two positional test assertions were updated.

The register carries this as **one row with two owners**, which is the truthful shape: the arrow serves
two syntaxes — inside a `###` section, and standalone — and a literal probe cannot see the `###` that
distinguishes them. Split across two rows, each flagged the other's owner; cross-exempting them would
have put two non-debts into a budget whose only value is that it holds debt.

`AGENTS.md` now carries the rule this register serves: name the owner before writing a parser, and
where the project both writes a syntax and reads it back, test the *pair* — over what the syntax
permits, and verified against the old behaviour before it is trusted.
