## One machine, several workspaces

This part is about one defect and the concept that was missing behind it: **a backend had no identity,
so every local client identified one by the port it answered on.**

## What happened

Two checkouts of this project sat on one machine, each with its own engagement repository, each
shipping `config/settings.yaml` with `backend.port: 8000`. The first workspace's backend took the
port. An agent then worked in the *second* workspace, whose MCP bridges did this:

1. resolve the preferred port — 8000, from the settings document every clone ships;
2. probe `http://127.0.0.1:8000/api/stats`, get a 200;
3. conclude "the backend is already running" and bridge every tool call to it.

For a whole session, `artifact_query_stats`, searches, neighbourhood walks — and any write that had
been made — addressed the first workspace's model. Nothing failed. Both backends answer correctly;
they answer *about different repositories*. The tell was subtle enough to survive a full session: the
`repo_roots` field in a stats response named a path in the other checkout.

The same assumption was in four more places:

| Surface | What it did |
| --- | --- |
| `arch-backend --status` | reported a neighbour's backend on port 8000 as this workspace's, running |
| `arch-backend --stop` | matched processes by port, so it would have signalled that neighbour |
| `arch-backend` start | refused to start at all ("port already in use"), so a second workspace could not run |
| `arch-write-cli` | trusted a recorded port, so a *write* could reach a repository nobody named |
| `arch-assurance unlock` | posted `authorize: true` to the configured port — authorizing a *neighbour's* backend to open its own confidential store |
| `npm run dev` | proxied `/api` to a hardcoded `127.0.0.1:8000` |

## What the fix is

The identity already existed. `GET /api/backend-identity` publishes the realpath-normalized roots a
backend serves, and `arch-repair upgrade --commit` already consulted it — it refuses to rewrite a
repository a backend is serving, and fails closed when it cannot confirm. What was missing was that
nothing else asked. So:

- **`BackendIdentity` moved to the domain** (`domain/deployment/backend_endpoint.py`) and its probe
  moved next to the other backend probes. The upgrade guard now imports both rather than carrying its
  own copy — two answers to "what does this backend serve" would be two things to keep true, and a
  fitness test in `tests/infrastructure/test_repository_upgrade_guard.py` holds them as one.
- **A pure planner decides the endpoint.** `plan_endpoint` takes a workspace's claim (its resolved
  engagement and enterprise roots), a port preference, the port this workspace last recorded, and an
  observer; it returns `AttachToBackend`, `StartBackendOn`, or `RefuseEndpoint` with a reason. Because
  observations are supplied by the caller, every process state a machine can be in is reachable in a
  test without a socket — see `tests/domain/test_backend_endpoint_plan.py`.
- **A port's authority decides whether it may be yielded.** `--port` and `ARCH_BACKEND_PORT` name this
  run; `backend.port` in `arch-workspace.yaml` names this workspace. All three are statements: if
  something else holds one, the command fails and names the occupant. `config/settings.yaml` ships the
  same value in every clone, so it is a preference — a second workspace moves to a port derived from
  its own repository paths (8100–8499, deterministic, so a restart returns to the same address).
  Without that distinction there are only bad options: either two checkouts cannot both run, or a
  stated port moves silently under the operator.
- **Ownership is a positive statement, never an absence.** A backend that will not say what it serves,
  or a workspace that cannot state a claim, yields "cannot confirm" — which never counts as ours. A
  status report, a stop request, and a write all fail closed on it.

## Choices worth recording

- **The fingerprint is over the repository roots, not the workspace directory.** Two directories
  configured to serve the same repositories are one instance, and sharing a backend between them is
  correct. It also means moving a checkout does not change the address its backend lands on.
- **`ARCH_MCP_BACKEND_URL` is still not identity-checked.** A container publishes the paths it sees
  inside itself, which never match a host workspace's; gating it would refuse every legitimate remote
  deployment. Naming a URL is the decision, and the log records what that decision reached.
- **A start no longer aborts because the port is busy.** That refusal was the reason a second
  workspace could not run at all. The plan relocates instead — and says which port it left and why.
- **Serving our engagement repository under a *different* enterprise tier refuses rather than
  attaches.** It is a real configuration conflict, and working around it silently would mean writing
  promotions into a tier the operator did not configure.

## Where it is tested

- `tests/domain/test_backend_endpoint_plan.py` — the decision matrix: nothing running, our backend on
  the preferred/derived/recorded port, a neighbour holding the default, a non-backend occupant, a
  backend that will not identify itself, a stale record, a record another instance took over, a stated
  port taken, an exhausted range, an enterprise conflict, and a workspace with no claim.
- `tests/tools/test_backend_multi_instance.py` — the same states through `ensure_backend_running`,
  `backend_status`, `stop_backend` and the stdio bridge, plus four tests over **real sockets** with no
  probe stubbed: two fake backends on two ports, each workspace reaching its own.
- `tests/tools/test_model_write_cli.py` — a write is not sent to a backend that does not serve the
  named repository.

## What an agent-facing reply costs

`artifact_bulk_write` returned one object per item, and the tool most likely to be called with fifty
items is this one. Each of those objects repeated the batch's `operation_id`, and carried an absolute
`path` derivable from the artifact id, its group and its type. Neither is per-item information.

The reply also did not echo `_ref`. The tool documents that items auto-sort — creates, then
connections, then edits — so a caller correlating its alias to the allocated id had to assume input
order survived that sort. It does, today. It is not something the tool says, and it is the only thing
most callers need from a successful create.

Why this outranked verbosity as a defect: the server already treats reply size as a design property.
`artifact_verify` takes `return_mode`, `artifact_query_list_artifacts` takes a field projection,
`artifact_query_viewpoint`'s own description says its limit "defaults small to protect context". Bulk
write was the outlier on the surface whose primary caller is an agent.

**One shape in every mode.** `return_mode` decides how much `items` carries, never whether the reply
is a list or an object — a caller that must branch on the mode to find the ids has been handed a
second contract rather than a smaller one. `summary` is the default, matching `artifact_verify`: a
clean fifty-item batch answers with its counts and its alias map and no items at all.

The registry keeps the batch **complete** whatever the caller asked to see, which is what lets a
replay under an idempotency key be re-shaped: a key names one logical batch, not one verbosity. A
stored summary could never be widened back.

Not addressed here, and worth its own change: `artifact_query_viewpoint(action='execute')` bounds its
`limit` per entity rather than per payload, and carries no styling — so the verdict a coverage
viewpoint exists to produce (realized against unrealized) is not available through MCP at all and has
to be recomputed from `connection_ids` by hand.

## Guidance that taught the wrong method

`assurance_guidance('stpa-ucas')` taught the Handbook's four guidewords. The ontology, the UCA matrix
columns, the wizard, the attribute-schema enum and the store migration had all moved to the five in
`domain/assurance/uca_guidewords.py`, where guideword 2 is split because "providing causes a hazard"
conflates a well-formed command in the wrong state with a wrong command in the right one — different
findings, different constraints.

Guidance is the one surface whose errors are invisible to the software: nothing downstream reads it, so
no check reported that an analyst was being told to fill four columns of a five-column matrix. The text
is now composed from the vocabulary, and a test holds the two together — including the failure
guidewords, which were latent rather than wrong.

`loss-scenario` is a full node type carrying both Handbook scenario classes (`scenario_type`
`unsafe-control` explains UCAs, `improper-execution` explains a hazard with no UCA involved), and it
had no guidance topic. That is the step where the analysis stops auditing its own register and starts
asking why any of it would happen.

The step numbers also disagreed with themselves: the guidance numbered constraints 5 and had no
scenarios, while `docs/04-assurance/methods.md` and the ontology both put scenarios before the
constraints they derive. Scenarios are 5, constraints 6, and every STPA answer now carries the mapping
onto the Handbook's four steps — six against four reads as a miscount until it is said.

## A metric that shaped the model

`motivation-coverage` quantifies universally over a row's branches, and enumerates those branches over
**direct stored edges only** — deliberately, because derived relationships would collapse or bypass the
branches the view exists to count. An aggregate goal has no realization of its own: it is realized
through the goals it aggregates. So enumeration from an apex found nothing, and "nothing" is
`missing-outcome`, which the semantics define as always a gap.

The consequence is the part worth recording. The only way to keep such a view green was to attach a
direct realization edge to the apex — which is a metric shaping the model rather than measuring it, and
the reason this was reported as a defect rather than a preference.

**Why the declarative grammar could not express it.** Branch keys are data, so a new branch was
declarable; quantification is not. Adding a `goal_to_subgoal` branch would have made aggregation
mandatory for *every* goal, failing every leaf goal that aggregates nothing. A `StoredEdge` is one hop
with one connection, one direction, one endpoint type — the grammar has no disjunction, so "either
realized directly, or all constituents covered" cannot be said.

**What was added instead.** A `rollup` edge, which is not a branch:

```yaml
rollup: {kind: rollup-edge, connection: archimate-aggregation, direction: outgoing, endpoint: {type: goal}}
```

It redirects enumeration rather than adding a quantified branch. A row with constituents bears no
missing-* obligation of its own and carries its constituents' obligations — under the *existing* fixed
universal quantification, that already reads as "every constituent is covered". No new quantifier, and
no second way to express one chain. Design points:

- **Declared, not inferred.** Which connection means whole-part differs by chain, and a hidden
  traversal is not reviewable. The endpoint type must be one the pattern already reports on: a descent
  into another type would be a second chain expressed as a composition rule.
- **Union, not either/or.** A branch the aggregate *does* have stays its own to satisfy. So a direct
  realization edge onto an apex can now only *add* an obligation — the incentive that shaped the model
  is gone, rather than merely unused.
- **It travels with `{ref:}` expansion**, like the branches and unlike the leaf. Otherwise the
  authoritative `overall_realization` pattern would still report the gap that the branch-completeness
  pattern had just stopped reporting: one view disagreeing with itself about one row.
- **Obligations are not retagged** on the way up, so a report names the constituent that is bare.

**The silent no-op this nearly shipped as.** The construct was declared, parsed, validated and
unit-tested — and did nothing against the real model, because `_referenced_connection_types` built the
graph index over branch, shortcut and leaf connections only. With no adjacency for
`archimate-aggregation`, every constituent lookup answered empty. Nothing failed: the unit tests each
supplied their own index with aggregation in it, and against the self-model the apex passed for an
unrelated reason. It surfaced only when the shipped viewpoint was executed against the real repository
and the verdict was right for the wrong reason. There are now end-to-end tests that run the real use
case, and the index derives its adjacency from the rollup as well.

### The self-model's own apex edge

The report asked whether the direct `outcome --realizes--> apex` edge in this repository exists on its
merits or to satisfy the metric. Established: on its merits.

- It is **not derivable** from any constituent. That outcome's other realization target,
  `Maintain a Coherent, Traceable Architecture Model`, is *associated* with the apex as a cross-cutting
  concern, not aggregated by it — so the apex realization is an independent claim, not a shortcut of a
  constituent's.
- It carries a stated one: "governance scaling without proportional overhead is the observable
  realization of unity of effort at agentic scale."
- `STD@…nNCIH_` (Motivation-Layer Modeling Conventions) reserves realization for outcomes realizing
  goals, with no prohibition on aggregates.
- Under the union rule the edge can no longer buy a greener row, so keeping it cannot be
  metric-motivated.

Executed against the self-model, the apex is still a gap — but now because three of its constituents
have outcomes with no requirements, and the report names those three rather than the apex.

## Junctions were a dead end

Two independent refusals, one symptom. `compose()` opened with `if "junction" in intermediate.classes:
return None` — no rule behind it, no comment. And had that been removed on its own, nothing would have
changed, because `RJ1` refuses a second time: it requires an intermediate's domain to match an
endpoint's, and `derivation_domains` puts a junction in `relationships` *precisely because* it stands
for a relationship rather than an element. That domain never equals an endpoint's, so every
junction-mediated derivation was disallowed.

What made it invisible is that the coverage leaf's eligible-realizer set deliberately excludes
`and-junction`, `or-junction` and `grouping` as structural helpers — correctly: a junction realizes
nothing. So a requirement realized through an AND-junction found exactly one realizer, the junction,
found it ineligible, and reported the requirement unrealized against a model that was right. Impact
analysis stopped at the same wall.

**A junction is one relationship, split or joined.** So there is nothing to weaken and no chain to
compose: both legs carry the same type, and the same type comes out between the real endpoints,
*certainly*. That last word is the distinction from a grouping, whose members only potentially carry
the whole's relationship — which is why `PDR12` is declared `potential` and this is not.

Three things this exposed about how the change had to be made:

- **The first attempt put the semantics in code**, and two fitness functions caught it: the suite
  encodes "every derived result corresponds to a declared composition rule, with that rule's certainty",
  and a hand-written path satisfies neither half. The rules are now four `RJ3` rows in
  `relationship_derivation.yaml` — one per derivation role, made exhaustive by
  `requires_same_connection_type` — matched by intermediate *class*, since `and-junction` and
  `or-junction` differ in what the combination means and never in how a relationship passes through.
- **Removing the blanket guard opened a hole.** With junctions merely un-refused, the ordinary chain
  rules applied to them, and `assignment` then `serving` across a junction derived a serving the model
  never stated. One invariant closes it: a junction intermediate is composed only by a rule that
  declares junctions.
- **The independent transcription had to learn the same dispatch.** `derivation_rules_independent_encoding.py`
  is a second encoding of the rule table compared against the runtime one, and the exhaustive test has
  its own matcher; both now model `intermediate_class`, `requires_same_connection_type` and the
  junction-exclusivity invariant. Two implementations of one spec, still compared.

## What a junction may carry

The other half of the same subject, and it is an authoring rule: **a junction's admissible types are
the intersection of what its participants permit.** Derivation cannot repair this after the fact. The
type table lets `@junction` carry all eleven types in both directions and *has to* — which type is
admissible depends on which other elements that junction instance joins, which is not a property of
either type. So the model could assert through a junction what it may not assert directly:
`function --assignment--> J --assignment--> function` was accepted while `function --assignment-->
function` is refused, and now that derivation passes through junctions, that acceptance produces a
derived relationship the ontology forbids.

Two diagnostics, reported against the file that declares the offending leg, and refused at the write
boundary before the leg reaches a file:

- **E128** — the legs of one intermediate do not agree on a relationship type;
- **E129** — the type it carries is not permitted between every upstream and every downstream
  participant.

Three things worth recording about the shape:

- **The rule is `RJ3`'s own words, read back.** `requires_same_connection_type` and
  `requires_permitted_result` are already declared there, so restating them in a verifier would hold a
  second copy of a rule the ontology owns. `relationship_mediation.py` reads them off the rule, and
  what selects an intermediate is *certainty*: a certain result means the model asserts the derived
  relationship, so its legs answer for it. A potential rule (`PDR12`) asserts nothing, so a grouping
  aggregating a member that could not itself realize what the grouping realizes stays a legitimate
  model. No junction vocabulary appears in the rule at all.
- **The write path already had a weaker copy.** `_check_junction_homogeneity` read the junction's own
  `.outgoing.md` and refused a second type found *there* — so a mismatched leg declared in a
  participant's file was invisible to it, as its own docstring admitted, and admissibility was never
  asked. One rule now serves both the refusal and the diagnosis, which is why they cannot say
  different things.
- **A junction's legs live in as many files as it has participants**, so a per-file check cannot see
  them: each participant's outgoing file declares its leg *into* the junction and the junction's file
  declares the legs *out* of it. The check runs per declaration but resolves the rest through the
  graph, which keeps the error on the file that can fix it — and reports only the pairs that leg takes
  part in, not the junction's whole cross-product.

A fixture defect surfaced on the way: one write-path test wrote `artifact-id` where an outgoing file
carries `source-entity`, so every connection it planted indexed with an *empty* source. Nothing
noticed while the junction rule read the file itself instead of asking the graph.

## A staging tree that could not be listed

A rename rewrites every file that names the entity, in the same transaction as the rename itself —
keyed on the `PREFIX@epoch.random` stem, so a referrer holding any older slug heals rather than
becoming permanently unreachable. That has been right for a long time, and its tests passed.

Through `artifact_bulk_write` it did nothing at all.

A batch stages its writes: `create_staging_repo` makes an **empty** directory and installs guards, so
a guarded write, unlink or rename symlinks the live file in first and copies it on write. Reading a
*named* path therefore falls through to the live repository. Listing a directory does not — there is
nothing there to list. Every operation that discovers its own work by enumerating saw an empty
repository:

- `plan_referrer_rewrites` globs `*.outgoing.md` across the model roots → no referrers;
- `rewrite_document_links_for_moved_entity` globs `docs/**/*.md` → no documents;
- `all_model_roots` returns *existing* directories only → inside the staging tree, almost none.

So the entity was renamed, its own sidecar moved with it, and every other file kept the old slug —
silently, because a stale slug still resolves and only a warning (W121) notices. Two agents hit this;
the failure looked like "the cascade does not work", while the same rename outside a batch was correct.

**The overlay owes callers a listing.** `overlay_paths(root, patterns)` yields the union of staged and
live matches as paths under *root*, symlinking each listed entry in so it can be read, and skipping
what the transaction has deleted — so an enumerating operation writes into the staging tree exactly as
a naming one does. A lazy overlay that answers point reads but not listings is not a repository view;
it is one that happens to work for callers who already know every path they need.

Two smaller things fell out of the same investigation:

- **`Path.resolve()` was the wrong comparison for a document link.** A markdown link is a lexical
  relative path; resolving it followed the staging tree's symlink to the live file, while the
  moved-from path — deleted by the rename — resolved to itself. Nothing matched, so no link was
  rewritten. The comparison is lexical now, which is also what a link means.
- **An operation must report every path it wrote.** `clear_repo_caches` is how an enclosing
  transaction learns what to carry out of its staging tree, and the M4 rename branch reported four
  paths on the grounds that "referrers were committed inside the same transaction" — true of the inner
  commit, false of the outer one.

What was *not* wrong, having been checked: the cascade covers referrers in other projects' model
trees, diagram sources, and the single-entity, REST and bulk write paths all go through the same
`edit_entity`. The enterprise admin surface does not rename at all.

## A field that selected the operation, ignored

Two bug reports arrived from the same batch of authoring work, and they had different causes. This is
the second: `artifact_bulk_write` reported `wrote: true` for a connection removal that never happened.

`artifact_edit_connection` selects removal with **`operation=remove`**. The item said
**`mode: "remove"`** — the word most tools use for this — and bulk ignored the unrecognised field,
fell through to the update branch, re-rendered the file with the connection still in it, and reported
success. The removal path itself is correct: with `operation`, the connection goes, the last one taking
its `.outgoing.md` with it, and a sibling connection keeps its description.

Ignoring an unknown field is only harmless when every field is decoration. Here fields *select the
operation*, so ignoring one silently substitutes a different operation — and the report is worse than
the omission, because a caller that trusts it proceeds. The next operation is the one that fails, with
"already exists", far from the cause.

So each op now declares the fields it accepts, in one table, and an item carrying anything else fails
that item — with the accepted list in the message, and nothing written. Six tests cover both the
refusal and the removals that must keep working, including the file-deletion case and a sibling
connection's description.

## A slug nobody was checking

The third report from the same batch of authoring work: **`artifact_verify` answered 0 warnings while
16 stale entity references sat in `entity-ids-used` across 6 diagrams.** The references resolved, as
they always do — identity is the `PREFIX@epoch.random` stem and the slug tail is a readability hint —
so nothing was broken and nothing was reported. The only part of an id a reader can read was wrong,
which in review is the part that matters.

The connection files had this check from the start: **W121**, "the target resolves but names a slug the
entity no longer has". It reached `.outgoing.md` files only. Nothing looked at a diagram's frontmatter,
so the drift was invisible for exactly as long as nobody went looking — and a rename that heals the
connection files leaves the diagrams alone unless something says so.

**Both sides now read one rule**, `current_spelling_of` in `src/domain/artifact_id.py`, beside the stem
and slug grammar it is about. It answers "how is this artifact spelled now" and has three reasons to
say nothing, which is most of the rule:

- **The reference carries no slug at all.** The stem alone is a legitimate spelling — it is the form the
  index keys artifacts under, and the form live diagrams use for `connection-ids-used` — and it names no
  title, so it misleads nobody. Without this, the first run over the live repository reported **506**
  warnings, every one of them a correct short-form reference.
- **The stem is ambiguous.** The engagement and enterprise tiers may both hold it, so there is no single
  current spelling to name and guessing would libel a correct reference. Cross-tier ambiguity is
  diagnosed on its own, by the resolver.
- **The stem is unknown.** That is a resolution failure, reported where resolution is attempted (E301,
  E124), not here.

**A connection reference is read against the *entity* index, not the connection one.** A connection is
keyed by its endpoints' stems and its type — `stable_id` is applied to both ends when the record is
built — so the index holds no slugged spelling of a connection to compare against. What can go stale is
the slug of an endpoint, and the entity index is what knows the current one; the warning names the whole
entry, because that is what a reader has to rewrite.

Two structural notes. `artifact_verifier_rules.py` had reached the 350-line file limit holding three
concerns, so the diagram-reference rules moved to `_verifier_rules_diagram_references.py` — the one with
its own vocabulary — rather than the rule being squeezed in beside them. And `parse_connection_id`
collapses both endpoints to their stable form, which is right for identity and useless for asking how a
reference reads, so the grammar's split now has one home (`connection_id_as_written`) that both answers
are built from.

W121 itself had **no test**. It has one now, beside the diagram-side tests that share its rule.

## One parameter, two meanings

`entity_ids` meant different things on the two diagram tools, and the difference was the trap.

On `artifact_create_diagram` it is the **membership**: the selection is resolved (junctions and their
legs pulled in when every other endpoint is already selected) and the PUML body is generated from it.
On `artifact_edit_diagram` the same parameter only rewrote `entity-ids-used` and left the body alone.

What an agent removing an entity from a diagram therefore got: a successful write, a diagram whose
frontmatter no longer listed the entity, a body still drawing it, and a delete of that entity still
refused because the diagram referenced it. Then `puml="auto-sync"` put the reference back — a reconcile
takes `dedupe(entities inferred from the body + entities listed in frontmatter)`, by design, because a
hand-edited body that *added* an element should have that recorded. The workaround was to delete the
diagram and create it again, losing everything else it carried.

The REST replace route (`PUT /api/diagrams/{id}`) had never had this problem: it resolves the selection
and regenerates the body, which is what the GUI does when a user changes a diagram's entities. So the
fix is not a new behaviour, it is the MCP tool doing what the other two surfaces already did.

**What is now defined.** `entity_ids` without `puml` states the membership; the body is regenerated from
it; `connection_ids` omitted means the connections the model has between those members, not the previous
list (which would keep connections to entities that just left). Passing `puml` *with* `entity_ids` is
unchanged and is a different request — the caller supplies the picture, and reference inference
reconciles the refs against it.

**What is refused, and why refusal rather than a warning.** Three kinds of diagram do not keep their
membership in `entity-ids-used`:

- **model-backed** — a projector draws it from a `scoped-by` binding, so membership follows the model;
- **standalone** — `diagram-entities` is the membership and the body is rendered from it;
- **`manual-layout: true`** — the author has ruled their body better than any regeneration, and sync
  keeps it verbatim, so a frontmatter-only change would be undone by the next reconcile.

For those, a partial success is exactly the failure mode being removed, and a warning is a partial
success that the caller has to read. Each refusal names the operation that does work.

The membership is resolved into the fields the ordinary edit already writes, rather than performed as
its own write, so it composes with everything else one call may carry — a rename, a version bump, a
group move. Doing it as a separate write would have dropped them.

`resolve_diagram_selection` moved to `src/application/diagram_selection.py`. It had lived under
`rest/routers/diagrams/` with nothing HTTP about it, and the write path needs it now; a write op
importing a REST router would have been the wrong dependency in the wrong direction. The MCP create
path's inline copy of "which connections join these members" went with it.

## Boxes the model does not hold

A diagram may draw a labelled box that corresponds to nothing in the model — "Write Requests",
"The Double Bind", "What Is Ultimately at Stake". The label is the whole point: it says something no
element type says, which makes an authored grouping **content**, not layout.

The renderer for this already existed and eight live diagrams used it. Three things were missing.

**It was not reachable.** `grep authored_groupings src/infrastructure/mcp src/infrastructure/rest
tools/gui` returned nothing: only the write *library* took the parameter, so the only way to create a
grouping was to hand-write frontmatter into a `.puml` — which `CLAUDE.md` forbids as a way of working,
and which no verification or rendering runs behind. It now reaches `artifact_create_diagram`,
`artifact_edit_diagram`, both REST write routes, and a Groupings panel in the GUI's authoring flow.

On edit it goes through the same path as a membership change and gets the same refusals: the boxes are
drawn *in the body*, so a diagram whose body is not the generator's to rewrite — model-backed,
standalone, `manual-layout` — is refused with the operation that does work rather than having its
frontmatter changed under a picture that will not follow.

**The look was hand-supplied.** Every declaration carried a `stereotype`, which is a second place to
say what the membership already says, and two places that can disagree. It is derived now:

- all members in one domain → that domain's grouping look, from `grouping_stereotype`, which the
  computed per-domain boxes have always used;
- members from several domains → `<<Grouping>>`, the ArchiMate grouping notation. The generic block
  existed in the generated stereotype include with a white background and a grey border, but **not
  dashed**, and nothing emitted it. It is dashed now and something emits it.
- a subgroup's members count towards its ancestors' domain, because a box is one thing however deep
  it goes.

The domain and the stereotype are passed in by the renderer that owns that vocabulary; the grouping
module names no domain. An explicit `stereotype` still wins, for the deliberate exception.

The audit that justified removing the keys: **28 groupings across the 8 diagrams, every one
single-domain**, and every hand-written value exactly what derivation produces — MotivationGrouping
×24, CommonGrouping ×2, ApplicationGrouping ×2. So the mixed-domain look has **zero** live instances:
it is new capability, not a migration. The four diagrams whose bodies the generator writes have had
their keys removed, so derivation is what runs. The other four are `manual-layout`: their bodies are
kept verbatim by design and hold the stereotype literally, so the frontmatter copy there is a record
of the body rather than an instruction to the renderer, and removing it would change nothing.

**Membership was per entity, not per drawing.** `resolve_authored_members` keyed on the entity's stable
id, so an entity drawn twice — an occurrence, which the renderer already supports with its own
`BASE__n` alias — could not be addressed, and "first declaration wins" was per entity rather than per
drawing. A member may now name an occurrence id; `claimed` is alias-keyed, so one membership per
*drawing* falls out. The id-keyed index also had a latent defect: built by last-write over records that
share an `artifact_id`, it handed the entity id to the *last* occurrence rather than the original.

**And groups are no longer flat**: `groups` nests to any depth, with claiming shared across the whole
tree so a member cannot appear in both a box and a box inside it.

There were **no tests at all** for any of this. There are 19 now, plus 6 in the GUI.

Two file-length extractions paid for the additions, both of them seams the policy's own note describes:
`artifact_delete_entity`/`artifact_delete_diagram` left `edit_tools.py` for `delete_tools.py` — they are
the only two mutations annotated `DESTRUCTIVE_LOCAL_WRITE`, and deleting is not editing — and
`CreateDiagramView.vue`'s preview pane became `DiagramPreviewPane.vue`, taking its scoped styles with
it, exactly as `EntityCreateView.vue`'s did.
