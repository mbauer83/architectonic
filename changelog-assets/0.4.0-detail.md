# 0.4.0 — detail

The short version is in [`CHANGELOG.md`](../CHANGELOG.md). This release adds a tier: a place to think
before anything has been decided, and a way to promote that thinking into ordinary verified model
content when — and only when — it is ready.

## The wall this removes

The typed model asks a contributor to name an element type before they have decided anything. That
question arrives first, it has no good answer early, and the honest response — "I don't know yet" —
is not one the model accepts. So the thinking happens somewhere else, in a document or a whiteboard,
and reaches the repository already shaped, or never.

A scratchpad is that somewhere, inside the product rather than beside it. A note needs only a title.
Nothing needs a type, a domain, a destination or a link. What it buys, that a whiteboard does not, is
that the thinking is already addressable when it is ready: a lift turns a selection into verified
model content through the same write path as any other authoring, rather than through a person
re-typing it.

## One canvas, four frames

Tabs were rejected early. The cross-area links are the content worth having — "this project realizes
that outcome" is exactly the sentence a strategy conversation produces — and tabs would put the two
ends on different screens.

So it is one canvas with four labelled frames: **Vision & strategy**, **Portfolio**, **Project**,
**Enabling**. They are *work archetypes*, not layers, which is why only the first narrows what it
holds: vision and strategy work is motivation and strategy by definition, while portfolio, project
and enabling work each reach across the whole model. A frame declares **domains** rather than type
names, so it keeps meaning the same thing when the ontology gains a type.

Area membership is **spatial and derived** — a note belongs to the smallest frame containing it, and
moving it is what changes its area. That is also why adding anything is a right-click at the point it
will land, rather than a per-frame button that would have to invent a placement rule.

**Focus mode** fits the viewport to one frame and fades the rest back. Nothing leaves the document:
a link crossing out of the focused frame keeps a visible far end, which is the whole reason this is
one canvas rather than four tabs.

## Refinement runs one level at a time

Down the meta-ontology's own classification levels, which modules now declare through
`classification_levels` rather than each consumer hard-coding a ladder. A note narrows to a **domain**
first — a real decision, worth recording and worth showing, and what the note's colour is derived
from — and to an **element type** after. Re-answering the coarser question re-opens the finer one,
rather than leaving a type the new domain may not contain.

A note wears its domain as a wash of that domain's colour and its type as that type's glyph, both
read from the ontology through the same two mechanisms the entity list and the picker already use.
A note and the element it becomes therefore look like the same thing before and after a lift.

## Binding, and why it is not typing

Right-click → *Add existing element…* puts an entity the model already has onto the canvas as a
**bound** note, at the point clicked, scoped to the types that frame permits. It takes its type from
the entity, because the entity is the authority on what it is.

Binding is what makes a scratchpad useful against a repository that is not empty. The common move is
thinking about work that touches things that already exist, and without it a lift would mint a
duplicate with nothing to stop it. One entity binds to one note per scratchpad; two would render the
same element twice and lift as one.

`bound` and `realized` are stored as one field with a flag rather than as two, because the storage is
identical and the difference is entirely provenance: `realized` was created by a lift this scratchpad
performed, `bound` was chosen from content that already existed. Conflating them would lose whether
untyping is free.

## Links get a verdict, in two tiers

A drawn link is typed later or never. Once both ends have types, the ontology answers whether the
relation is permitted, and the answer is served with the link rather than discovered at the write:

- a refusal at the level relationships are keyed on (**E126**) blocks the lift;
- a narrowing by a specialization (**W128**/**W129**) warns and does not.

Both fall out of the ontology's declaration rather than a rule written into the verifier. A refusal
leads with **Reverse the link** when the reverse triple is the permitted one — which is only
offerable because the drawn direction survives typing.

A verdict is **never stored**. It is derived on read, because the ontology may move under a saved
scratchpad and a stored verdict would be an answer to a question nobody asked again.

## Lift is preflighted, and never writes back

A selection becomes ordinary verified model content through `artifact_bulk_write` — the same
operation, the same refusal vocabulary and the same verified write path as any other authoring.
There is deliberately no second route into the model.

The dialog reports four things before anything is written: what would be **created**, what is
**skipped** because it already carries a model reference, what is **refused** and why, and which
links reach a note **outside** the selection. A refusal blocks the whole lift, because the write is
one transaction and half a lift is a state nobody asked for.

A target model-project is chosen **per frame**, not per lift: the frames are work archetypes, so a
canvas routinely holds strategy work for one project and delivery work for another. A frame with no
target lands in the root model. A project is created if it is new; one declaring a different
meta-ontology is refused rather than coerced.

**A lift never writes back.** A note already bound or realized is skipped, never updated. Re-lifting
would be bidirectional synchronisation between a sketch and a governed model, and would clobber
whatever had been edited there since. A second lift therefore creates only what is new — usually the
links between notes lifted before.

## Nothing is permanent until it is lifted

A scratchpad is for thinking, and thinking includes deciding that a note was wrong, that two things
are not related after all, or that a type was premature. So every one of those is reversible, on
every surface:

- a **note** is removed with its links, its group memberships and its placement;
- a **link** is rubbed out, leaving both notes where they are;
- a **refinement** — a domain, an element type, a document type, a link's relation — is taken off,
  and untyping a note untypes every link touching it, because a typed link with an untyped end is a
  claim the aggregate can no longer support.

What removal does *not* do is retract model content. A note whose reference says `realized` names an
entity a lift created: deleting the note removes the *thinking*, and the entity outlives it exactly
as an entity created any other way would. Dropping the reference is how a note stops claiming
something without pretending the lift never happened.

The GUI gained the two affordances it was missing here — a link had no delete at all, and its
*Relation → Undecided* set the type to the empty string rather than removing it, which stored a
relation named `''`.

## One write in two shapes

The resource is the aggregate: there is no note route and no link route, because the root enforces
the invariants and a partial update cannot be validated without loading the whole thing anyway.

`PUT` replaces the aggregate whole. That is right for the canvas, which holds the document in memory
and saves one coherent state — and it is what makes "at most one write a second" a property with a
test rather than an accident of whichever gesture fired last. The collection happens in the browser,
before any request is issued: a server-side debounce would still cost one request per drag, and the
point is that N open scratchpads must not multiply into N × gestures of traffic.

It is the wrong shape for everyone else. An agent removing one note had to read the whole canvas and
send it all back — two full documents to change three lines, a payload that grows with the size of
the thinking rather than the size of the edit, and a wider window for the version to move underneath.

So `PATCH /api/scratchpads/{id}` and `scratchpad_edit` address the **same write** by delta:

```json
{ "version": "0.1.7",
  "remove": { "links": ["l1"] },
  "upsert": { "notes": [{ "id": "n2", "element-type": null }] },
  "layout": { "notes": { "n2": [40, 60] } } }
```

It is not a second door into storage. The delta becomes an aggregate and takes the identical path, so
the invariants, the refusals and the version token are the same code rather than the same intent. Two
rules make it predictable:

- **a patch is a merge patch** — a key left out keeps its stored value, a key set to `null` clears it,
  and an id the scratchpad does not have creates the row. This is the one place the two writes differ,
  and they differ on purpose: under `PUT` the document sent is the whole truth, so omission there
  *is* removal;
- **a removal takes what the aggregate says it takes** — note removal routes through
  `Scratchpad.without_note` rather than restating the cascade, so "remove a note" cannot come to mean
  two different things depending on which surface asked.

An edit that changes nothing is refused rather than ignored, and so is a collection name the document
has no such thing as: a typo would otherwise be a write that reports success and changes nothing.

## Notes in the search index, ranked last

Notes are indexed and findable, and **never outrank model content, documents or diagrams**. A note is
a half-formed thought; an entity is a commitment.

The record type was not reserved in the index schema when it should have been, so this was a schema
change rather than a scoring function: a fifth FTS table, a `ScratchpadNoteRecord`, a
`list_scratchpad_notes` on the store port, and a loader for the only artifact kind whose searchable
units live *inside* another file. A note is addressed as `{scratchpad_id}#note/{note_id}` — the same
shape a diagram already uses for the constructs it owns — and a hit navigates to the canvas it sits
on, because a note is a card rather than a page.

The ranking guarantee could not be delivered by weights. Per-table bm25 and the token-match
supplement are on scales that say nothing about each other, so a low-weighted note and a
high-weighted entity are not comparable. It is delivered by draw order instead: subordinate kinds do
not take part in the round-robin at all, and fill only the slots left once every other kind has had
its turn. A round-robin would have honoured "below" against the *first* hit of each other kind while
still putting a note above the second entity.

The cost is real and accepted: a query whose result window is filled by model content will not show a
note even if the note matched it exactly. A picker never offers notes at all — it offers content to
reference, and a thought nobody has committed to is not that.

While reserving the kind, the searchable-kind vocabulary was consolidated. It had been declared four
times — in `_search.py`, in `artifacts/repository.py`, on `SearchHit`, and again as `KeywordRecordType`
in the REST contract — so the two mappings between its singular and plural forms had no owner, and
`search_fts` carried one boolean per kind through four signatures while its only caller had already
built the set it wanted.

## Parity is arranged, not promised

Parity here is a property of *this feature*, not of the platform: `PRI@1780220699` deliberately
disclaims full parity across every surface, and it is right to — MCP serves agents, the CLI serves
CI, REST serves GUIs. The scratchpad has a local reason the platform does not. It is the
lowest-barrier surface, the place a newcomer starts, so a human-only version would make that the one
place an agent cannot help, which inverts the product's own claim to be for humans *and* AI.

So it is arranged rather than promised. Every capability is a method on `ScratchpadService`; the REST
router and the MCP tools are both thin adapters over it and neither may reach past it. A capability
on one surface and not the other is then a missing *adapter*, which
`tests/architecture/test_scratchpad_surface_parity.py` can see — it compares the two against the
service class, and it is what made `edit` reach both surfaces in the same commit rather than one.

## What the browser suite found

Three defects that 9,700 backend tests, a typed lint and the whole unit suite all passed:

1. **A drag died the moment the cursor crossed the note panel.** The panel is absolutely positioned
   over the canvas's top-left corner as a *sibling* of the viewport, so a drag toward it left
   `.sp-viewport`, `pointerleave` ended the gesture, and the note stopped following the cursor a
   third of the way across its own canvas. Every gesture now takes the pointer with
   `setPointerCapture` and ends on `pointerup`/`pointercancel` — including outside the window, which
   `pointerleave` could not see either.
2. **A lift preflight reported a refusal about nothing.** The plan is computed by the server against
   the *stored* scratchpad while the canvas writes on an idle timer, so notes written moments earlier
   existed only in the browser: "The selection names notes this scratchpad does not have". The canvas
   is now flushed before every lift request, and the document read *after* the flush, since a save
   answers with the version the next request must carry.
3. **A square note had almost nowhere to grab it by.** At 132×120 the title is nearly the whole card,
   and it stopped `pointerdown` so a click would land the caret. The press now propagates and starts
   a drag; a press that does not move still lands the caret.

The second and third were found by specs that were correct as written, which is the argument for not
loosening a spec that fails.

## Four things wrong under the diagram surface

None of these belong to the scratchpad. They were found by using the product rather than by running
its gates, which is the part worth recording: each one had a test suite passing over it.

**A diagram could not be dragged by the boxes on it.** Both viewports refused to pan whenever the
press landed on `[data-entity-id]` or `[data-conn-id]` — a guard that resolves the click/drag
ambiguity by giving up on one of them. The denser the view, the more of it was a dead zone, until
only the auto-created grouping boxes could be moved. The two gestures are now separated by travel
instead: under four pixels is a click, past it is a pan, and the click the pan would otherwise have
produced is swallowed so the picture does not move and the sidebar change at once. Nothing caught it
because the guard was doing exactly what it said; only a pointer on a real render shows that what it
said was wrong. The fix took the model vocabulary out of a generic composable, where it never
belonged, and the same press now also works in the diagram editor, which had its own copy.

**A C4 element was not selectable, and its drill-down badges never appeared.** `entity_id` is
stripped from every item on the way to disk, because the top-level `bindings` block is canonical
there — and nothing put it back on the way out, for any of the three readers that need it. The read
envelope re-hydrates it now. The reason the suite was green is worth stating plainly: every C4
navigation fixture was hand-built with `entity_id` on the items, describing a shape no persisted
diagram has ever had. The replacement builds its fixtures by running an authored payload through the
real normalization and asserting the shorthand is gone before asking navigation to resolve it.

**A crashed render was reported as a success.** A 35-node view across seven boxes made GraphViz throw
out of `DotStringFactory.solve`; PlantUML exited 0, wrote the stack trace into the image, and the
write answered `valid: true` with the crash filed under warnings. It is an **E350** error now. The
`-[hidden]` ordering chains that caused it are dropped above 24 boxed members — they are what makes
a small boxed view read in order, and free only at that size, which is also why every rendering test
had missed it. Separately, `puml="auto-sync"` returned early and silently discarded any other
argument it was handed; it refuses now.

**A network stall was still being reported after the network came back.** `sync_enterprise` records
`fetch_failed` on a fetch timeout but cleared it only when a poll reached a fully grounded state —
a different claim entirely. A poll whose fetch succeeded while its reconcile stopped short left the
block in place, so one transient failure stayed visible across every later healthy poll. A
successful fetch now retires it, decided from the health persisted at that moment rather than from
the state reconcile started with, so a `diverged` this poll raised is not cleared by the same poll.

## What is not here

- **Alternatives per note** — a collapsed stack of variants, exactly one active, only the active one
  lifting. Designed and deliberately deferred until typing and lift were solid.
- **Enterprise scratchpads and promotion.** Engagement tier only, revisited only if asked for.
- **An authored channel for a diagram's direction hints**, which the lift's optional view would use.
  `direction_hints` is only ever computed, and giving a diagram an authored one re-renders every
  committed diagram — a change of the class that has already failed GraphViz layout outright once.
