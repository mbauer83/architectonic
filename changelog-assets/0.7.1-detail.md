## Where a convergent step is drawn

The activity walk had no notion of where a decision's branches meet. Its loop guard was "keep going
until a step has already been drawn", so a branch walked straight through the meeting point and took
the rest of the graph with it. Where the outermost decision enclosed everything, the whole process was
drawn inside one arm and the other arm dead-ended.

`_step_graph` answers where a set of branches converges, and the answer is **post-dominance** rather
than reachability. The distinction carries the fix: a step both arms *can* reach may still be escaped
by a path through one of them, and hoisting such a step past the `endif` would draw it on a path that
never had it. A convergence point is one every branch reaches and that no path out of the branching
step gets past, which is what makes drawing it once, after the construct, faithful. The same rule
serves a fork, whose branches are drawn past `end fork` whether or not the model declares a join step
for them to meet at.

Four shapes, and where each is drawn:

| Shape | Where it is drawn |
| --- | --- |
| both arms of one decision reach it | after that decision's `endif` |
| a fork's branches meet at a declared join | after `end fork` |
| a fork's branches meet at a plain action | after `end fork` — a join entry is not required |
| the arrivals are at different nesting depths | in each branch that arrives at it, along with whatever follows it there |

The fourth is the residue: no placement in an `if`/`else` tree covers exactly those paths and no
others, so the step is drawn in each branch that arrives at it. Both drawings carry the same
`arch://` sentinel, so both are selectable and both resolve to the one artifact — which is what makes
two drawings of one step readable rather than confusing.

Two alternatives were tried and neither survives contact with the viewer. `label` / `goto` would
state the arrival directly, and on the pinned PlantUML 1.2026.3 both are accepted and then ignored: a
backward `goto` draws an arrow to the following node, and inside a branch it leaves a dangling
arrowhead. A flowchart connector pair renders correctly and is unreadable here, because it puts an
unlabelled circle into a surface where every element is expected to be clickable and to resolve to
the artifact it stands for, and the circle resolves to nothing.

What bounds the duplication is that the walk carries the chain of steps it is currently inside: a
step already on that chain ends the walk rather than being drawn again. So a `step-flow` that closes
a loop is **not drawn** — every step of the loop is, which a cyclic diagram did not manage before,
but the edge back has no rendering here yet.

Two further defects in the same walk drew nothing at all rather than drawing the wrong thing. A back
edge leaves no step that nothing enters, so the walk had no root and emitted `start` / `stop` with
nothing between. And the pass over steps the root walk did not reach ran only when there was no root,
so a second declared chain went undrawn; it now runs whenever any step remains.

### What the gate asserts

Every declared step is drawn. No step is drawn more often than what leads to it is drawn, which is
the ceiling that separates a second arrival from the fork multiplication where one tail appeared once
per branch. Every drawing is the step itself, never a connector or a jump. Every branch reaches its
own first step. What follows a join sits where its fork closes. And a step every arm of a decision
reaches is drawn in all of those arms or in none of them, never in some — that last one is a picture
saying one path carries on and the other stops, which is the defect this release exists for.

Coverage is scoped to the step kinds that emit a labelled line, because PlantUML's `fork` keyword
takes no label or link argument, so a fork carries nothing to read back.

Two of the shapes it is stated over exist because a diagram whose forks are all at top level cannot
distinguish a repaired walk from a broken one: appending the leftover steps to the end of the body
lands in exactly the right place. A nested fork and a loop declared from its middle separate them.

`tests/diagram_types/activity_golden_bodies.txt` records the rendered body of every shape, so a change
to the walk is a diff rather than a discovery. The walk moved to its own module in a commit of its
own, with that file as the guard on the move.

## Reading a step's identity back off a line

W045 asks whether a **stored** body draws a declared step. Re-rendering from `diagram-entities` and
comparing would put the renderer against itself and pass on every input, which is the staleness the
diagnostic exists to catch, so it reads the body as stored. Two contracts were completed to allow
that.

`BaseDiagramVerificationContext` now carries the body, filled by the runner from the content the
verifier has already read. The alternative — a contribution re-reading the file from `ctx.loc` — would
spell the frontmatter fence a fifteenth time.

Reading a step's identity back off a rendered line has an owner: `sentinel_of` and `drawn_step_ids`
sit beside the two functions that write it, and `tests/architecture/test_each_syntax_has_one_reader.py`
carries the row. The pair is asserted together over what the syntax permits — both emission forms, an
id carrying the one escaped character, a user link alongside, a step bound to an entity — because a
writer checked against one fixture and a reader against another can agree with nothing.

The diagnostic sees an omitted step, not a misplaced one. Presence is readable off a line; placement
needs the body's nesting, and that reading lives only in the renderer's own gate.

## Reconciling what a diagram says it draws

Both ways a body arrives at an edit — rendered from `diagram-entities`, or supplied as `puml` — ended
by unioning the stored reference set with what the new body draws. Union is right for combining a
caller's own argument with what a fresh artifact draws, and wrong for carrying a stored value across a
replacement. The two were conflated one line above the merge that then could not tell them apart, so
the caller's argument and the file's own value have separate names and only the second is reconciled.

The reconcile is stated once, after both branches, because both hand it the same question. What they
bring differs: a rendered body brings what the renderer drew and nothing it was unsure about; a
supplied body brings what was read off it plus the pairs the reader could not name.

Three things let it be decisive:

- **Inference says what it could not decide.** It was already deliberately silent where a drawn glyph
  fits more than one connection. It now reports those pairs, so silence about a pair is not read as
  evidence against it.
- **Nesting is read transitively.** `_containment_relations` reads one level, which is the level the
  completeness rules compare and is unchanged. A body nesting an element two levels down also states
  that the outermost contains it, and `indirect_nesting_relations` states the ancestry above the
  immediate parent, with an unaliased grouping transparent as it is there.
- **Endpoints are compared through `parse_connection_id`.** The `source---target@@type` form is not
  spelled a second time, because a plain `find("---")` matches the hyphen inside a slug.

A reference is dropped only where all three hold: both endpoints are among the entities the body
declares, the pair is not one the reader could not decide, and the reference is not among what the
body draws.

Connections only. The entity side refuses the equivalent write already — **E309** fires when
`entity-ids-used` names an entity whose alias the body does not declare — so there is no silent drift
there, and reconciling it would turn a refusal into an automatic rewrite of the author's frontmatter.
The asymmetry is that the connection side had no such rule; E316 catches only the inverse, a relation
drawn but unlisted.

`puml="auto-sync"` does not do this and is not meant to. It restores consistency by redrawing the
missing edge, which resolves the disagreement in favour of the stored reference rather than the body.
On a `manual-layout` diagram the union is kept deliberately, because there the picture is the
author's.

## What may host an artifact

The deployment projection listed five host types and the relationship table permitted the first hop of
the deployment chain from one of them. One row states it for the class the five share, in the
vocabulary the table already speaks, so one row replaces four:

```yaml
- ["@technology-internal-active-structure-element", artifact, [assignment]]
- [technology-node, artifact, [aggregation]]
```

Aggregation stays on the pair that already had it and is not widened alongside assignment. The models
it exists for can only have used that pair, since it was the only one ever permitted, and widening it
would break the composition-mirrors-aggregation invariant (ArchiMate 4 §5.1.2) in four new places —
whose one documented exception is that pair.

`_DEPLOYMENT_HOST_TYPES` is gone. The host set derives from the class that defines it, through the
port that already answers class membership, and a derived set cannot drift from the table.

`_HOSTING_TYPES` becomes two sets, because it answered two questions with one literal.
`_ARTIFACT_HOSTING_TYPES` is what puts an artifact on a host: assignment and aggregation, with
composition dropped because the table permits it from no host into an artifact, so no valid model can
hold one. `_NODE_CONTAINMENT_TYPES` is what puts one host inside another: composition and aggregation,
and composition belongs there. A single shrunken set flattens every deployment view into one box,
which says the containers run side by side on a machine rather than together inside a runtime.

The gates are three, one per pair, deliberately not combined. A single gate over "the hosting types"
would make one pair's requirement drive the other pair's fix, and would drive the wrong one.

Reading `serving` as hosting is a standing non-goal with a test that says so. It is the only direct
technology-to-application rule, so it looks like the obvious substitute, and it means the opposite:
ArchiMate separates assignment, which allocates, from serving, which consumes.

## One specification per format facet

A shipped description said `format: uri` was informative only and that any string was accepted, while
the checker refused values. The description and the checker were two statements of one rule, in two
layers, free to drift — and they had drifted once already, the correction having been written into a
materialised copy without reaching the default it was copied from.

`format_rules` specifies each format as the procedure that decides it: the alternatives a value may
satisfy, one predicate each, any of them sufficing. The application's checker runs that rule instead
of holding its own copy, and both the shipped description and the refusal message are composed from
the rule's own terms, so neither can say something the procedure does not do.

There is no equality gate between a materialised copy and the shipped default.
`DefaultSchemataEnsureStep` documents a divergent copy as a supported state, since an operator's local
edit is never overwritten, so such a gate would turn a future customisation into a build failure. What
the gate asserts instead holds regardless: every declared format is one the checker runs, a
description saying what its format accepts says it in the rule's terms, and no shipped description
claims a format is unenforced. It is stated over the whole shipped schema set rather than the
ArchiMate subset of it.

## A gate that failed at random

`uv run zuban check` reported `Invalid type comment or annotation` on a file no change had touched, on
some runs and not others. Two modules named each other: the endpoint planner imports the refusal
wording at runtime, and the wording named the planner's own types under `TYPE_CHECKING`. That is
invisible to Python, but a type checker resolving the pair has to pick a side, and which side it
picked depended on what else it had already read. The value types both modules speak moved to
`endpoint_vocabulary`, which each imports downward; `backend_endpoint` re-exports them, so no caller
changed.

`tests/architecture/test_no_type_checking_import_cycles.py` refuses the shape, as the conservative
rule it is: the same cycle restored after the extraction leaves the checker passing, because the
annotated names are then defined in a third module the cycle does not pass through. So such a cycle is
a latent hazard rather than a proven failure, and the one pre-existing pair carries an allowance with
what is known about it.
