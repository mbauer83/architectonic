## A bridge that lost its backend answered nothing, for ever

**Reproduced first, at the wire level.** A bridge (`arch-mcp-stdio-read`) was pointed at a real backend
on a throwaway port, the backend was stopped mid-session, and one `tools/list` was written to the
bridge's stdin:

| | Before | Now |
| --- | --- | --- |
| reply to the pending id | **none, for the full 45 s deadline** | a JSON-RPC error in **10 ms** |
| the bridge process | **still running** | exited with status 3 |
| what a client could observe | nothing — no reply, no error, no EOF | the error, then EOF |

That is the failure a live session hit: a bridge parked in `do_epoll_wait` for five hours on one second
of CPU, while nothing listened on its port.

**The recorded diagnosis named the wrong line.** The register blamed the
`isinstance(message, Exception)` branch in `_pump_reader_to_writer` for swallowing the transport's
failure. Instrumenting the transport showed that branch is never reached here: `httpx.ConnectError`
is raised in a task of the SDK's own task group and surfaces at the `streamablehttp_client` boundary,
not on the read stream. Both pumps were cancelled 10 ms after the request went out. The bridge simply
did nothing with the failure — and then could not exit.

**Why it could not exit.** `stdio_server` reads the client's stdin with `anyio.wrap_file`, i.e. in a
worker thread blocked in `readline()`, which cannot be cancelled. The task-group teardown therefore
waits for a line that a client waiting for a reply will never send. A `faulthandler` dump taken eight
seconds after the failure shows exactly that: the main thread back in the event loop, one AnyIO worker
parked in the read.

**The fix, in two obligations.**

- **Answer what was forwarded.** A proxy inherits the JSON-RPC contract it relays. Every request id
  taken from the client is recorded (`src/infrastructure/mcp/bridge_replies.py`) and answered with
  `CONNECTION_CLOSED` (-32000) and the reason when the backend can no longer answer it.
- **Stop.** The process ends with status 3 — distinct from the startup refusal — so the client
  relaunches a bridge that re-runs the autostart with its health and workspace-identity checks. Via
  `os._exit`, because returning cannot end this process for the reason above; the replies are written
  and flushed first.

The two directions are no longer the same pump, because the decision differs:

| Direction | An exception on the stream means | What happens |
| --- | --- | --- |
| client → backend | a line that is not JSON-RPC. No id, nothing broken. | named in the log, session continues |
| backend → client | a reply that cannot be attributed to any id | the session ends, the ids are answered |

`tests/infrastructure/mcp/test_bridge_answers_a_lost_backend.py` drives the real bridge process
against a stub MCP backend it then kills. Both it and the pump test fail against the previous
behaviour.

Two of the three defects in the report are deliberately untouched: the transport already has
`timeout=30` / `sse_read_timeout=300`, and re-resolving a backend mid-session is design work that
exiting makes unnecessary for now.

## The backend log had no bound

`.arch/backend.log` reached **62 MB over 491,225 lines** on a development box and was truncated by
hand. A serving backend now rotates its own log:

| Setting | Default | Meaning |
| --- | --- | --- |
| `backend.log_max_bytes` | 16 MiB | rotate once the log passes this |
| `backend.log_generations` | 3 | kept as `backend.log.1` … `.3`; at most **64 MiB** in total |

**Not a `RotatingFileHandler`, and the reason is the mechanism.** The log is not written through a
logging handler at all: `--daemon` hands its child a stdout and stderr that already point at the file,
so everything the process emits arrives by *file descriptor* — logging records, uvicorn's own output, a
traceback from interpreter shutdown, a print from a dependency. A handler would rotate the records it
formats and leave every other writer appending to the renamed inode: the same bytes, under a name
nobody reads, still growing.

So rotation happens where the descriptors are owned — rename the generations, then re-point stdout and
stderr at the fresh file — and `_redirect_stdio_to_backend_log` now delegates its output half to the
same function, so "this process writes to that file" has one definition rather than two.

**Only the log this process is writing to.** Every entry point compares stdout's inode against the
file's first. A foreground `arch-backend` on a terminal keeps its console; renaming a file it never
writes to and then redirecting its output into the replacement would have taken that away.

Verified against a real backend, not only in tests: one serving on a throwaway port with an 8 KiB
threshold rotated at 9,965 bytes, kept `backend.log.1`, and wrote everything after that — including the
line recording the rotation — to the new file.

## Every request was rendered twice in the log

Measured: one `curl` produced **three** lines.

| Line | Written by | Carries |
| --- | --- | --- |
| `HTTP request started …` | the application's middleware | method, path |
| `HTTP request completed …` | the application's middleware | method, path, status, **duration** |
| `… "GET /api/stats HTTP/1.1" 200` | uvicorn's access log | method, path, status |

The third is a second rendering of the event the second already records, carrying less. The SPA polls
continuously, so what it added said nothing new: in one window `/api/sync/status` appeared 7,238 times,
`/api/events` 6,073, `/api/assurance/status` 3,860. `access_log=False`.

**It was not free.** The register that measures which REST operations the *running* application has
executed reads uvicorn's access format, and so do the three REST/MCP walks. Dropping the line took all
three walks to **zero** reached operations — caught by the full suite, not by reasoning. So
`parse_requested_routes` now reads either shape. Both, not only the new one: the negative half of that
register depends on history predating `REGISTER_TAKEN` (2026-08-02), and every line of that history is
in uvicorn's format, so recognising one shape would have retired the evidence along with the
duplication.

## A failing fetch retried every minute for ever

The engagement fetch retried every 60 s with no backoff, no cap and no deduplication, so one
unreachable origin wrote git's six lines of stderr for as long as the backend ran — **7.3 MB of the
same failure** on an instance whose key needed an agent.

A remote that has just refused is now deferred, doubling from the poll interval to a ceiling of half an
hour, and one success clears the record:

| Twenty minutes of an unreachable origin | Before | Now |
| --- | --- | --- |
| fetch attempts | 20 | **5** (60 s, 120 s, 240 s, 480 s, 960 s) |
| lines carrying git's stderr | 20 | **1** — the first attempt of the episode |
| what the later lines say | the same six lines again | the attempt count and the next attempt |

The ceiling matters as much as the doubling: a permanently broken remote must not end up retried once a
week, because a fix on the other side has to be noticed without a restart.

**Both roles come through one gate.** The enterprise path fetched separately and recorded its own
health reason, so a broken remote was retried at two rates for two reasons. `_fetch_origin` reports
which of three things happened — `Fetched`, `FetchFailed`, `FetchDeferred` — and the enterprise path
still persists a failure while a *deferral* adds nothing, because the record that earned it is still
standing.

## A gate that read 841 MB of coverage output

`tools/gui/.nyc_output` arrived with the E2E coverage flag and was not in the retired-route scan's skip
list, so its 221 istanbul files — 841 MB — were read in full and matched against all 67 retired
literals, once per scanning test.

| | Before | Now |
| --- | --- | --- |
| `tests/architecture/` | **over 10 minutes** | 42 s |
| the literal scan alone | over 8 minutes | 20 s |

A gate that slow is a gate a developer stops running. The skip list is a hand-maintained approximation
of `.gitignore`, and the comment now says so — along with why the obvious fix does not work here:
`git ls-files` at this root omits `enterprise-repository`, which is its own checkout and genuinely part
of the tree being scanned.

## An FMEA occurrence justification named the wrong date

`FMD@1785065977` (*Backend keeps serving assurance reads after activation was revoked*) carried an
occurrence re-affirmation whose text put the analysis's baseline at **2026-08-26**. The baseline is
**2026-07-26** — the day the failure mode and its FMEA were authored — and 2026-08-26 was a fortnight
*after* the revision that named it, so it could not have been a baseline for anything.

Re-recorded as revision 2 against the same basis digest, with the value unchanged at `unlikely`, so
nothing about the priority band moves. Two things changed besides the date:

- The prior text's commit count is **not restated**. It cannot be reproduced from the history (307
  commits since 2026-07-26, not 14), and a number nobody can check is not evidence for a judgement.
- The premise was re-checked rather than assumed, at `_sqlcipher_connection.py`: the connection pool
  still invalidates by generation, so revocation still takes effect in the running process.

The frequency band remains the owner's judgement, restated and not re-derived; revision 1 is retained,
as every superseded revision is.
