# 0.8.2 — detail

Maintainer-facing mechanism for the summary in `CHANGELOG.md`.

---

## An ordered value set is coloured along a gradient

A value set with an order — a maturity ladder, a risk band — was coloured from the qualitative
palette, which assigns a colour by a member's position in the declared order and cycles when it runs
out. Six members came out as six unrelated hues. A picture then said which value each element held
and nothing about which elements were further along, which is the question the attribute exists to
answer.

Members now spread along a named gradient in declared order. The member a schema declares as its
`default` takes white and is removed from the spread, so the remaining members still use the whole
range: with six members of which one is unset, five span the gradient rather than being squeezed into
four fifths of it.

### The four constraints that fix every stop

- **No stop is a neutral.** White means "not assessed". A grey or near-white stop in the middle of a
  scale says the same thing in the same picture, so a reader cannot tell an unassessed element from a
  middling one. This rules out the standard colour-blind-safe schemes, which are diverging and pivot
  on exactly that.
- **No stop is muddy.** Red interpolated straight to green runs through brown: the two channels cross
  over at the middle, which is the half of the scale a reader most needs to read.
- **Adjacent members stay apart** — at least a CIE76 dE of 25, which is about where two fills stop
  reading as one at the size a diagram draws an element. The three-stop versions of both gradients
  bunched their members at whichever end the stops were sparse in: 26 between the middle members of
  one, 27 between the top two of the other.
- **The far end is not an ink.** Darkening it widens the last gap and is measured as an improvement,
  while a reader sees "off" rather than the end of a scale. Held at L\* 27.

Both gradients carry five stops, so a five-member set lands one on each and every colour a reader sees
is a chosen one. `yellow-blue` is the colour-blind alternative: those two
poles survive every common form, and it runs light to dark so it survives greyscale as well.

All four constraints are tests over the derivation, because the stops are where a later edit loses
them. The tests also record the limit: **beyond six graded members no two-colour-family gradient keeps
them apart**, and a larger value set wants a palette.

`scale_tokens` is a variable-length tuple and the served contract a list, so a gradient with middle
stops *looked* representable. Four places enforced exactly two, and one did it silently: the
presentation parser replaced anything but a pair with `()`. A scale declaring five stops became a
scale declaring none, and the failure of a scale is silence — no error, no warning, a picture carrying
its authored fills. All four now take two or more, and one stop-walking function serves the ramp path
and the graded path alike.

Both gradients are also offered reversed — `green-red` beside `red-green`, `blue-yellow` beside
`yellow-blue` — because the direction belongs to the reader. These run bad to good, which is a
maturity ladder; a risk band is the same shape upside down, with its high end the bad one. The
reverses are derived from the same stops rather than written out again, so a stop edited once is
edited for both directions and the four constraints above cover a reversed gradient without naming it.

One consequence is worth stating: a *number* keeps the magnitude pair unless a reader names a
gradient. Applying a bad-to-good gradient to a numeric ramp by default paints a large `risk_score`
green. So "no gradient named" and "the default gradient" are different requests — a graded value set
is coloured by the default either way, a ramp is not.

## The control, and where the colours come from

The reading panel offered a colour per member and nothing else, so the gradient choice was reachable
only by editing a URL.

It now shows the gradients above the swatches, each **previewing itself** as the colours it gives this
attribute's graded members — a name alone asks a reader to imagine the result. The per-member pickers
are unchanged and still win: a reader's own colour applies over whatever the gradient gives.

The gradients also put the panel and the picture at odds. The panel derived its swatches in the
browser from the qualitative palette while the fills came from the gradient on the server, so the key
would have described a colouring the picture did not use — the one thing the panel exists to prevent.

So the server hands over the colours. Each attribute offer carries `colour_by_gradient` as
`{gradient: {member: colour}}` — every gradient at once, so switching costs no round trip — beside the
unset member and the panel's list of gradient names. The browser holds no gradient table and derives
no colours, and a control cannot offer a gradient the renderer will not accept because it offers what
it was served.

## One colouring or two

A diagram normally carries two colourings at once. An element is filled by its kind — the stereotype
fill its ontology declares — and colouring by an attribute repaints only the elements that carry a
value for it. That is honest, and it is often what a reader wants: the kind is still true, and it is
what they navigate by. It is also one fill channel carrying two meanings, and a reader looking at a
green box has to ask which of them it is.

`Element-kind colours` now offers `Keep` or `Remove`. Removing gives every element the attribute says
nothing about the **unset member's** colour rather than a colour of its own, because a value nobody
recorded and a value declared "not assessed" are one state to a reader — a second neutral beside the
first would put a third meaning in the channel the choice exists to clear. A reader who recolours the
unset member moves both, through the same lookup, so one neutral stays one neutral.

Three refusals keep it a reading rather than a blanking:

- **It does nothing without an attribute colouring.** With nothing to make room for, removing the kind
  colours leaves every element the same neutral — a blank diagram out of a request that meant to draw
  a clearer one. A stale choice in a URL cannot do that to a diagram nobody asked to have coloured.
- **Containers keep their colour.** A grouping is not something an attribute could have spoken about,
  and a neutral plane behind the elements would erase the structure a reader navigates by.
- **An unrecognised name keeps the colouring.** Falling the other way would repaint every element a
  reader did not ask about, off a mistyped URL.

It is one diagram-level control rather than one per attribute, and beside the legend rather than in the
attribute rows: there is one colouring at a time, so what becomes of the kind colours is a fact about
the picture.

## Styling a stereotype is not drawing one

Both are spelled `<<name>>`. A `skinparam rectangle<<goal>> { … }` block says how a goal would be
drawn; whether any element takes it is a separate question, and `referenced_in` — which every caller
asks that second question of — matched the glyph anywhere. Every stored diagram carries its own
skinparam blocks inlined, so every kind a body styles was reported as a kind it draws.

The legend read that as "this fill is still on screen" and named a colour no element carried. It was
visible wherever an attribute colouring recoloured *every* element of a kind, which the section
handling that case was written to prevent; removing the element-kind colouring makes it happen on every
diagram, which is how it was found. The pattern's own comment had said "on an element line" since it
was written.

The styling declaration now has a register row in `test_each_syntax_has_one_reader.py`, with one
spelling of its head serving both questions asked of it. The bare `<<name>>` reference deliberately has
no row: that glyph is also how an arrow names its relation type, and the grouping parser, the two
relation parsers and the verifier's rules read it for genuinely different purposes.

## What a reader calls an element type

An ArchiMate value stream is drawn as the stages that make it up, so a box in one is a stage, and a
legend calling it "Value Stream" names the diagram rather than the box.

`EntityTypeInfo.label` carries what a reader calls a type where the type's own name is not it. It is
declared by the ontology, so every surface naming a type says the same thing, and it is injected into
the legend the way the rest of `rendering/` takes what it presents. Only `value-stream` declares one;
everything else derives its name.

Element kinds and relationships are terms of the modelling language, so the legend names them as
proper names — Application Component, Strategy Grouping, Assignment — through `readable_label`, the
one owner of that spelling, so all five legend sections agree.

## Correcting a hand-laid diagram's references

W307 names a wrong `connection-ids-used` entry and told the caller to pass `connection_ids` alongside
`puml`. On a hand-laid diagram that means a *literal* body, which runs to tens of kilobytes — so on
exactly the diagrams the rule fires on, the correction did not fit in a call and the warning repeated.

`entity_ids` and `connection_ids` are now taken beside `puml="auto-sync"`. They are a claim about the
body rather than an edit to it, and a sync already rewrites those two fields' spellings, so they sit
inside what a sync does. Where the sync keeps the body verbatim the lists change and nothing else does.
Where it regenerates the body, a stated set is refused: that body decides what it draws and therefore
what it records.

Those two fields were the only ones a sync accepted and dropped in silence. Every other field it will
not carry was already refused.

## Fullscreen survives a save

The browser leaves fullscreen when its fullscreen element is removed from the document, and every
reload removed it: a save re-ran the diagram query, which discarded the data and raised the loading
flag, and the branch holding the canvas is chosen on both.

A reload of the diagram already on screen is a refresh and keeps what is on screen. `run()` already
clears the error and supersedes an in-flight call, so `reset()` contributed only the discard — right
when a different diagram is being loaded, and wrong on a refresh.

This ships without an automated test. Whether a detached element ends fullscreen is the browser's
rule, so it belongs in the browser suite; and every trigger for the reload path writes to the model, so
a spec driving one leaves a modified file behind on every run. No spec in the suite does that, and the
release gate should not start. A working spec exists and lands with e2e isolation, where a run gets a
seeded fixture repository to write to and throw away.
